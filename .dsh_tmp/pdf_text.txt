摘要
知识图谱以其结构化、语义化的知识表达能力，已成为支撑智能教育与个性

识图谱智能构建与学习导航系统。系统围绕“课程资料上传→文档解析→大模型
知识抽取 → Neo4j 图谱存储 → 图谱可视化 → RAG 智能问答 → 学习路径推荐 →
题库练习”的完整业务闭环展开。

策树、负例约束的 Prompt 体系，并支持前置、包含、相关、应用四类知识关系，

径推荐，并提供题库练习、课程协作等教学功能，实现 “图谱推荐学什么 → 题库
提供对应练习”的闭环。
在工程实现环节，系统采用 SQLite 与 Neo4j 双存储架构，后端基于 FastAPI、

4.3 双存储设计
系统数据按其访问模式分为两类：一类是用户、课程、文档、学习记录、题库
等结构化业务数据，具有事务性与频繁联表查询特征；另一类是知识点及其关系

由 Python 标准库直接支持，无需安装配置；连接管理、建表与幂等迁移封装于
core/sql_database.py。考虑到比赛演示与部署场景，第一阶段以SQLite落地；若后
续需迁移 MySQL，仅替换该模块底层连接实现即可，表名、字段名与方法签名保
持不变，业务代码零改动（类型映射参考见交付文档）。

第 5 章 知识抽取设计与实现
知识抽取是整套系统的起点，其输出质量直接决定图谱质量与上层应用（问
答、路径推荐）的可用性。本章介绍基于大语言模型的知识抽取方案、Prompt工程
设计、分块与并发策略以及参数冻结纪律。本章描述与实现代码（backend/app/
services/knowledge_extractor.py）、评测配置（backend/eval_config.py）及
《V1.1冻结说明》逐点对应。
5.1 LLM 抽取方案
（1）单阶段抽取架构 系统采用单阶段抽取方案：大语言模型在一次调用中同
时完成知识点实体识别与关系提取，输入为课程文本分块，输出为JSON格式的实
体列表与关系列表。相比两阶段方案（先抽实体、再判关系），单阶段方案减少了
调用次数与拼接错误的可能，同时让关系判定能够利用实体识别的上下文信息。
（2）实体模型 每个知识点实体包含三个字段：name（知识点名称，要求简洁、
规范、稳定）、category（类别，限「概念」「定理」「公式」「方法」四类，无法归
类时用「概念」）、description（一句话描述该知识点在课程中的含义）。实体粒
度要求为” 独立可学习的知识点”，不过度拆分也不堆砌冗余修饰；同义词与中英
文缩并需合并为一个规范名称；人名、页码、章节标题、指代词、普通名词等明确
不抽取。
（3）关系模型 系统支持四类知识关系，类型以英文大写表达：PRECEDES（前
置知识，学习依赖）、CONTAINS（包含，上下位/整体-部分/类别-成员）、RELATED_TO
（相关概念）、APPLIES_TO（应用，方法/技术用于解决问题）。每条关系必须携带
两个证据字段：evidence（支持该关系的原文短句，必须逐字来自输入文本）与
confidence（0 1 置信度，如实反映证据强弱）。这两类证据随关系入图，为教师
审核与后续评测提供溯源依据。
（4）处理流程 完整抽取流程为如图 5.1 的四步：文本分块（上限 6000 tokens，
相邻块重叠400tokens）→分块并发抽取（最大并发4）→失败分块重试（限流/超
时导致的分块失败串行重试一次）→ 结果合并与完整性校验。合并阶段承担全部
数据完整性约束：实体按规范名去重（全角转半角、空白折叠、纯英文缩写统一大
写）；关系执行类型白名单过滤、空值/自环过滤、source/target实体存在性校验（过
滤悬空边）、按三元组去重、置信度阈值过滤；分块错误透传（最多 3 条）供上层
判断抽取是否真正成功。这些约束不依赖LLM自觉，全部在应用层兜底。

6.1 Neo4j 图模型
（1）存储选型 知识图谱存储选用Neo4j图数据库，节点标签为KnowledgePoint。
相比关系型数据库的邻接表建模，图数据库天然支持可变长度的路径遍历（如前置
知识链的递归查询），无需维护传递闭包表，是学习路径推荐等图算法的直接支撑。
图数据库与 SQLite 的关系为：SQLite 保存用户、课程、文档、学习记录、题库等
关系型业务数据与知识点向量，Neo4j只保存知识点节点与关系；知识点在SQLite
中的元数据以 kp_id 作为逻辑外键与 Neo4j 节点互指，不建物理外键（跨库无法
建）。
（2）节点模型 KnowledgePoint 节点携带以下属性：kp_id（全局唯一标识，
SQLite 逻辑外键）、name（知识点名称）、category（类别，中文「概念/定理/公
式/方法」存储，另映射英文type字段）、description（一句话描述）、course_id
与 document_id（整数，双重归属隔离——同一课程不同文档的图谱互相隔离）、
confidence（节点置信度，构建期缺省 0.9）、is_manual（是否为教师手动创建，
自动抽取节点为false）。节点创建为幂等操作（同文档内按名称MERGE）。
（3）关系模型 关系类型为四类英文大写类型（PRECEDES/CONTAINS/RELATED_TO
/ APPLIES_TO），每类对应中文标签（前置知识/包含/相关概念/应用），供前端图
例与界面展示。每条关系携带confidence（LLM判断的置信度，缺失时保守填充
0.8）与evidence（原文证据短句）两个属性，以及is_manual标记。证据与置信
度入图的目的：使教师能够在图谱上直接审核LLM抽取的每一条关系，逐条溯源
到原文。
（4）构建流程与完整性校验 文档抽取完成后，build_graph依次创建节点与关
系。应用层在入图前再次执行完整性校验：关系类型白名单过滤（VALID_RELATION_TYPES）、
空值与自环过滤、关系创建异常（如目标节点不存在）捕获——无效关系不入图。
构建结果返回节点数与关系数，供上传流程回显。

题库与练习系统为教师提供基于知识图谱的组题能力，为学生提供”学练结合”

9.1 题型与判分
（1）题型范围 系统第一版支持三种可自动判分的客观题型：单选题（SINGLE）、
多选题（MULTI）与判断题（JUDGE）。填空题与简答题因需要答案归一化策略或大
模型评分、准确性无法保证，暂不纳入第一版；表结构已预留q_type白名单扩展
位，便于后续扩展。
（2）判分口径 三类题型的判分规则如下：单选题采用选项键归一化后严格相
等（如标准答案"A"与作答"A"判对，"a"经全角转半角、转小写归一化后同样判
对）；多选题采用选项键集合严格相等，顺序无关，少选或多选均判错；判断题采
用布尔同义归一化（”对/正确/是/true/T/1”一律视为true，”错/错误/否/false/F/0”一
律视为false，无法识别的作答判错）。所有比较均基于归一化后的文本进行，不改
变存储值；未作答一律判错。
（3）存储设计 题目的options（选项列表）与answer（答案）一律以JSON文
本序列化后入库。采用该设计有两方面原因：其一，SQLite无数组类型；其二，开发
期曾出现直接原样入库导致回读失败的缺陷——单选答案 "A" 回读时 json.loads
会失败、判断答案"true"会被误读成布尔值，导致”单选题永远判错”，该缺陷被
test_question_bank.py 捕获并修复，入库与回读统一走 JSON 序列化/反序列化
封装。
（4）答案下发时机（防泄题机制）教师出题与学生练习的答案下发遵循严格时
机控制：学生端出题接口走白名单投影（_public_view），只返回题目编号、题型、
题干、选项、难度、关联知识点与收藏状态，绝不包含 answer 与 analysis 字段；
只有学生提交作答、服务端判分之后，才随判分结果返回正确答案与解析。学生查
看本人已作答记录的接口返回正确答案（用于回看复习），属预期行为。教师端接
口返回完整答案与解析，但每个方法均执行” 课程归属校验”——非本课程教师一
律拒绝（错误码4003），不能仅依赖教师角色判断。

第 12 章 市场背景与可行性分析
12.1 市场背景
12.1.1 市场需求
（1）课程知识服务需求 随着课程数字化资源持续积累，教师与学生对于“知
识导航、智能问答、个性化学习”等结构化知识服务的需求逐步增加。传统课程资
料主要以教材、课件、讲义等非结构化形式存在，知识点之间的关联关系需要依靠
教师经验进行整理，导致课程知识图谱的构建成本较高，使相关智能学习服务难
以在普通课程中广泛落地。
本系统通过“课程文档上传 → 知识抽取 → 图谱构建 → 智能应用”的方式降
低知识图谱构建门槛，使教师无需手工完成大规模知识点和关系标注，即可形成
可视化课程知识图谱，并进一步支撑智能问答、学习路径推荐和题目推荐等功能。
（2）教师侧建设需求 对教师而言，课程资料在长期教学过程中不断积累，但
资料整理、知识点维护和教学资源组织需要投入大量时间。尤其当课程知识点数
量较多时，传统人工维护方式难以保证知识结构的一致性和更新效率。
本系统以教师为课程知识建设主体，提供文档上传、知识图谱自动构建、图谱
可视化、知识点编辑和关系修正等功能，形成“机器构建+教师校验”的课程知识
建设模式，在降低建设成本的同时保留教师对知识内容的控制权。
（3）学生侧学习需求 学生在课程学习过程中不仅需要获取知识内容，还需要
明确“先学什么、后学什么、哪些内容需要复习”等问题。传统课程平台主要提供
资料浏览与题目练习，知识之间的结构关系与学习顺序通常需要学生自行判断。
本系统利用课程知识图谱中的前置关系，为学生提供前置知识查询、下一步
学习推荐和目标知识点学习路径，并结合课程知识库提供带来源的智能问答，使
课程资料由“静态资源”进一步转化为“可导航、可查询、可练习”的知识服务。
12.1.2 目标市场与用户
（1）核心目标市场 本系统主要面向高校及职业院校的课程教学场景，重点服
务具有数字化课程资源、课程知识体系较为稳定、同时存在智能学习需求的教学
团队。
（2）核心用户 直接用户包括授课教师、学生和教学管理人员。教师负责课程
知识图谱的建设、维护和教学资源管理；学生使用知识图谱、在线文档、智能问

（3）潜在用户 院系教务部门、教学质量评估部门以及承担课程数字化建设工

12.1.3 政策与产业机会
（1）教育数字化发展带来的机会 教育数字化持续推进，高校课程资源逐步向
数字化、智能化方向发展，为课程知识组织和智能学习服务创造了应用空间。本项

文档，这些资料本身具有较高的知识价值，但目前大量内容仍以非结构化形式存

（3）轻量化部署带来的机会 本系统采用SQLite、Neo4j、FastAPI、Vue3等轻
量技术栈，主要依赖大模型和向量服务完成智能处理，能够在普通电脑环境下完
成部署和运行，适合课程级、院系级的小规模试点，也为后续在高校内部逐步推广
提供条件。
12.1.4 竞争格局与差异化
（1）传统教学平台的局限 现有课程平台已经能够提供课程资料、视频、题目
和学习记录等基础功能，但课程知识点之间的结构关系通常没有被充分利用，知
识图谱构建和个性化学习导航能力相对有限。
（2）商业知识图谱平台的特点 部分商业知识图谱产品主要服务于企业知识管
理或大型数字化项目，通常需要较高的部署、实施和维护成本，与高校单门课程或
院系级课程建设的轻量应用场景存在一定差异。
（3）项目差异化定位 本系统主要形成三方面差异化：第一，以课程文档为输

示层面；第三，采用轻量化技术栈和普通电脑部署方案，降低课程级应用的使用门
