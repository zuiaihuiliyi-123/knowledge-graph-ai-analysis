## 三、口径冻结

**这是地基，必须在跑任何数之前定死，定死后不得回改。**

### 3.1 主指标定义：Core / Full 双层金标准

**问题根源**：现行 gold 采用"宁可漏标"的保守标注（15330 字符只标 33 条关系），而模型输出是"尽可能全"的（约 70 条/轮）。用**选择性 gold** 去算**完备性预测**的 Precision，模型必然被大量"合理但未标注"的关系压死。第7章报告 §三 的归因证实了这一点：

| 错误类别 | 3 轮合计 | 性质 |
|----------|:--------:|------|
| 纯臆造（节点对不在 gold） | 118 FP | **多数可能是"合理但 gold 未标"** |
| 方向颠倒 | 30 FP / 28 FN | 真实缺陷 |
| 节点对对、类型判错 | 25 FP / 3 FN | 真实缺陷 |
| 完全漏抽 | 36 FN | 真实缺陷 |

118 条"臆造"里混着大量金标准粒度问题，直接算进 Precision 不公平、也不可信。

**修正方案**：每篇文档标两层关系集。

- **Core 集**：文本明确、无争议、按决策树必然成立的关系 → **用于计算 Recall**
- **Full 集**：`Core ∪ {合理但边界模糊的关系}`（含 RELATED_TO、整体-部分、应用场景） → **用于计算 Precision**

**主指标**：

```
Recall    = |Pred ∩ Core| / |Core|
Precision = |Pred ∩ Full| / |Pred|
F1        = 2PR / (P+R)          ← 记为 F1_full，作为赛题申报口径
F1_core   = Core 集上的完整 P/R/F1  ← 保守下界，一并披露
```

报告**必须同时披露 `F1_core` 与 `F1_full`**，并说明两者差异来源（Full 集的准入标准 + 边界案例登记簿）。这是方法学选择而非调参，写清楚即可。

> **这不是放水**：模型输出仍须落在 Full 集内才算对。方向错误、类型错误、真臆造照样全额扣分。Full 集只是把"人类标注员事后也认可"的关系还给模型。

### 4.3 Dev / Sealed 分离机制

对应 `项目说明3.md` 风险项"禁止跑一次→改一次"：

- **开发集（D1/D2）**：Prompt 迭代时反复跑，允许看错误、改 Prompt
- **封存集（T1/T2）**：Prompt 定稿并冻结版本号后**只跑一次**，结果直接进报告
- **物理隔离**：封存集 gold 与预测结果放 `eval_data/sealed/`，由另一名队员保管，跑前不开封
- 封存集跑完后，**封存集上的任何 Prompt 调整都视为新一轮实验**，需重新封存新文档

### 4.4 标注规范（升级为通用手册 `docs/标注手册.md`）

**关键：标注用的决策树必须与 Prompt 里的决策树是同一份。** 否则人和模型按不同规则判，指标无意义。

1. 实体类别定义（概念/定理/公式/方法）与粒度规则（何为"独立可学习的知识点"）
2. 关系决策树：CONTAINS → PRECEDES → APPLIES_TO → RELATED_TO → 不输出（**与 [knowledge_extractor.py](backend/app/services/knowledge_extractor.py) 第 39–45 行逐条对齐**）
3. **Core / Full 双层判定标准**（§3.1），含正反例各 ≥5 条
4. 同义归一化规则（标注阶段就统一到规范名）
5. **边界案例登记簿**：所有争议判定记录并给出结论 → 直接作为 Prompt Few-shot 素材
6. 每条关系必须带 `evidence`（原文逐字短句，`validate_gold.py` 程序校验）
7. 每条关系标 `core: true/false`

### 4.5 质量保障

- **双人独立标注**至少 D1、T1 两篇，计算 **Cohen's Kappa**；实体 Kappa ≥0.8、关系 Kappa ≥0.6 为合格
- 分歧由第三人仲裁，结论写入边界案例登记簿
- `scripts/validate_gold.py` 程序校验（C6 后增加 Core ⊆ Full 校验）
- 标注完成后 **gold 打 SHA256 冻结**，写入报告

### 4.6 工作量

按第7章已标注文档的精细度（49 实体 / 33 关系 / 每条含 evidence）：

| 任务 | 单篇工时 |
|------|:--------:|
| 文本准备（清洗 + 分块 + 来源登记） | 0.5 h |
| Core 集标注 | 2 h |
| Full 集补标（含边界仲裁） | 2 h |
| 程序校验 + 修订 | 0.5 h |
| **合计** | **5 h / 篇** |

4 篇 ≈ **2.5 人天**；双人标注则 ×1.8 ≈ **4.5 人天**。

> **降级预案**：人力/时间不足时最低配置为 **3 篇**（D1 复用 + D2 化学 + T1 物理），仍跨 2 门课。但 **D2 不可省**——否则开发集只有 1 篇，改 Prompt 必然过拟合。

### C6 — `validate_gold.py` 增强 ✅

**实施结果（与下述原方案有出入，差异已注明）**

原方案：支持 `core` 字段 · 校验 Core ⊆ Full · 输出 Core/Full 计数。

实际做的前两件事是原方案没预料到的：

1. **适配 list-of-docs（原方案漏了，且这是崩溃级问题）**：C2 把 gold 从 dict 改成 list 之后，`validate_gold.py:32` 仍在按 dict 读，`AttributeError: 'list' object has no attribute 'get'` —— 对**所有** gold 文件直接崩，不是"不支持 core 字段"这么轻。
2. **把校验项从"Core ⊆ Full"换成"Core 非空"**：原方案那一条是**恒真的**。本数据模型里 Core 定义为 `core=true` 的关系、Full 定义为全部关系，子集关系由构造保证，永远不可能失败，作为校验项没有意义。真正会出错且**会静默污染指标**的是 Core 全空 —— 此时 `eval_accuracy.py` 的 `recall = 0/0 = 0.0`，报告会把它当作"召回率为零"发出去，看上去像模型一个都没抽对。故校验这一项。

最终校验项：

- 顶层 list-of-docs（兼容旧 dict 写法）；`text_id` 全局唯一
- 实体：name 非空不重复 / category 合法 / description 非空
- 关系：type 合法 / 端点存在于实体 / 无自环 / 无重复三元组 / confidence ∈ [0,1]
- evidence 逐字存在于原文（提供 `--text` 或 `--text-dir` 时启用）
- **`core` 必须是 JSON 布尔**（挡 `"core": "true"` / `1` / `"是"` 这类手写错误；`bool` 是 `int` 子类，判断顺序不能反）
- **Core 非空**（错误）；**Core == Full** 时警告"双层口径未生效"
- 输出每个文档的 实体/关系/Core/Full/Core占比

用法：

```bash
python scripts/validate_gold.py eval_data/gold_第7章_树.json                  # 形式校验
python scripts/validate_gold.py eval_data/gold_第7章_树.json eval_data/第7章_树.txt   # + evidence 逐字
python scripts/validate_gold.py eval_data/gold_all.json --text-dir eval_data/  # 多文档
```

现状：`gold_第7章_树.json` 与 `_人工版.json` 全部校验通过（33/33 与 17/17 条 evidence 逐字命中）。`gold_数据结构第一章.json` **不通过** —— 它是从已删除的 `test_extraction_accuracy.py` 内联 Python 集合归档而来，本就没有 `description` 与 `evidence` 字段。该文件仅为历史可复现性保留，**不是合格标注**，不必修。

### C6 附 — 错误归因拆桶与对账（原计划未列，实测发现的缺陷）✅

`collect_dropped_relations()` 返回 4 种丢弃原因，但 `build_error_taxonomy()` 把它们**全部计入 `synonym_split`** —— 于是"端点为空""关系类型非法"都被算成"同义拆分"。三者是完全不同的 Prompt 缺陷，混在一个桶里等于这一列不可用。

同时发现两个更深的问题：

1. **抽取器侧证据被销毁**：`_merge_results` 在关系写入预测**之前**就静默 `continue` 掉了非法类型/自环/悬空边/重复/低置信度。评测器看到的预测里这些关系根本不存在，所以 `collect_dropped_relations` 对 live 路径**恒为空**——只对手写预测文件有效。已让 `_merge_results` 返回 `raw_relation_count` / `dropped_counts` / `dropped_relations`，并随 `--live` 落盘。
2. **`low_confidence` 会伪装成召回不足**：被置信度阈值砍掉的关系若本来是对的，会被 `missed_core` 记成"模型没抽到"，把"阈值设太严"误诊为"模型能力不够"。现在单独成列。

改动后 `counts` 分三组：**已评分的三类 FP** / **评分前被丢弃的 6 类** / **对账三个数**。并新增对账等式 `原始输出 == 进入评分 + 丢弃`，不成立时报告显式标 ✗ 而不是给出一份对不上的归因。

验证：6 种丢弃原因全部触发且对账平衡（合成输入，不调 LLM）；第7章历史预测复算 `75 = 74 + 1`、`62 = 55 + 7`、`70 = 69 + 1` 三轮全部 ✓。

### C7 — `eval_accuracy_live.py` 支持多文档 + 落盘预测

现状痛点：`TEXT_FILE` / `GOLD_FILE` 硬编码（[第35-37行](backend/eval_accuracy_live.py#L35-L37)），预测只存在 report 的 `runs` 里。

### 6.2 执行流程：三步严格分离

```
① 抽取    eval_accuracy_live.py  →  落盘 pred_<doc>.json（含原始 LLM 输出）
   ↓      【此后不再调用 LLM】
② 评分    eval_accuracy.py --gold ... --pred ...  →  eval_report_<doc>.json
   ↓      【gold / alias 已冻结，不得回改】
③ 报告    make_report.py 由 json 生成 Markdown（禁止手抄数字）
```

**铁律**：
- 预测结果**先落盘再评分**。任何"跑一次不满意再跑一次"都必须作为**独立轮次**记录，不得覆盖，且不得只报最好那轮
- 多轮取 **mean ± std**，同时报 `entity_stability` / `relation_stability`
- **禁止在预测后修改 gold、别名表或匹配规则**；如需修改，升级版本号并**全量重算**
