### 1.3 统一设计原则

全部提示词遵循以下五条共同原则：

1. **输出形态与下游消费方式匹配**——**凡是输出要被程序解析的提示词**（P1 知识抽取、P2 关系补全、P7 答案补全、P8 试题抽取，以及 P4/P5 的结构化字段），一律要求"严格只输出 JSON，不要 Markdown 代码块、不要解释文字"，并在 System Prompt 中重申，保证程序可直接解析、无需二次清洗；**凡是输出本身就是最终交付物的提示词**（P3 问答回答、P6 教材翻译），则要求保持既有结构、只输出目标内容、不附加解释或前后缀。两类任务的约束目标一致——**消除输出中的非交付内容**，区别只在交付物是"结构化数据"还是"自然语言正文"。因此 P6 的翻译提示词不要求 JSON，这与本原则并不冲突。
2. **证据约束**：关系抽取类提示词要求每条关系必须携带 `evidence`（原文短句，不得编造）与 `confidence`（0~1 置信度），实现抽取结果可溯源、可人工核验——这是赛题"知识抽取准确率 ≥70%"（出处见 `docs/项目说明3.md` §二）能够被**验证**而非仅凭主观判断的基础。需明确的是：本项目的申报口径是 Gold 标注下的 **P/R/F1 指标**（定义见 2.5 节），而非单一"准确率"数值；`confidence` 是模型自评、不参与评分，两者不可混用（详见 2.5 节第 4 点）。
3. **宁缺毋滥**：明确"宁可少抽取，也不要臆造关系""证据不足时宁可不输出"，避免 LLM 幻觉污染知识图谱。
4. **负向示例（反例）驱动**：在易混淆边界处同时给出正例与反例（如"栈是一种操作受限的线性表"必须判 CONTAINS 而非 PRECEDES）。在本项目的版本迭代实验中，针对**已定位的**边界错误补充反例约束后，残留臆造关系进一步下降（v1.2 → v1.5"臆造"由 31 条降至 5 条，见 2.4 节），说明反例约束对本任务具有明确的工程价值。需要说明的是，这是版本迭代过程中的工程观察，**并非"同一版本 + 正例"与"同一版本 + 反例"的严格对照实验**——本项目未单独设置该对照组，故不将其表述为普适结论。
5. **低温度采样**：凡涉及分类判断（关系类型、风险等级）的任务 temperature ≤ 0.15，抑制随机性；仅开放生成类（问答）放宽到 0.3。降低温度降低的是采样随机性，**并不等于结果严格确定**，两者区别见第八节。

## 二、P1 知识抽取提示词（核心，含完整迭代记录）

### 2.1 提示词设计目标

从课程文档分块中抽取"独立可学习的知识点"实体，并识别实体间的语义关系。这是全系统的技术核心，直接决定知识图谱质量与学习路径推荐的正确性。

**调用方式**：长文档先按 6000 tokens 分块（overlap 400 tokens），并发 4 路调用，逐块抽取后在代码层做实体归并与去重。

**System Prompt**：

```
你是一个精确的知识图谱构建助手。请只输出JSON格式的结果。
```

### 2.1.1 Prompt 与确定性工程规则的职责边界

本项目的抽取质量由**提示词**与**确定性工程规则**共同保证。两者职责不重叠，评估时也不混同：

| 层次 | 解决的问题 | 具体手段 |
|------|-----------|---------|
| **提示词（P1）** | **语义理解**：什么算一个知识点、两个知识点之间是什么关系、方向如何 | 决策树、边界规则、反例集、类别判定细则、命名规则 |
| **工程代码** | **系统可靠性**：输出能否被解析、结果是否自洽、脏数据能否被拦住 | JSON 三级容错解析、实体归一化与同义词合并、代码符号过滤（`_is_code_symbol`）、悬空端点校验、重复关系去重、低置信度阈值过滤 |

**为什么要分成两层**：提示词擅长处理"模型理解偏差"这类**概率性**问题，能够显著降低出错率，但无法对"必须 100% 拦住"的**确定性**问题给出保证。因此第二类约束一律下沉到代码层实现——例如 v1.4 新增的 `_is_code_symbol` 过滤（见版本 E），它不依赖模型是否遵从提示词，属于**确定性兜底**；即使提示词命令模型"不要抽取程序符号"，代码层仍会再拦一道。

**由此产生的一个必要区分**：**模型的原始输出 ≠ 计入评分的 Pred 结果集**。两者之间的差额被六类"评分前丢弃"逐类记账（见 2.5 节），报告中的对账恒等式保证这个差额可核验。本文档 §2.4 的指标是在 **Prompt + 工程规则这一整条链路之后**的结果上计算的，因此其含义是"**系统最终产出的质量**"，而不是"模型裸输出的质量"——这两者在本文档中不做混同表述。

> 这一分工也是本项目与"单纯堆提示词"路线的区别所在：提示词负责让模型**尽量对**，工程代码负责让系统**确定不出格**。二者缺一不可，且都可独立验证。

### 2.2 当前版本（v1.5，决策树 + 方向自检版）完整原文

User Prompt（`{text}` 为分块后的课程文本）：

```
你是高校课程知识图谱构建专家。请从给定课程文本中抽取「可用于知识图谱与学习路径推荐」的知识点实体，并识别实体之间明确存在的语义关系。

## 核心原则
宁可少抽取，也不要臆造关系。禁止仅凭文本先后顺序、常识或名称相似性推断关系。
若对某条关系证据不足，直接不输出该关系。
每输出一条关系前自问：「换一个领域专家，只看 evidence 原文，会不会认同这条关系的类型与方向？」不确定就删除。

## 一、实体要求
每个实体包含：
- name：知识点名称，简洁、规范、稳定
- category：只能是「概念」「定理」「公式」「方法」之一（无法归类时用「概念」）
- description：一句话描述该知识点在课程中的含义

category 判定（易错区，务必注意）：
- 具体的遍历方式、算法步骤、操作、表示法 → 「方法」。例如：前序遍历、中序遍历、后序遍历、层序遍历、广度优先遍历、深度优先遍历、旋转、插入节点、数组表示，全部属于「方法」，不得标为「概念」。
- 「遍历」「旋转」这类类别性总称 → 「概念」。
- 数据结构、术语定义、性质名词 → 「概念」。例如：二叉树、队列、平衡因子、高度。

实体粒度：
- 一个实体应是一个「独立可学习的知识点」，不要过度拆分，也不要堆砌冗余修饰。
- 同义词、英文缩写与中文全称属于同一知识点时，只保留一个规范名称。例如 CNN 与「卷积神经网络」合并为「卷积神经网络」。
- 名称不要带「算法」「方法」「结构」等冗余后缀，除非该词是固定术语本身（如「二分查找」不要写成「二分查找算法」）。
- 名称不要用裸动词（如「插入」「删除」「查找」），必须带操作对象（如「插入节点」「删除节点」）。
- 不要抽取：人名、学校、公司、页码、章节标题本身、「本节」「上述方法」等指代词、普通名词、单纯例子名。
- 不要抽取代码示例中的函数名、变量名、运算符、类名、关键字等程序符号（如 ==、equals()、BUILD_TREE()、public、private），它们不是课程知识点。
- 不要抽取代码注释/代码清单里出现的操作描述短语（如「初始化二叉树」「构建二叉搜索树」），它们只是某段代码的用途说明，不是独立知识点。
- 注意抽取文中明确出现的「类别性总称」：当文本说「前序、中序、后序遍历统称/属于遍历」时，「遍历」这类上位总称本身也是一个实体，必须单独抽取（它是关系链的上位节点，漏抽会连带漏掉一批关系）。同理「右旋与左旋统称旋转」中的「旋转」。
- 注意抽取定义句中的上位类别词：如「树是一种非线性数据结构」中的「非线性数据结构」、「红黑树是一种平衡二叉搜索树」中的「平衡二叉搜索树」，这类总称同样是关系链的上位节点。
- 文中明确提出的方法论/思想（如「分治」）若作为方法讲解，应抽取为「方法」。

## 二、关系类型（仅限 4 种，英文大写，方向严格）
PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO

## 三、关系判定必须按下述顺序（决策树）
对任意两个知识点，按顺序判断：

1. 「X 是 Y 的一种/子类/特殊形式/变体/属于 Y」或「X 是 Y 的典型操作」？ → CONTAINS（source 是上位概念 Y，方向 source→target，详见第五节）
2. 否则，文本明确表达「学习 source 是理解 target 的必要前提」？ → PRECEDES（方向 source→target）
3. 否则，source 是方法/算法/技术，且文本明确说明其用于实现/解决/完成 target 代表的问题/任务？ → APPLIES_TO（方向 source→target，判定边界见第六节）
4. 否则，文本明确说明二者存在密切关联（工具-主体、并列类似）？ → RELATED_TO（方向约定见第七节）
5. 以上均不满足或证据不足 → 不输出关系

## 四、PRECEDES 只表示「学习依赖」，不表示「文本顺序」
只有文本明确表达以下语义才用 PRECEDES：学习 B 前须掌握 A；A 是理解 B 的基础；B 建立在 A 之上；掌握 A 后才能学 B。
典型触发词：「基础」「先修」「前提」「掌握…之后」「进一步学习」。

反例（以下禁止推断为 PRECEDES）：
- 「本章首先介绍线性表，然后介绍栈」→ 这是叙述顺序，不是学习依赖，不得输出「线性表 PRECEDES 栈」。
- 「卷积神经网络是神经网络的一种」→ 是包含关系，必须用「神经网络 CONTAINS 卷积神经网络」，不得用 PRECEDES。
- 「算法运行后生成结果」→ 时间先后，不是 PRECEDES。
- 「X 是理解 Y 的关键」「通过 X 判断 Y」「X 是 Y 的重要指标」→ 这只是"X 有助于理解 Y"，不等于"必须掌握 X 才能学 Y"，不得输出 X PRECEDES Y。
- 「回顾 X 的定义，下面介绍 Y」「上一节介绍了 X」→ 章节引用/复习指令，不是学习依赖声明。

## 五、CONTAINS 的方向与边界（最高频错误区，务必逐条核对）
### 5.1 方向规则（source 是上位概念，target 是下位概念）
- 「X 是 Y 的一种 / 特殊形式 / 变体 / 属于 Y」「Y 包含 X」「Y 包括 X」「Y 的常见类型有 X」→ **Y CONTAINS X**（上位概念在前，绝不反向）
  例：「栈是一种操作受限的线性表」→ 线性表 CONTAINS 栈
  例：「AVL 树是二叉搜索树的一种」→ 二叉搜索树 CONTAINS AVL 树
  例：「前序遍历是深度优先遍历的一种」→ 深度优先遍历 CONTAINS 前序遍历
  例：「完美二叉树也是一棵完全二叉树」→ 完全二叉树 CONTAINS 完美二叉树
- 「X 是 Y 的操作」（句式如「Y 的 X 操作」「Y 支持 X 操作」）→ **Y CONTAINS X**
  仅当 X 是直接对 Y 执行的基本操作（插入、删除、查找、遍历等，句式以 Y 为操作对象）。
  例：「二叉搜索树支持插入节点、查找节点、删除节点操作」→ 二叉搜索树 CONTAINS 插入节点、二叉搜索树 CONTAINS 查找节点、二叉搜索树 CONTAINS 删除节点
  反例：「AVL 树通过旋转保持平衡」——旋转是维护平衡的手段、不是对 AVL 树执行的增删查操作，不得输出 AVL 树 CONTAINS 旋转。

### 5.1 附：历史上反复出错的输出（逐条核对，严禁出现）
- 严禁输出「AVL 树 CONTAINS 二叉搜索树」——正确为 二叉搜索树 CONTAINS AVL 树
- 严禁输出「AVL 树 CONTAINS 平衡二叉树」——正确为 平衡二叉树 CONTAINS AVL 树
- 严禁输出「完美二叉树 CONTAINS 完全二叉树」——正确为 完全二叉树 CONTAINS 完美二叉树

### 5.2 输出前方向自检（每条 CONTAINS 必做）
把关系读成「target 是 source 的一种/子类/典型操作」，若语义不通，而读成「source 是 target 的一种」才通，
说明方向写反了，必须翻转 source 与 target。翻转后仍不确定就删除该关系。

### 5.3 不是 CONTAINS 的情况（严禁）
- 整体-部分结构（「二叉树由根节点、叶节点组成」「链表由节点构成」）：部分只是结构的组成单元、而非"X 是 Y 的一种"类型关系时，不得输出 CONTAINS。只有当"X 是 Y 的一种/子类"（如「完全二叉树是二叉树的一种」）才成立。
  点名禁止（这些是"组成/属性"而非"类型包含"，一律不建立任何关系）：
  - 二叉树 与 节点/根节点/叶节点/左子节点/右子节点/边/层/度/高度/深度 之间
  - 节点 与 左子节点/右子节点 之间
  - 操作关系中的主体必须是正文明确的对应结构（如「二叉搜索树的插入操作」→ 二叉搜索树 CONTAINS 插入节点），不得把操作挂到泛化主体上（「二叉树 CONTAINS 插入节点」不成立）
- 「X 具有属性/特征/指标 Y」（如「二叉树具有高度」「AVL 树用平衡因子衡量平衡」）：Y 是 X 的属性而非 X 的一种，不得输出 X CONTAINS Y。
- 「X 通过 Y 机制维持性质」（如「AVL 树通过旋转保持平衡」）：Y 是维护机制而非 X 的类型，不得输出 X CONTAINS Y（但「右旋、左旋是旋转的两种基本操作」→ 旋转 CONTAINS 右旋 成立）。
- 「X 使用公式/函数 Y 进行表示或计算」（如「数组表示使用映射公式」）：Y 是 X 的计算工具，不得输出 X CONTAINS Y。
- 「要学习 X，必须先掌握 Y」→ Y PRECEDES X，不是 CONTAINS
  例：「要学习多态，必须先掌握继承」→ 继承 PRECEDES 多态

## 六、APPLIES_TO 的判定（含「实现机制」的正确映射）
只有当 source 是方法/算法/技术类知识点、且文本明确说明其被用于实现、解决、完成 target 代表的问题/任务时，才能使用 APPLIES_TO（方向 source→target）。

「X 基于 Y 实现」「X 通过 Y 实现」「X 借助 Y 实现」「X 用 Y 实现」句式：
- Y 是方法/算法/技术 → **Y APPLIES_TO X**
  例：「深度优先遍历通常基于递归实现」→ 递归 APPLIES_TO 深度优先遍历（严禁输出反向）
  例：「前序遍历基于递归实现」→ 递归 APPLIES_TO 前序遍历
- Y 是数据结构等非方法类概念 → 降级为 RELATED_TO（见第七节）；证据不足则不输出
  例：「广度优先遍历借助队列实现」→ 队列 RELATED_TO 广度优先遍历，**严禁 APPLIES_TO**

「X 可用于实现 Y」（X 是技术/结构，Y 是应用对象）→ X APPLIES_TO Y
  例：「二叉搜索树可用于实现多级索引」→ 二叉搜索树 APPLIES_TO 多级索引

方法论思想贯穿某对象的设计（如「二叉树体现分治思想」「分治思想应用于二叉树」）→ 方法 APPLIES_TO 对象
  例：「二叉树体现一分为二的分治逻辑」→ 分治 APPLIES_TO 二叉树

严禁的输出：
- 「X 用于表示 Y」「X 是 Y 的存储方式/表示法」（如「数组表示用于存储完全二叉树」）：表示法与被表示对象的关系不是 APPLIES_TO，若证据不足则不输出。

严禁的输出（违反方向）：
- 深度优先遍历 APPLIES_TO 递归、广度优先遍历 APPLIES_TO 队列、中序遍历 APPLIES_TO 深度优先遍历（这些方向全部颠倒；「X 是 Y 的一种」走 CONTAINS，不是 APPLIES_TO）

不要为了覆盖所有语义而强行映射到现有四类关系；证据不足时宁可不输出。

## 七、RELATED_TO 的方向约定（从严输出）
仅用于「明确密切相关、但既非上下位、也非学习前置、也非应用」的情况，且文本有明确关联表述。
方向约定：
- 工具/支撑方为 source，主体/被支撑方为 target：
  例：「广度优先遍历借助队列实现」→ 队列 RELATED_TO 广度优先遍历
  例：「二叉树可用链表表示」→ 链表 RELATED_TO 二叉树
- 并列类似关系（「与…类似」「工作原理一致」「互为镜像」「互为对称」）时，source 取正文中先出现的一方：
  例：「红黑树与 AVL 树类似」→ AVL 树 RELATED_TO 红黑树
  例：「右旋与左旋互为镜像对称」→ 右旋 RELATED_TO 左旋
- 主体与其思想来源（「X 的查找思想源于二分查找」）→ X RELATED_TO 思想来源
  例：「二叉搜索树的查找思路与二分查找一致」→ 二叉搜索树 RELATED_TO 二分查找
- 方向无法确定时宁可不输出。

严禁的输出：
- 仅因两个概念出现在同一段就输出 RELATED_TO。
- 「X 与 X 序列」这类名称派生关系（如 中序遍历 与 中序遍历序列）不构成 RELATED_TO 证据。
- 「X 的时间复杂度」「X 的性能」等属性关联不得输出。
- 两个知识点仅通过第三方间接联系（如完美二叉树与广度优先遍历仅都关联层序遍历）→ 不输出直接关系。
- 「X 与其维护机制/属性/表示工具」（如 AVL 树与旋转、完美二叉树与高度、数组表示与映射公式）不建 RELATED_TO。
- 仅共享词根不构成关联证据（如「二分查找」与「查找节点」都含"查找"二字，不代表二者存在 RELATED_TO 关系）。

## 八、每条关系必须携带证据与置信度
- evidence：支持该关系的原文短句（必须来自输入文本，不得编造）
- confidence：0~1 的置信度，如实反映证据强弱，不确定就降低

## 九、输出约束
- source 与 target 必须都出现在 entities 中，且 source ≠ target
- 不重复输出相同 (source, type, target)；文本中因分块出现的重复段落，同一知识点/关系只输出一次
- type 只能是 PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO
- 关系密度控制：参考密度为每 1000 字符正文 2~4 条关系。若本次输出明显超出该密度，说明混入了证据不足的关系，请删减到最明确、最有价值的子集。
- 输出前对每条关系自检：
  ① CONTAINS：target 是 source 的一种/子类/典型操作？（读反则翻转 source 与 target）
  ② PRECEDES：文本有明确的「学习 target 前必须掌握 source」表述？
  ③ APPLIES_TO：source 是方法/技术，target 是它实现/解决的问题或任务？
  ④ RELATED_TO：source 是工具/支撑方或正文先出现方？
- 严格只输出 JSON，不要 Markdown 代码块，不要解释文字

## 十、输出格式
{
  "entities": [
    {"name": "实体名", "category": "概念", "description": "一句话描述"}
  ],
  "relations": [
    {"source": "源实体名", "target": "目标实体名", "type": "PRECEDES", "evidence": "原文证据", "confidence": 0.95}
  ]
}

## 课程文本
{text}

请只输出 JSON，不要包含任何其他内容。
```

### 2.3 版本迭代完整记录

抽取提示词共经历 **6 个版本**，版本号冻结于 `backend/eval_config.py`（当前 `PROMPT_VERSION = "v1.5"`），每次变更均可追溯至对应 git 提交与 `experiment_config_*.json` 实验快照。

#### 版本 A（v1.0，初版 · commit 6755b9f，858 字符）

四类关系 + 实体字段（`name` / `category` / `description`）+ 基础输出约束（禁自环、禁重复、source 与 target 必须在实体列表中），`temperature=0.1`。**无 Few-shot 示例、无 `evidence` / `confidence` 字段**。

这一版已定下"4 种关系类型 + 严格 JSON 输出"的骨架，此后 5 个版本均未改动该骨架——后续所有改动都发生在**边界判定**与**约束强度**上。

#### 版本 B（v1.1，Few-shot 版 · commit f4e8d9b、b262538，1818 → 1824 字符）

首轮真实文档测试暴露的问题：模型对"什么才算前置关系"缺乏语感，PRECEDES 产出过少。本版由该结果驱动（见 2.4 节量化闭环），核心改动三点：

1. **新增「PRECEDES 示例」整节（示例 1 ~ 示例 4）**，用具体文本锚定判定，取代此前纯规则的抽象描述：

   ```
   示例1：
     文本："要学习面向对象编程，必须先理解类和对象的概念。"
     输出：{"source": "类和对象", "target": "面向对象编程", "type": "PRECEDES"}

   示例4（关键区分）：
     文本："卷积神经网络是神经网络的一种，常用于图像识别任务。"
     输出：
       {"source": "神经网络", "target": "卷积神经网络", "type": "CONTAINS"},
       {"source": "卷积神经网络", "target": "图像识别", "type": "APPLIES_TO"}
     （注意：这里"神经网络→卷积神经网络"是包含关系，没有先后顺序，所以用 CONTAINS 而非 PRECEDES）
   ```

   示例 4 是这一版的核心：它首次把 **CONTAINS 与 PRECEDES 的边界**用正反例的方式摆到模型面前，而不只是陈述规则。

2. **强化 PRECEDES 产出**，新增两条硬性条款：
   - "识别到任何'先学后学'的先后顺序关系时，**必须**使用 PRECEDES，不得降级为 RELATED_TO！"
   - "同一段文本中，PRECEDES 占比不应为 0。如果存在任何先后顺序表述，必须产出 PRECEDES。"

   > 这两条在下一版被**删除**——它们解决了"PRECEDES 太少"，却制造了"没有前置关系时硬造 PRECEDES"。这是本项目最有价值的一次自我修正，详见版本 C。

3. **temperature 0.1 → 0.3**：给模型更大的判断空间以识别前置关系，同时保持在稳定区间内。

#### 版本 C（v1.2 · 决策树版 · commit f62bd23、d9516c2）

在 v1.1 基础上的结构性重构，改动五点：

1. **引入"关系判定决策树"**（见 2.2 原文第三节）：强制模型按 CONTAINS → PRECEDES → APPLIES_TO → RELATED_TO → 不输出的**固定顺序**依次判断，从"平行规则挑一条"变为"互斥的有序判定流程"，彻底消除规则间冲突。这是本版本最关键的改动，直接导致下一段的删除。
2. **删除 v1.1 的两条 PRECEDES 强化条款**（即版本 B 中的第 2 点）：
   - "必须使用 PRECEDES，不得降级为 RELATED_TO"——它把 PRECEDES 提升为"优先级最高"的规则，与决策树"自上而下互斥判定"的机制直接冲突；
   - "PRECEDES 占比不应为 0"——这条**把关系产出量当成了目标**，会诱导模型在没有真正前置关系时硬造 PRECEDES 边，与"宁缺毋滥"原则根本对立。

   删除理由：v1.1 用这两条治好了"PRECEDES 太少"，代价是 Precision 崩塌。**产出量不是目标，准确率才是**——这正是 2.4 节 4 类错误归因中"臆造"一项的直接来源。

3. **删除 v1.1 的编号 Few-shot 示例**：改用决策树 + 分节反例（第五、六节）替代具体示例。原因是示例只覆盖了"神经网络 / 卷积神经网络"一种语义形态，模型容易照搬句式而非理解规则；分节反例则按**错误类型**组织（方向颠倒 / 组成关系 / 属性关系 / 实现机制），覆盖更全。
4. **新增第六节**"APPLIES_TO 与实现 / 构成关系的区分"（此后在 v1.3 重写，见版本 D）：修复复测中发现的新混淆模式——"X 由 Y 实现 / X 使用 Y 构成"被误判为 APPLIES_TO，明确此类表达不强行映射到现有四类关系。
5. **新增证据与置信度强制要求**（第七节）：每条关系必须携带 `evidence` 原文证据与 `confidence`，实现抽取结果可溯源；同时新增实体同义词合并规则。

此外，`temperature` 在本版由 0.3 调回 **0.15**——关系类型判别需要稳定输出，0.15 是在"稳定性"与"判断力"之间取的折中（`f62bd23` 的代码注释原文："关系类型判别需稳定；0.15 在稳定与判断力之间取平衡"）。
#### 版本 D（v1.3，真实章节规模第一次定向修复 · commit cb2a045）

由第7章·树（15330 字符 / 49 实体 / 33 关系）真实规模评测驱动，关系主指标 F1 仅 0.1614。错误归因显示四类缺陷：CONTAINS 方向系统性颠倒（「X 是 Y 的一种」输出成 X CONTAINS Y）、臆造（属性/机制关系滥用 CONTAINS，如「AVL 树 CONTAINS 高度」）、APPLIES_TO 与 gold 决策树冲突（Prompt 禁止「基于…实现」映射 APPLIES_TO，但 gold 标注「递归 APPLIES_TO 深度优先遍历」）、RELATED_TO 方向随机。核心改动：

### 2.5 评测口径与「丢弃记账」机制

提示词迭代之所以能被量化，前提是评分口径稳定、且**每一个数字都能对账**。本节记录 v1.3 迭代中同步建立的三项机制——它们是「0.1614 → 0.8312」这条曲线可信的基础，也是本文档与《知识抽取准确率测试报告》共用同一套口径的依据。

#### （1）三种关系指标口径：Core / Full / Primary

同一份 Gold 中，每条关系可携带 `core` 布尔标记：

- **Core 集**（`core=true`）——文本明确、按决策树必然成立、无争议的关系；
- **Full 集**——Core ∪ 合理但边界模糊、需人工裁量的关系。

评测器据此**同时输出三套口径**，互不替代（实现见 `backend/eval_accuracy.py`）：

| 报告字段 | Precision 分母 | Recall 分母 | 性质 |
|---------|:---:|:---:|------|
| `relation_full` | Full | Full | **标准 F1**——P、R 取自同一 Gold 集，可与任何外部结果直接比较 |
| `relation_core` | Core | Core | **保守下界**——只在无争议关系上评分，要求最严，须与主指标一并披露 |
| `relation_primary` | Full | Core | **本项目主口径**——P、R 分母有意不对称（`eval_accuracy.py:429`） |

**`relation_primary` 的分母为什么不对称**——两类错误的实际代价不同：把一条"模型确实抽对、只是标注边界模糊"的边判为错误，会低估 Precision；把一条"无争议、该抽却没抽"的边放过，会高估 Recall。该口径**仅为本项目的补充观察指标，不用于替代标准 F1**；因此本项目在披露主指标的同时，始终一并给出 `relation_core` 与 `relation_full` 两套完整 P/R/F1。

**关于本次申报数值，需要向评审明确的一点**（避免口径误读）：

> **开发集第 7 章·树的 Core = Full = 33 条**——gold 中全部 33 条关系的 `core` 均为 `true`，没有任何 `core=false` 项。因此在本开发集上**三套口径数值完全相同**：`relation_primary` = `relation_core` = `relation_full` = **0.8312（P=0.7841，R=0.8889）**（三套数值可在 `eval_report_第7章_树_v15.json` 中逐一核对）。
>
> 也就是说，**本次申报的 0.8312 就是标准意义上的 F1**，非对称口径在本开发集上未产生任何偏离，不存在"用非标准 F1 抬高分数"的情况。
>
> 双层 Gold 机制是为**边界存在裁量空间的数据集**准备的：当标注员对某条关系是否可接受存在合理分歧时，可标为 `core=false` 归入 Full，使"模型抽对了、但标注本身有争议"的边不至于被全额扣分。该机制真正生效的实例是第 1 章·语句（Core 40 / Full 45，Core 占 89%），它验证了机制可用；该章的数值不属于本次申报范围。

#### （2）评分前的六类丢弃与对账恒等式

关系从模型输出到进入评分须过 6 道过滤，每道丢弃的原因单独计数、单独披露：

| 代号 | 含义 |
|---|---|
| `invalid_relation_type` | 关系类型不在四类白名单内 |
| `invalid_endpoint` | source 或 target 为空 |
| `synonym_split` | 归一化后 source == target（模型把同一实体拆成两种写法） |
| `dangling_endpoint` | 端点不在 `entities` 列表中（悬空边） |
| `duplicate` | 重复三元组（多因分块重叠） |
| `low_confidence` | 模型自评置信度低于该类阈值 |

**为什么必须逐类记账**：其中 `low_confidence` 最容易造成误诊——这类关系**模型其实抽到了**，是本系统的阈值把它砍掉的。若不单独披露，它会被错误归因里的「⑤ 完全漏抽（Core）」一并吃掉，于是"**阈值设太严**"被系统性误诊为"**模型召回能力不足**"，后续优化方向会完全跑偏。

同理，报告中的 `raw_source` 字段标明该轮计数来自抽取器直接上报（`extractor`，精确值）还是评测器反推（`derived`，仅用于补齐），并要求每轮满足对账恒等式：

```
pred_raw_total == pred_total + dropped_total
```

报告中逐轮显示「✓」；一旦对不上，即说明抽取侧与评测侧的计数口径已经漂移，该轮结果不可采信。

#### （3）可复现指纹

报告头部固定记录三项指纹，保证"某个分数由哪份数据、哪套归一化规则算出"可追溯：

| 项 | 第 7 章 v1.5 实验取值 |
|---|---|
| 归一化版本 | `NORMALIZATION_VERSION = "n1"` |
| 别名表 SHA256 | `960bb3117d7fe9ef…` |
| Gold SHA256 | `50f316ce7bea6690…` |

三者任一变化，历史分数即不可直接比较。因此**修改别名表必须递增 `NORMALIZATION_VERSION` 并全量重算**（该纪律以注释形式写在 `eval_accuracy.py:172`，与代码同处一地，避免遗忘）。

#### （4）`confidence` 的定位：辅助字段，不是准确率

`confidence` 是提示词要求模型输出的**自评置信度**（P1 第八节），本项目中它只承担三件事：

1. **工程侧过滤**——低于阈值的关系在入库/评分前丢弃，并单列为 `low_confidence`（见上文第（2）点）；
2. **人工复核排序**——教师审核抽取结果时，低置信度条目优先呈现；
3. **结果分析**——用于观察模型"自认为不确定"的部分是否与错误高发区重合。

**明确不作为**：模型准确率、概率校准度（calibration）或评测分数的任何替代指标。模型自报 0.95 **不代表**该条 95% 正确——该字段未经任何概率校准，与真实正确率之间没有可用的对应关系。

> **真实准确率只由 Gold 标注 + `backend/eval_accuracy.py` 的 P/R/F1 计算得出。** 同一口径亦记于 `docs/V1.1_冻结说明.md`，两份文档表述一致。

### 2.7 已知边界与待验证项（如实披露）

本节列出当前提示词与评测中**已知的局限**，供评审判断本结果的适用范围。以下各条**均未在 v1.5 上改动**（提示词正文已冻结，见第九节第 7 条），因此列入"已知边界"而非"已解决"：

1. **"关系密度 2~4 条/1000 字符"是软性自检，不是产出目标。** P1 第九节含一句"参考密度为每 1000 字符正文 2~4 条关系……若明显超出该密度……请删减"。它的原意是**抑制输出膨胀**（早期版本臆造偏多时，靠它压掉一批证据不足的边），但不同课程、不同章节的合理关系密度差异很大（公式密集章节与概述性章节不可直接类比），因此该条款对**高密度章节理论上可能偏保守**。相应地，它的正确定位是**异常产出的自检提示**，而非产品质量 KPI——本项目的一贯立场是"产出量不是目标，准确率才是"（见 2.3 节版本 C）。
   - 就开发集而言：第 7 章·树 v1.5 三轮的**原始输出**条数为 36 / 41 / 47（见 `评测报告_第7章_树_v15.md` §5.3 对账表），折合 15330 字符下约 **2.3 / 2.7 / 3.1 条每千字符**，均落在参考带内；Gold 本身为 33 条（约 2.15 条每千字符）。即该条款在本开发集上**未出现需要触发的偏离**。需说明的是，模型对提示词的遵从是隐性的，无法从最终输出中分离出"该条款是否曾让模型主动少输出"，上述密度仅能说明结果本身处于合理区间。
   - 是否把该条款改写为更宽松的表述，属于**需要重新跑基线的提示词变更**，未纳入 v1.5。
2. **双层 Gold 在开发集上未激活。** 第 7 章·树 Core = Full = 33（见 2.5 节），"边界模糊关系"的裁量能力尚未在申报数据集上被真正检验；封存集标注时将实际使用该机制。
3. **开发集为单一章节。** §2.4 的全部指标来自第 7 章·树（数据结构课程的树结构部分）。跨课程（化学、物理、数据结构其他章节）与跨文档格式的泛化能力，以**封存集**验证，按计划**只跑一次**、结果直接进交付报告——这是为了避免"反复跑封存集调提示词"而使其失去独立验证的意义（见 2.4 节"封存集计划"）。
4. **关系召回存在结构性上限（评测口径固有性质，非模型缺陷）。** 评分按三元组（节点对 + 类型 + 方向）匹配，**若某条 Gold 关系的任一端点未被抽为实体，该关系在本口径下不可能被记为命中**。因此关系 Recall 天然受制于实体抽取对关系端点的覆盖程度，两者会同时下降。披露此点的意义在于避免误读**单类型** P/R/F1：某一关系类型的 F1 偏低时，其原因既可能是"该类关系的判定规则失效"，也可能仅仅是**该类关系所依赖的端点实体没被抽出来**（后者与关系判定无关）。诊断时应**先回看实体层，再判断关系层**。需要注意的是，本口径下"关系召回"与"实体召回"不会独立变动，因此不宜把关系 Recall 与实体 Recall 当作两项独立能力来对比。

## 三、P2 前置关系补全提示词

### 3.1 用途与设计动机

文档文本中"必须先学 A 才能学 B"的显式表述往往是稀疏的，仅靠抽取会让 PRECEDES 边过少，学习路径推荐覆盖不足。本提示词在图谱构建完成后，将全部知识点清单（名称 + 类别 + 描述）一次性交给大模型，**基于教学逻辑常识**补全缺失的前置关系。

**接入状态（如实标注）**：本模块的提示词、调用封装、结果校验与写库逻辑均已完整实现，并提供 `__main__` 命令行入口（含 `--rollback` 子命令，可删除指定文档下全部 `is_inferred=True` 的 PRECEDES 边）。但**当前版本未挂载 API 路由、前端无对应界面**，因此无法通过产品操作触发；`app/core/metrics.py` 亦已将其列入 `UNTRACKED_LLM_SCOPES`（"未接入统计"）。保留于此作为关系补全能力的已实现储备，接入界面即可启用。

**可靠性设计**：补全的边带 `is_inferred=True` 标记，与抽取所得边区分存储，可被单独检索与回滚，不污染人工确认的知识。这一设计针对的是"补全边由模型凭常识推断、可信度低于原文抽取"的事实——**先承认模型会犯错，再给它留出可撤销的余地**，而不是指望它不出错。

**与 P1 的证据标准差异（有意为之，不是自相矛盾）**：P1 的核心原则是"**禁止仅凭文本先后顺序、常识或名称相似性推断关系**"，而 P2 恰恰要求**基于教学逻辑常识**补全 P1 无法从文本中抽到的前置关系。二者标准不同，但**并不冲突**，因为它们是两个目标不同、且数据层相互隔离的任务：

| | P1 知识抽取 | P2 前置关系补全 |
|---|---|---|
| 任务定位 | **抽取**——把文本里已经写明的知识结构化 | **补全**——在已有知识点之上推断文本未写明的教学顺序 |
| 证据标准 | 仅接受**文本显式证据**（每条关系必须带 `evidence` 原文） | 允许**教学逻辑推断**（无原文证据，故不要求 `evidence`） |
| 信任级别 | 视为**可信的知识本体** | 视为**推断结果**，不计入"原文证据型"关系 |
| 数据隔离 | 正常入库 | 标 `is_inferred=True`，可单独检索、可 `--rollback` 回滚 |
| 当前状态 | **主链路**（上传文档即触发） | 已实现，**未接入**产品调用链 |

也就是说：**P1 的"不许推断"约束的是"把推断结果伪装成文本证据"这一行为**，而 P2 从不声称这些边来自文本——它显式标记自己为推断，并在图谱中与原文抽取边分区存放。因此 P2 的推断关系**不会进入 P1 的证据型统计**，也不会被计入本文档 §2.4 的抽取指标。这一区分是本项目"证据可溯源"原则能够成立的前提。

**System Prompt**：

```
你是一名严谨的知识图谱构建助手，只输出 JSON。
```

### 3.2 完整原文

User Prompt（`{node_list}` 为每行一个"名称（类别）：描述"的知识点清单）：

```
你是一名教育领域知识图谱专家。下面是一个课程的知识点清单（名称 + 类别 + 一句话描述）：

{node_list}

请根据教学逻辑，补全这些知识点之间**缺失的「前置知识（PRECEDES）」关系**。

## 严格规则
- PRECEDES 方向为 source → target，表示「必须先掌握 source，才能学习 target」。
- **只有当两个知识点之间存在明确的先后学习依赖时，才输出 PRECEDES。**
- 以下情况**严禁**输出（这些不是前置关系）：
  - "X 是 Y 的一种 / 特殊形式 / 变体 / 组成部分"（这是包含关系 CONTAINS）
  - 两个知识点只是相关、并列、同层（这是相关关系 RELATED_TO，无先后顺序）
  - "X 用于 / 应用于 Y"（这是应用关系 APPLIES_TO）
  - 你不确定、或先后依赖不明显的
- 宁缺毋滥：只输出你**高度确信**的 PRECEDES 关系。
- source 与 target 必须是清单中**已有的知识点名称**，且不能相同。

## 输出格式（严格 JSON，只输出 JSON，不要输出任何解释）
{{
  "relations": [
    {{"source": "继承", "target": "多态"}}
  ]
}}

如果没有需要补充的关系，输出 {{"relations": []}}。
```

**设计要点**：负面清单中显式列出"包含 / 相关 / 应用"三类易混淆情形并指向正确的关系类型，与 P1 的决策树思想一致；示例取自教学场景中无争议的"继承 → 多态"，降低误补全率。

## 四、P3 智能问答提示词（RAG）

### 4.1 用途与检索链路

学生提问 → 问题 embedding（BAAI/bge-m3）→ 与知识点向量做余弦相似度 → 取 top-5 知识点作为上下文 → 填入 System Prompt → 大模型生成回答。向量检索失败时自动退回关键词检索。该设计对应赛题"利用 RAG 技术，让大模型在回答问题时优先参考课程知识图谱中的权威内容，避免幻觉"的要求。

### 4.2 完整原文

System Prompt（`{context}` 为检索到的知识点格式化内容；无相关知识时填"暂无相关课程知识"）：

```
你是一个课程学习助手。请基于提供的课程知识图谱内容回答学生的问题。

## 规则
1. 优先使用提供的知识内容回答问题
2. 如果知识库中没有相关信息，请诚实告知，不要编造
3. 回答要准确、简洁、易于理解
4. 如果合适，可以推荐相关的知识点供进一步学习

## 课程知识内容
{context}

请根据以上内容回答学生的问题。
```

User Prompt：学生原始问题原文，不做模板包装。

**设计要点**：
- 规则 1 + 规则 2 构成"优先引用 + 拒答诚实"双保险，直接针对 LLM 幻觉问题；拒绝编造是赛题明确关注点。

### 4.3 测试验证

## 六、P8 试题文档结构化抽取提示词

### 6.1 用途与接入状态

把教师上传的试题文档（章末习题、试卷）解析为结构化题目（题干 / 题型 / 选项 / 答案 / 解析），是"试题导入"功能的数据入口。

**接入状态**：提示词、分块调用、三级容错 JSON 解析与合并逻辑均已完整实现，并有量化评测脚本 `backend/eval_question_import.py`（`temperature=0`）。**但当前产品内的试题导入走确定性规则解析**（切"题目区 / 答案区"→ 按题号切块 → 答案映射 → 题型判定，见 `app/api/questions.py:172` 的 `import/preview`），未调用该 LLM 提示词——中文教材习题题号规整，规则解析足够稳定且无 API 成本与延迟。该提示词作为"题号不规范、规则解析失效"场景下的 LLM 兜底储备。

### 6.2 完整原文

User Prompt（`{text}` 为分块后的试题文本；分块 6000 tokens、overlap=0）：

```
你是试题结构化专家。请从给定课程文本中抽取试题，并输出严格 JSON。

## 规则
1. 只抽取文本中**真实存在**的试题；不要臆造题目；看不清或不确定的题直接跳过。
2. 答案必须来自文本（题目后紧跟的“答案/解答”，或文末答案区）。
   - 文本中没有给出答案时：answer 填空字符串 ""，**绝对不要自己解题**。
   - 选择题答案写选项字母（如 "B"）；多选写数组（如 ["A","C"]）。
3. q_type 只能取：SINGLE（单选）/ MULTI（多选）/ JUDGE（判断，answer 为 "true" 或 "false"）/
   FILL（填空）/ ESSAY（解答）。
4. 选项写成 [{"key":"A","text":"..."}]；没有选项时用 []。
5. 只输出 JSON，不要 Markdown 代码块，不要任何解释文字。

## 输出格式
{"questions":[{"number":1,"q_type":"SINGLE","stem":"题干","options":[{"key":"A","text":"选项"}],"answer":"B","analysis":""}]}

## 课程文本
{text}
```

### 6.3 设计要点

1. **只抽真实存在的题**（规则 1）："不要臆造题目；看不清或不确定的题直接跳过"——与 P1 的"宁缺毋滥"同源。题库一旦混入臆造题，教师需逐题核对，导入效率反而不如手工录入。
2. **禁止自行解题**（规则 2）：文本未给答案时 `answer` 填空串，并以"**绝对不要自己解题**"加重约束。这是本提示词与通用"解题助手"的关键分野——系统要的是**结构化**，不是**代做**。一旦让模型自行解题，答案便不再可溯源，后续批改环节的权威性会被破坏。
3. **题型枚举封闭**（规则 3）：`SINGLE / MULTI / JUDGE / FILL / ESSAY` 五类封闭取值，直接对应题库表 `q_type` 字段，无需二次映射。
4. **无选项时输出 `[]` 而非省略字段**（规则 4）：保证下游解析路径唯一，避免"字段缺失"与"空值"两种状态并存。
5. **三级容错解析**：`_parse_json`（`question_extractor.py:41`）沿用 P1 的做法——直接解析 → 剥离 Markdown 代码块 → 正则截取 JSON，单块解析失败不致整篇丢弃。

## 八、调用参数汇总

| 提示词 | temperature | max_tokens | 选择依据 |
|--------|:-----------:|:----------:|---------|
| P1 知识抽取 | 0.15（评测时 0） | **8192** | 分类判断需稳定；评测设 0 以降低采样随机性、提高实验可重复性 |
| P2 关系补全 | 0.15 | 4096 | 同 P1，误补会污染图谱 |
| P3 智能问答 | 0.3 | 1024 | 需语言流畅度，但偏低保事实性 |
| P4 Commit 分析 | 0.1 | 2048 | 结构化枚举输出，要求高一致性 |
| P5 回滚评估 | 0.1 | 2048 | 同 P4，且直接关系操作安全 |
| P6 教材翻译 | 0.1 | 8192 | 翻译忠实性优先 |
| P7 答案补全 | 0.1 | 8192 | 计算与事实准确优先 |
| P8 试题抽取 | 0（默认） | 4096 | 只做结构化、不解题，最高一致性优先 |

其他工程参数：抽取分块 6000 tokens、块间重叠 400 tokens（防止知识点被切断导致关系丢失）、并发 4 路（受 API 限流约束）。

**关于"评测温度设为 0"的确切含义**：温度 0 的作用是**降低采样随机性、提高实验的可重复程度**，**而不是**"保证结果严格可复现"——即使 `temperature=0`，大模型的输出仍不完全确定。因此本项目**不依赖"重跑得到相同结果"**，而是采用**预测落盘**的纪律：每次正式评测把模型输出一次性写入 `pred_*.json`，此后所有评分、调参、出图都基于同一份预测文件（见 2.6 节）。这样"提示词改动带来的分数变化"与"模型自身的随机波动"才不会混在一起。相应地，本文档中"评测温度 0"统一理解为"降低随机性"，不写作确定性保证。

**关于 P1 的 `max_tokens`**：该值由 `_MAX_OUTPUT_TOKENS` 常量控制（`knowledge_extractor.py:192`），取值 **8192**——即 `deepseek-chat` 的单次输出上限。此前曾设为 4096，实测在知识点密集的块（如章末习题、公式密集章节）会导致 JSON 数组**中途被截断**（`finish_reason=length`），进而使**整个分块的抽取结果解析失败、该块知识点全部丢失**。这类损失在报告里表现为"完全漏抽"，极易被误诊为模型召回能力不足，因此上调至上限并记录在案。

**关于 P3 的 `temperature=0.3`**：这是全项目唯一高于 0.15 的取值。问答属于开放生成任务，过低温度会使回答生硬；但更高温度又会牺牲"不编造"的约束强度，0.3 是折中。

## 九、方法论总结

1. **数据驱动的迭代闭环**：提示词迭代不是凭感觉改，而是"人工标注金标准 → P/R/F1 量化 → 定位系统性错误 → 修改规则/Few-shot/温度 → 复测验证"。**在玩具规模**（708 字节 / 4 条关系）上，v1.0 → v1.1 的修复使关系 F1 由 0.4667 升至 0.9333，单次闭环成本极低；但正如 2.4 节所示，**玩具规模的达标不能外推到真实章节**——真正的价值在于这套闭环本身可复用，v1.3~v1.5 在真实章节上的修复走的正是同一条路径。
2. **决策树优于平行规则**：v1.2 将"四条平行规则"重构为"互斥有序决策树"后，模型不再需要在规则间自由选择，类型混淆问题从机制上收敛。
3. **反例约束在易混淆边界上具有明确的工程价值**：在易混淆边界（"X 是 Y 的一种"≠ 前置关系）显式给出"错误输出"标注的反例，是本项目 v1.3 → v1.5 压制残留臆造的主要手段之一（"'臆造'由 31 条降至 5 条"，见 2.4 节）。需要如实说明的是，本项目**未设置"同一版本 + 正例"与"同一版本 + 反例"的对照组**，因此上述结论的适用范围仅限本项目自身的迭代观察，不宜表述为普适规律（"反例一定优于正例"）。
4. **证据强制 + 可回滚设计**：关系必须携带原文 evidence；推断边带 `is_inferred` 标记可回滚——从工程上兜底"LLM 一定会犯错"的前提，保证图谱质量上限不受模型错误影响。
5. **归一化口径必须先冻结**：同一知识点在 Gold 与模型输出中的写法差异（大小写、括号、术语后缀、同义词），若不在归一化层统一，会**同时**制造假性漏抽与假性臆造——一个实体在两边各算一份，把分数量化出来的"模型能力不足"里掺进大量口径噪声。归一化规则与别名表因此与提示词正文同等冻结，并以 `NORMALIZATION_VERSION` + 别名表 SHA256 指纹固化在每份报告中（见 2.5 节）。**先统一口径，再谈模型优化**——顺序反了，优化方向必然是错的。
6. **记账先于结论**：任何"少了 N 条"的说法都必须能拆解为"哪一类、为什么"。评测器为评分前的每一道过滤单独计数（见 2.5 节六类丢弃），并强制满足 `原始输出 = 进入评分 + 丢弃` 的对账恒等式。这一条的直接收益是：把"阈值设太严"与"模型没抽到"这两类**优化动作完全相反**的病因区分开来。
7. **冻结纪律**：进入正式评测（Gold 标注）后提示词正文冻结不可修改（见 `docs/V1.1_冻结说明.md`），保证测试报告与提交版本严格对应。v1.3 → v1.5 的三次定向修复均**先在开发集第 7 章·树上跑基线、拿到错误归因证据后才改**，每次版本跃迁都留下 `eval_report_第7章_树_v1*.json` 与 `experiment_config_v1*.json` 两份存档（见 2.3.1 溯源表）。冻结不是"不许改"，而是"**没有证据不许改**"——禁止的是"跑一次 → 感觉某类少了 → 改提示词 → 再跑"这种破坏测试集独立性的循环。
