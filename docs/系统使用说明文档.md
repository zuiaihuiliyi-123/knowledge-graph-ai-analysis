# 第一章 系统概述

## 1.1 系统简介与建设目标

在高校教学过程中，课程内容往往以教材、课件、教案等**非结构化文档**形式存在，知识点分散、缺乏清晰的关联关系。传统课程知识图谱的构建高度依赖教师或专家手工整理，工作量大、周期长，难以推广。

本系统利用 AIGC 技术自动完成 **文档解析 → 知识点抽取 → 关系构建 → 图谱生成**，把知识图谱的构建门槛从「专家标注」降低到「上传一份文档」，并在此基础上提供个性化学习路径推荐与基于 RAG 的智能问答。

**建设目标**：

1. 让教师无需具备图谱建模知识，也能为学生提供结构化的课程知识资源；
2. 让学生从「线性阅读教材」转向「按知识关联学习」；
3. 让学习路径从「教师统一安排」转向「依据个人掌握情况动态推荐」。

## 1.2 适用对象与使用场景

| 角色 | 典型使用场景 |
|---|---|
| 高校教师 | 上传本课程教材/课件 → 自动生成知识图谱 → 人工校对修正 → 分享给学生 → 通过学情监测了解学习进度 |
| 高校学生 | 加入课程 → 浏览知识图谱理解课程结构 → 标记已掌握知识点 → 按推荐路径学习 → 随时提问 |
| 教学管理者 | 多课程统一管理、平台资源治理、运行状态监控 |

**不适用场景（边界说明）**：

- 系统面向**单门课程内的知识组织**，明确**不提供跨课程知识融合**（不同课程的同名知识点相互独立）；
- 抽取质量受原文结构影响，**扫描版 PDF（无文本层）无法处理**；
- 系统依赖外部大模型 API，**必须联网**，不适用于完全离线环境。

## 1.3 系统核心功能与特色

以下五项是本系统相对手工建库方式的实质差异，也是竞赛演示中应当重点展示的部分。

### 特色一：从文档到图谱的自动化构建

教师上传 PDF / DOCX / TXT / MD 文档后，系统自动完成解析、分块、实体抽取、关系识别与入图，无需任何标注工作。

- **对教师的价值**：原本需要数天手工整理的知识结构，压缩到一次上传；
- **可验证的证据**：见 [3.2.3 上传文档](#323-上传课程文档核心步骤) 与 [5.3 准确率测试](#53-知识抽取准确率测试)。

### 特色二：知识点在原文中的可追溯定位

知识图谱中的每个知识点都可以回到它被抽取出来的**原始文档片段**。

- **对教师的价值**：可以核对抽取是否准确，判断是模型错误还是原文本身表述模糊；
- **对学生的价值**：阅读文档时可看到当前段落对应的知识点，实现「读文献 + 看图谱」联动；
- **对应功能**：见 [3.2.9 文档在线阅读](#329-文档在线阅读)。

### 特色三：基于掌握情况与前置关系的路径推荐

系统依据图谱中的前置关系和学生的实际掌握情况，动态计算下一步应学习的知识点。

- **对学生的价值**：不必自己判断「接下来该学什么」，避免在不具备前置知识时贸然学习后续内容；
- **算法约定与边界条件**：见 [4.3 个性化学习路径推荐](#43-个性化学习路径推荐)。

### 特色四：基于课程内容的 RAG 问答

学生提问后，系统先检索课程知识图谱中的相关知识点，再交由大模型生成回答，并**给出本次回答所依据的知识点引用来源**。

- **对学生的价值**：回答围绕本课程内容展开，并可通过引用来源自行核对；
- **技术边界说明**：见 [4.4 RAG 智能问答](#44-rag-智能问答)（含准确性的客观描述）。

### 特色五：教师可校对、可干预

自动生成的结果并非最终结果。教师可增删节点、修改知识点描述、建立关系，也可对知识点图谱结构进行人工修正。

- **对应功能**：见 [3.2.4 查看与编辑知识图谱](#324-查看与编辑知识图谱)。

## 1.5 用户角色与权限说明

系统分三种角色，权限按**三档**授予。

| 角色 | 登录后落点 | 可访问范围 |
|---|---|---|
| 教师 | 课程中心 → 我的课程 | 本人创建或被邀请协作的课程 |
| 学生 | 课程中心 → 我的课程 | 已加入并审核通过的课程 |
| 管理员 | 管理工作台 | 全平台（治理视角，不参与教学） |

### 三档权限

| 关系 | 读课程元数据 | 读课程内容 | 管理课程 |
|---|---|---|---|
| 课程创建者 / 协作教师 | ✅ | ✅ | ✅ |
| 已通过审核的学生成员 | ✅ | ✅ | ❌ |
| 待审核 / 被拒绝 / 已被移除 | ✅（仅查看自己的申请状态） | ❌ | ❌ |
| 公开课程（**仅学生**） | ✅ | ❌ | ❌ |
| 公开课程（教师） | ❌ | ❌ | ❌ |
| 无任何关系 | ❌ | ❌ | ❌ |

**两点需要特别说明**：

1. **公开课程的元数据只对学生开放。** 学生需要看到公开课程详情才能提交加入申请；教师对本人课程之外无可见性，避免教师误入他人课程。
2. **「已被移除」优先于「公开」。** 被移除的成员不会因课程转为公开而自动恢复，必须重新申请。

# 第二章 系统安装与部署

## 2.1 快速启动（竞赛演示用）

**这是最短路径。** 假设本机已安装 Python 3.10+、Node.js 18+、Neo4j 5.x，完整流程如下：

```bash
# ① 启动 Neo4j（Neo4j Desktop 点击 Start；或命令行）
cd neo4j-community-5.x && ./bin/neo4j console      # Windows: bin\neo4j.bat console

# ② 配置后端环境变量
cd backend
cp .env.example .env                                # Windows CMD 见下方对照表
# 用编辑器打开 .env，至少填写：LLM_API_KEY、EMBEDDING_API_KEY、NEO4J_PASSWORD、SECRET_KEY

# ③ 安装后端依赖
python -m venv .venv
.venv\Scripts\activate                              # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

# ④ 启动后端（保持终端开启）
python -m uvicorn app.main:app --reload

# ⑤ 新开终端，启动前端（保持终端开启）
cd frontend-vue
npm install
npm run dev
```

**访问系统：** 浏览器打开 <http://localhost:5173>

## 2.4 图数据库与外部服务配置

### 2.4.1 安装并启动 Neo4j

Neo4j 是**外部依赖**，不在 pip 依赖内，必须先于后端启动。

**方式 A：Neo4j Desktop（推荐用于演示环境）**

1. 官网下载 Neo4j Desktop 并安装
2. 新建 Local DBMS，版本选 5.x
3. 设置密码（后续填入 `.env`）
4. 点击 **Start**，确认状态为 Running

**方式 B：Neo4j Community Server**

```bash
cd neo4j-community-5.x
./bin/neo4j console              # Windows: bin\neo4j.bat console
```

**连接信息：**

| 项 | 默认值 |
|---|---|
| Bolt 地址 | `bolt://localhost:7687` |
| HTTP 地址 | `http://localhost:7474` |
| 默认用户 | `neo4j` |
| 初始密码 | `neo4j`（首次登录强制修改） |

> 首次访问 Neo4j Browser 需修改初始密码。**改完的密码填入 `.env` 的 `NEO4J_PASSWORD`**。

### 2.4.2 申请大模型 API Key

系统需要**两家**服务商的 Key，缺一不可（原因见下）：

| 用途 | 服务商 | 申请地址 | 说明 |
|---|---|---|---|

## 2.9 生产环境部署与安全建议

竞赛演示按 2.1 启动即可。若需长期运行或对外提供服务，注意以下几点。

### 2.9.1 服务部署

1. **不要使用 `--reload`**。它面向开发，会监听文件变化重启，且性能更低。
2. **前端打包**：`npm run build` 产出 `frontend-vue/dist/`，交由 Nginx 等服务托管；此时需把 Nginx 的 `/api` 反向代理到后端 8000 端口，替代 Vite 的开发代理。
3. **多进程部署的适用条件**：

   ```
   uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
   ```

   ⚠️ **不要不加分析地照搬 `--workers 4`。** 适用性取决于两点：
   - **SQLite 的写入并发**：SQLite 采用库级写锁，多进程并发写入会互相阻塞甚至报 `database is locked`。本项目为写入较少的教学场景，若并发写压力上升，应改用「单写进程 + 读副本」或迁移到 PostgreSQL/MySQL；
   - **Neo4j 连接池**：每个 worker 会建立自己的连接池。worker 数量 × 连接数不应超过 Neo4j 的 `dbms.connector.bolt.thread_pool_max_size`。

   在本项目的预期负载下（课堂规模、数十人并发），**单进程配合异步即可满足**；`--workers` 主要用于提高并发请求吞吐，需结合实际压测结果确定。
4. **收紧 CORS**：当前后端 `allow_origins=["*"]` 全放行（便于开发）。对外部署必须改为具体域名。
5. **启用 HTTPS**：由反向代理终止 TLS。
6. **显式配置引导密码**，避免依赖启动日志。

### 2.9.2 数据安全

| 措施 | 说明 |
|---|---|
| `.env` 权限 | 限制为仅运行账号可读，且**不纳入版本控制** |
| `SECRET_KEY` 轮换 | 泄露后必须更换；更换会使全部已签发 Token 失效，用户需重新登录 |
| 日志访问控制 | 见 [7.3](#73-日志及系统监控) |
| 定期备份 | 见 [7.1](#71-数据备份与恢复) |

### 2.9.3 错误信息暴露

⚠️ **当前实现会把后端异常信息返回给前端。** 这在开发与竞赛演示时有助于定位问题，但**在生产环境可能向普通用户暴露技术细节**（如文件路径、内部调用栈摘要、外部服务报错原文）。

**部署建议**：对普通用户，前端应把此类错误统一呈现为友好的提示（如「操作失败，请稍后重试」），详细错误仅写入服务端日志供管理员排查。**若当前版本尚未做此区分，请在部署说明中如实标注，并作为后续改进项。**

| 新建关系 | 在两个知识点之间建立关系，选择关系类型 |

**四种关系类型**：

| 类型 | 中文名 | 含义 |
|---|---|---|
| `CONTAINS` | 包含 | 上下位、整体-部分、类别-成员 |
| `PRECEDES` | 前置 | 学习 A 是学习 B 的前提（**路径推荐依赖此关系**） |
| `APPLIES_TO` | 应用于 | A 是方法/算法，用于解决 B 所代表的问题 |
| `RELATED_TO` | 相关 | 密切相关但非以上三类 |

> ⚠️ **两点注意**：
> 1. **不要试图创建自定义关系类型。** 系统对关系类型有白名单校验，非法值会回退为「相关关系」，自定义类型不会生效。
> 2. **修改知识点描述会使该文档的向量索引失效**，下次问答会重新计算整个文档的向量（涉及外部 API 调用），首次响应会明显变慢。详见 [4.4.4](#444-索引的构建与失效)。

# 第四章 核心功能原理与使用说明

本章解释用户**需要理解**的工作原理。代码级实现细节请参见《项目详细方案》。

## 4.1 文档解析与知识抽取

### 4.1.1 处理流程

```
上传文档
   ↓
① 解析：按格式调用对应解析库提取纯文本
   ↓
② 清洗：统一空白字符、去除页眉页脚等噪声
   ↓
③ 分块：按章节切分，超长章节按段落切分为约 6000 token 的块
   ↓        （相邻块之间保留约 400 token 的重叠）
④ 抽取：每个块并发提交给大模型，抽取知识点与关系
   ↓
⑤ 合并：跨块结果去重、校验、过滤
   ↓
⑥ 入图：写入 Neo4j
```

### 4.1.2 为什么需要重叠分块

长文档必须切分后才能交给大模型处理。但切分会产生一个问题：跨块的指代会断裂。例如第 2 块开头的「该算法」指的是第 1 块末尾提到的内容，没有重叠时模型无从判断。

因此相邻块之间保留约 400 token 的重叠区。代价是重叠部分会被重复抽取，由合并环节的去重逻辑兜底。

### 4.1.3 关系类型的判定规则

系统让大模型按一个**固定顺序**判断两个知识点之间的关系，先命中先返回：

| 顺序 | 判定条件 | 输出关系 |
|---|---|---|
| 1 | 上下位 / 整体-部分 / 类别-成员 | `CONTAINS` |
| 2 | 学习 A 是理解 B 的必要前提 | `PRECEDES` |
| 3 | A 是方法/算法，用于解决 B 代表的问题 | `APPLIES_TO` |
| 4 | 明确密切相关但非上述三类 | `RELATED_TO` |
| 5 | 证据不足 | **不输出** |

**特别注意两类容易混淆的情况**：

- 「栈是一种操作受限的线性表」→ 应判为**包含关系**（线性表包含栈），而非前置关系；
- 「本章先介绍线性表，再介绍栈」→ 这只是**叙述顺序**，不能判为前置关系。

因为文本中出现顺序不等于学习依赖顺序，如果把叙述顺序误判为前置关系，学习路径推荐会产生错误结果。

**设计取向**：系统在提示词中明确要求「宁可少抽取，也不要臆造关系」——即**优先保证准确率**，允许一定程度的漏抽。

### 4.1.4 合并与校验

抽取结果在写入图谱前会经过多层校验：

| 校验项 | 规则 |
|---|---|
| 实体去重 | 按规范化后的名称去重（全角转半角、折叠空白、纯英文统一大写） |
| 关系类型 | 必须属于四种合法类型 |
| 自环 | 起点与终点相同的边被丢弃 |
| 悬空边 | 两端知识点必须都存在于实体集合中 |
| 重复边 | 相同「起点-类型-终点」三元组只保留一条 |

### 4.1.5 已识别与未识别的能力边界

**已识别的**：

- 一章规模（约 1.5 万字符）的课程文本，可抽取约 50 个知识点、30 余条关系；
- 知识点的类别归入四类：概念、定理、公式、方法；
- 关系类型覆盖四种。

**未识别的（已知限制）**：

| 限制 | 说明 |
|---|---|
| 扫描版 PDF | 无文本层，无法解析。需先 OCR |
| 图表与公式图像 | 图片内容不参与抽取 |
| 跨文档知识融合 | 不提供。同名知识点在不同文档中相互独立 |
| 同义词归并 | 当前未启用别名映射表，同一概念的多种写法可能被识别为不同知识点 |

## 4.2 知识图谱生成、浏览与编辑

### 4.2.1 数据组织方式

**知识点的唯一标识由三个要素共同确定**：课程 + 文档 + 知识点名称。

这带来的直接结果是：**同一门课程的两份文档中出现同名知识点时，它们是两个独立的节点**。例如《数据结构》教材和课件中都有「栈」，二者各自拥有独立的描述与关系。

**为什么这样设计**：修改一份文档的知识点不会波及另一份文档，避免课件修订导致教材图谱被意外改动。

### 4.2.2 与赛题要求的对应

| 赛题要求 | 系统实现 |
|---|---|
| 多课程独立管理 | 按课程隔离，支持同时维护多门课程 |
| 不要求跨课程融合 | 课程之间不建立关联，符合赛题要求 |
| 文档级隔离 | 同一课程内进一步按文档隔离 |

### 4.2.3 图谱的完整性保障

系统在返回图谱数据前会做**引用完整性校验**：每条关系的两端必须都能在返回的节点集合中找到，否则该关系被丢弃并记录日志。

**为什么需要**：前端图渲染库遇到「关系指向不存在的节点」时会直接抛错、整图无法显示。宁可少显示一条边，也不能让整个图谱打不开。

### 4.2.4 编辑操作的影响范围

| 编辑动作 | 影响 |
|---|---|
| 修改知识点名称 / 类别 / 描述 | **该文档的向量索引整体失效**，下次问答重新计算 |
| 删除知识点 | 该节点及其关联关系一并删除 |
| 新建 / 删除关系 | 仅影响该关系 |

> ⚠️ 第一项影响范围较广，演示与日常使用时需注意，详见 [4.4.4](#444-索引的构建与失效)。

## 4.3 个性化学习路径推荐

### 4.3.1 关系方向的定义（重要）

系统中的前置关系有严格的**方向约定**：

```
A -[:PRECEDES]-> B     表示「A 是 B 的前置知识」，即先学 A，再学 B
```

由此推出：

| 概念 | 对应 |
|---|---|
| B 的前置知识 | 指向 B 的边（入边） |
| B 解锁的后续知识 | 从 B 出发的边（出边） |
| 入门知识点（根节点） | 没有任何入边的节点 |

**在界面上理解**：图谱中箭头从 A 指向 B，表示「学完 A 才能学 B」。

### 4.3.2 下一步推荐的算法

```
输入：学生已掌握的知识点集合 M

① 候选生成
   找出所有满足「存在某个已在 M 中的知识点指向它」且「它自身不在 M 中」的节点

② 前置饱和检查（核心步骤）
   对每个候选节点，取其全部前置知识集合 P
   仅当 P ⊆ M 时，该候选才被保留
   —— 即：所有前置都必须掌握，而不是掌握其中一部分

③ 优先级排序
   按 |P|（前置数量）从多到少排序

④ 截断
   最多返回 10 条
```

**第 ② 步的意义**：这是「拓扑排序」思想的应用——只有当某个知识点的所有前置都已具备时，学习它才是可行的。把「入度为 0」放宽为「所有前驱已完成」。

**关于第 ③ 步的说明**：系统按前置数量降序排列，其依据是「前置越多，说明该知识点在知识体系中越靠后、越综合，越应该在当前阶段优先补齐」。**这是一个业务启发式规则，而非数学上的必然结论。** 其他合理的排序策略（如优先推荐路径最短的知识点）同样成立，本系统的选择已在实现中固定，此处如实说明。

### 4.3.3 目标路径的算法

```
输入：目标知识点 T

沿前置关系从「入门知识点」出发搜索到 T 的路径
  · 起点必须是入门知识点（没有任何前置）
  · 路径深度上限 10 层
  · 按路径长度升序排列，最多返回 5 条（即最短路径优先）
```

**两个重要约定**：

1. **起点必须是入门知识点**——排除了「从半路开始」的片段路径，保证推荐路径是完整可学的。
2. **不考虑学生已掌握的知识点**——无论学生当前掌握到哪里，返回的都是从入门到目标的完整路径。它回答「学会 T 需要经过哪些步骤」，而不是「我还需要学几步」。

### 4.3.4 边界条件与已知限制

| 情况 | 系统行为 |
|---|---|
| 学生未标记任何已掌握知识点 | 推荐入门知识点（无前置的节点），最多 10 个 |
| 已掌握但未解锁新知识点 | 返回除已掌握外的入门知识点，提示「未解锁新知识点」 |
| 某知识点无前置关系 | 查询前置时，降级返回其「包含」关系的上层概念，标注为「建议先了解的上层概念」 |
| 目标知识点无前置路径 | 降级返回该知识点本身 + 其相关概念，提示「该知识点未抽取到先修路径」 |
| 目标知识点不存在 | 返回空，前端提示知识点不存在 |

**已知限制（如实说明）**：

| 限制 | 影响 |
|---|---|
| **无显式环检测** | 系统未对图谱做环检测，防止无限遍历的方式是**限制路径深度**（前置查询 5 层、目标路径 10 层）。若图谱中存在环，路径不会被无限展开，但可能返回绕行的结果。**建议教师在建图时避免制造环**（如 A→B→C→A） |
| **同优先级无确定顺序** | 当前置数量相同时，系统未定义明确的排序规则，显示顺序取决于数据库返回顺序。**相同优先级的推荐结果之间没有稳定顺序** |
| **前置查询可能重复** | 若某个前置知识点通过多条路径到达目标，查询结果中可能出现重复条目 |

> 上述限制属于当前版本的客观情况，建议在《项目详细方案》中作为改进方向记录。

## 4.4 RAG 智能问答

### 4.4.1 检索链路

```
学生提问
   ↓
① 问题向量化（调用 bge-m3）
   ↓
② 取回该文档的全部知识点向量（必要时先构建/更新索引）
   ↓
③ 计算问题向量与每个知识点向量的余弦相似度，取最相关的若干条
   ↓
④ 按知识点标识回查图谱，取回知识点的名称、类别、描述与关系
   ↓
⑤ 与问题一起提交给大模型生成回答
   ↓
⑥ 返回「回答 + 本次使用的知识点引用来源」
```

### 4.4.2 关于回答准确性的客观说明

**系统通过提示词约束模型优先依据检索到的课程内容作答**，具体约束包括：

1. 优先使用提供的知识内容回答问题；
2. 如果知识库中没有相关信息，应如实告知，不要编造；
3. 回答要准确、简洁、易于理解；
4. 如合适，可推荐相关知识点供进一步学习。

**需要明确的技术边界**：

| 说明 | 内容 |
|---|---|
| 引用来源的含义 | 引用来源是**本次实际提供给模型的上下文**，即「回答所依据的材料」。它证明检索到了哪些内容，**但不等于回答必然正确** |
| 无强制校验 | 系统**未对模型的输出做事实性校验**。即使有检索内容，大模型仍可能生成检索内容未直接支持的信息 |
| 检索质量决定上限 | 若检索到的知识点与问题不相关，回答质量会下降 |
| 检索不足时的行为 | 提示词要求模型如实告知知识不足，但这是**提示词层面的软约束**，不是硬性拦截 |

> **结论**：系统通过「先检索课程内容、再生成回答、并给出引用来源」的方式降低了无依据生成的风险，提高了回答与课程内容的一致性。**回答的准确性应通过问答测试集进行验证**，结果见 [5.2](#52-核心功能测试) 与《问答测试集》。

### 4.4.3 检索的降级机制

为保障弱网或未配置向量服务时功能仍可用，系统采用三级降级：

| 级别 | 触发条件 | 行为 |
|---|---|---|
| 一级：向量检索 | 正常情况 | 语义相似度检索 |
| 二级：关键词检索 | 向量检索失败或未配置向量服务 | 按关键词匹配知识点 |
| 三级：同文档补充 | 检索结果不足 | 用同文档其他知识点补足上下文 |

> ⚠️ **降级是静默的**。当向量服务不可用时，系统不会报错，而是自动退回关键词检索——表现为「回答质量下降但不报错」。排查时请查看后端日志中的警告信息，或确认 `.env` 中的 `EMBEDDING_API_KEY` 是否有效。详见 [6.5 Q3](#65-大模型向量检索与数据库问题)。

### 4.4.4 索引的构建与失效

**构建时机**：系统采用**懒构建**——首次问答时若发现索引缺失，才现场生成该文档全部知识点的向量。

**重建时机**：每次问答前会比对图谱中当前的知识点与已存储的向量是否一致，不一致则整体重建。

**失效粒度**：**整个文档**。教师修改任意一个知识点的描述，会导致该文档全部向量被删除，下次问答时全量重算。

**为什么要整份重建而不是只更新一条**：知识点重新抽取时，其内部标识会整体更换。旧向量会指向已不存在的节点，而数据库表中的记录「非空」会让系统误以为索引有效、永不重建。因此系统采用「整份比对、整份重建」的策略，用一定的性能代价换取索引不会失效后无声无息。

**对使用者的影响**：

| 场景 | 表现 |
|---|---|
| 首次对该文档提问 | 明显较慢（需现场生成向量） |
| 教师编辑过该文档的知识点后首次提问 | 明显较慢（全量重建） |
| 后续提问 | 正常速度 |

> ⚠️ **演示提示**：如果演示流程中包含「先修改图谱、再当场提问」，请在修改后**先提一个问题把索引热起来**，否则那一问的耗时会明显偏长。

### 4.4.5 检索方式的性能特征

系统采用**全文比对**的方式计算相似度，未使用近似最近邻（ANN）索引。

| 项 | 说明 |
|---|---|
| 复杂度 | 与知识点数量成正比 |
| 适用规模 | 单文档数百个知识点以内，响应时间为毫秒级 |
| 不适用 | 跨全部课程的大规模检索 |

**为什么不用 ANN**：当前文档规模（数十至数百个知识点）远未达到需要索引的程度，全文比对的结果是**精确解**而非近似解，反而更准确。相关对比实验见《论文算法复现实验》。

## 4.5 题库、练习及学情分析

### 4.5.1 判分规则

| 题型 | 判分方式 |
|---|---|
| 单选题 | 文本归一化后比对 |
| 多选题 | 集合相等判定（顺序无关） |
| 判断题 | 归一化后比对 |
| 填空题 | 逐空比对 |
| 解答题 | 教师人工批改 |

**归一化规则**：判分前统一去除首尾空白、全角字符转半角、转为小写。因此「Ａ」与「a」等价。

### 4.5.2 答案的可见性控制

学生端接口采用**字段白名单**方式构造响应，`answer`（答案）与 `analysis`（解析）字段**不会下发**给学生。正确答案仅在该题提交作答后随判分结果返回。

### 4.5.3 题目删除的策略

| 情况 | 行为 |
|---|---|
| 题目已有作答记录 | **软删除**：移出出题池，但不删除记录，保护学生作答历史 |
| 题目无任何作答记录 | 物理删除 |
| 文档被删除时 | 该文档的题目及其作答记录一并清理；**课程通用题（不属于任何文档）保留** |

### 4.5.4 学情分析的进度口径

```
学习进度 = 已掌握知识点数 / 该文档知识点总数 × 100%
```

进度**按文档计算**。切换文档后，进度会相应变化。

| 指标 | 结果 | 说明 |
|---|---|---|
| 关系主指标 F1 | **0.8312** | 赛题申报口径 |
| 实体类别准确率 | 见测试报告 | 在「已识别实体」的交集上评价 |

**关系主指标的统计口径**：

- Precision = 正确预测数 / 预测总数（金标准全部关系为分母基准）
- Recall = 正确预测数 / 核心关系数（核心关系 = 原文明确、无争议的关系）
- 模型的输出必须落在金标准内才算正确；方向错误、类型错误、臆造均全额扣分

**辅助指标**（详见测试报告）：按关系类型的 P/R/F1、方向错误率、错误归因五分类（臆造 / 方向颠倒 / 类型混淆 / 同义拆分 / 漏抽）。

> **说明**：模型输出携带的 `confidence`（自评置信度）**不参与任何 P/R/F1 计算**，仅用于阈值过滤。

## 6.1 安装部署问题

### Q1：Neo4j 无法启动 / 连接不上

**问题现象**：后端启动时报连接错误，或 Neo4j Desktop 状态异常。

**可能原因**：Neo4j 未启动；密码错误；端口被占用。

**解决步骤**：

1. 确认 Neo4j 已启动（Neo4j Desktop 显示 Running）
2. 访问 `http://localhost:7474`，确认能打开 Neo4j Browser
3. 核对 `.env` 中的 `NEO4J_PASSWORD` 与 Neo4j 实际密码是否一致
4. 检查 7687 端口是否被占用（命令见 2.1 跨平台对照表）

**仍无法解决时**：查看 Neo4j 的 `logs/` 目录，看具体报错。常见的是端口冲突或数据目录损坏（后者可尝试新建一个 DBMS）。

### Q2：后端启动崩溃，报 starlette 相关错误

**问题现象**：`python -m uvicorn app.main:app --reload` 立即退出并打印异常。

**可能原因**：依赖版本不匹配。`starlette` 被升级到了与 `fastapi 0.115.x` 不兼容的版本。

**解决步骤**：

```bash
cd backend
pip install -r requirements.txt --force-reinstall
```

**仍无法解决时**：确认是否曾执行过 `pip install -U starlette` 之类的单独升级。重建虚拟环境是最可靠的方案：

```bash
rm -rf .venv          # Windows: rmdir /s .venv
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

### Q3：健康接口返回异常或无法访问

**问题现象**：`curl http://localhost:8000/health` 无响应或返回错误。

**可能原因**：后端未启动；端口不是 8000。

**解决步骤**：

1. 确认后端终端仍在运行且无报错
2. 确认终端输出的端口号（若改过端口，需同步修改 `vite.config.js` 的代理目标）
3. 重新执行 `curl http://localhost:8000/health`，期望返回 `{"status":"ok"}`

**仍无法解决时**：查看后端终端完整输出，定位启动阶段的异常。

### Q4：前端启动失败或依赖安装报错

**问题现象**：`npm run dev` 报错，或 `npm install` 失败。

**可能原因**：Node.js 版本过低；npm 源网络问题。

**解决步骤**：

1. 确认 `node --version` ≥ 18
2. 切换镜像源后重装：

   ```bash
   npm config set registry https://registry.npmmirror.com
   rm -rf node_modules package-lock.json
   npm install
   ```

**仍无法解决时**：删除 `node_modules` 后重试；若仍失败，检查是否有代理软件拦截 npm 请求。

### Q5：页面打开是空白

**问题现象**：浏览器访问 5173 端口，页面空白。

**可能原因**：前端未启动；或后端未启动导致接口请求全部失败。

**解决步骤**：

1. 按 F12 打开控制台，查看报错
2. 确认后端已启动（见 Q3）
3. 确认前端终端显示 `Local: http://localhost:5173/`

**仍无法解决时**：查看控制台的网络请求，确认 `/api` 请求是否返回 404 或连接被拒。

### Q6：端口被占用

**问题现象**：启动时报 `address already in use`。

**解决步骤**：按 2.1 的跨平台命令对照表查找并结束占用进程，或改用其他端口启动。

**仍无法解决时**：重启机器是最直接的办法。

## 6.2 教师端操作问题

### Q1：上传后知识点为 0，或提示「文档解析结果为空」

**问题现象**：文档上传成功，但抽取出的知识点数为 0。

**可能原因**：**扫描版 PDF 没有文本层**——它本质是图片，无法提取文字。

**解决步骤**：

1. 用 PDF 阅读器尝试选中正文文字
2. 如果无法选中，说明是扫描件
3. 换用电子版文档，或先用 OCR 工具转换为可复制文本的版本

**仍无法解决时**：换一份 DOCX 或 TXT 文档测试，以排除是否格式特有问题。

### Q2：提示「文件格式不支持」

**问题现象**：上传时被拒绝。

**可能原因**：文件扩展名不在支持范围内，或实际格式与扩展名不符。

**解决步骤**：

1. 确认扩展名为 `.pdf` / `.docx` / `.txt` / `.md` 之一
2. 若是 `.doc`（旧版 Word），用 Word 另存为 `.docx`
3. 若文件从其他格式改名而来（如把 `.doc` 改成 `.docx`），需用 Word 真正转换

**仍无法解决时**：换一份确认无误的文档测试。

### Q3：抽取失败，提示「知识抽取失败」

**问题现象**：解析成功但抽取阶段报错。

**可能原因**：API Key 无效；账号余额不足；网络不通。

**解决步骤**：

1. 检查 `.env` 中的 `LLM_API_KEY` 是否有效
2. 登录 DeepSeek 平台确认账户余额
3. 检查网络能否访问 `LLM_API_BASE`
4. 查看后端终端的具体报错信息

**仍无法解决时**：见 [6.5 Q1](#65-大模型向量检索与数据库问题)。

### Q4：学生无法加入课程

**问题现象**：学生输入加课码后提示无效，或申请一直处于待审核。

**可能原因**：加课码输入错误；申请尚未被审核。

**解决步骤**：

1. 核对加课码（系统已剔除 `0/O`、`1/I/L` 等易混字符，不会出现这些字符）
2. 学生提交后，教师需在「成员管理」中**通过**其申请
3. 检查学生是否曾被移除（被移除的成员需重新申请，不会自动恢复）

**仍无法解决时**：改用邀请链接的方式让学生加入。

### Q5：图谱修改失败

**问题现象**：编辑知识图谱时保存失败。

**可能原因**：必填字段缺失；存在同名知识点冲突。

**解决步骤**：

1. 确认知识点名称等必填项已填写
2. 若提示重名，检查该文档下是否已存在同名知识点

**仍无法解决时**：刷新页面后重试，并查看浏览器控制台的报错信息。

### Q6：想重新处理一份文档

**操作建议**：当前版本不支持「重新抽取」按钮。如需重做，请**删除该文档后重新上传**。

> ⚠️ **注意**：删除文档会级联清理该文档的知识图谱、向量、学习记录、收藏与该文档的题目。**学生的相关学习记录会一并删除**，操作前请确认。

**仍无法解决时**：如仅需修正个别知识点，可在图谱编辑态直接修改，无需重新上传。

### Q7：如何导出或备份课程资料

**当前状态**：系统界面暂未提供课程资料的导出功能。

**替代方案**：

- 原始文档仍保存在服务器 `backend/data/uploads/` 目录下，可按目录结构手动获取
- 知识图谱可通过 Neo4j Browser 导出查询结果
- 完整备份方法见 [7.1 数据备份与恢复](#71-数据备份与恢复)

## 6.5 大模型、向量检索与数据库问题

### Q1：知识抽取一直失败

**问题现象**：上传文档后抽取阶段持续报错。

**可能原因**：API Key 无效；余额不足；网络不通；外部服务异常。

**解决步骤**：

1. 确认 `.env` 中 `LLM_API_KEY` 与 `LLM_API_BASE` 正确
2. 登录服务商平台确认余额
3. 测试网络连通性
4. 查看后端终端的完整报错

**仍无法解决时**：临时切换到其他兼容 OpenAI 接口的模型服务，验证是否为服务商侧问题。

### Q2：问答回答「知识库中没有相关内容」

**问题现象**：提问后系统回答未找到相关内容。

**可能原因**（按可能性排序）：

1. **未选定课程与文档**——问答是文档级范围的
2. **该文档没有知识点**——抽取失败或结果为空
3. **Neo4j 中没有图谱数据**——见 Q4

**解决步骤**：

1. 确认已选定课程与文档
2. 前往「图谱管理」确认该文档有知识点
3. 在 Neo4j Browser 中执行：

   ```
   MATCH (n:KnowledgePoint) RETURN count(n)
   ```

   若结果为 0，说明图谱为空

**仍无法解决时**：见 Q4。

### Q3：回答质量突然变差，但不报错

**问题现象**：问答功能可用，但回答明显不如之前准确，且系统没有报错。

**可能原因**：**向量检索静默降级为关键词检索**。当 `EMBEDDING_API_KEY` 未配置或向量服务调用失败时，系统会自动退回关键词检索——功能仍可用，但质量下降且不报错。

**解决步骤**：

1. 检查 `.env` 中的 `EMBEDDING_API_KEY` 是否配置且有效
2. 确认 SiliconFlow 账户余额
3. 查看后端日志中的警告信息（系统在降级时会记录 warning）
4. 确认网络能访问 `EMBEDDING_API_BASE`

**仍无法解决时**：临时改用其他提供 embedding 接口的服务。

### Q4：换机器后图谱为空，问答不工作

**问题现象**：在另一台电脑上 `git clone` 项目并启动后，已有课程还在，但图谱是空的。

**可能原因**：**Neo4j 的数据不随代码仓库走。** SQLite 数据库文件（`app.db`）在项目目录内，会随代码一起获取；但 Neo4j 的数据存储在它自己的数据目录中，`git clone` 拿不到。

**解决步骤**（任选其一）：

1. **重新上传文档**：在新环境的系统中重新上传课程文档，重新抽取
2. **从旧环境导出导入**：在旧环境用 Neo4j 的 dump/load 工具迁移数据
3. **整体迁移**：把旧环境的 Neo4j 数据目录整体复制到新环境

**仍无法解决时**：确认新环境的 Neo4j 确实在运行且 `.env` 指向正确的数据库。

### Q5：修改知识点后第一次提问特别慢

**问题现象**：教师修改了知识点描述，之后第一次提问耗时明显偏长。

**说明**：**这是预期行为。** 向量索引的失效粒度是**整个文档**——修改任意一个知识点会导致该文档全部向量被删除，下次问答时全量重算。详见 [4.4.4](#444-索引的构建与失效)。

**解决步骤**：无需处理，等待索引重建完成即可。若希望避免，可在修改后先提一个无关问题把索引「热」起来。

**仍无法解决时**：若耗时异常长，确认该文档的知识点数量是否过大。

### Q6：数据库文件损坏或数据异常

**问题现象**：SQLite 报错，或数据出现异常。

**解决步骤**：

1. **立即停止后端服务**，避免继续写入
2. 备份当前的 `backend/data/app.db`（即使已损坏，也保留以便分析）
3. 从最近的备份恢复（见 [7.1](#71-数据备份与恢复)）

**仍无法解决时**：SQLite 自带完整性检查，可执行 `PRAGMA integrity_check;` 查看损坏程度。

### Q7：测试脚本运行后演示数据被污染

**问题现象**：运行了 `test_*.py` 或前端 e2e 测试后，演示库中多出了测试账号或课程。

**可能原因**：**多数验证脚本会真实写入数据库**——会真实创建账号、课程与节点，而不是使用隔离的测试库。

**解决步骤**：

1. 停止使用演示库运行测试
2. 手动清理测试数据，或从备份恢复
3. **今后在运行测试前先备份 `app.db`**，或另建一份数据库专用于测试

> ⚠️ **这是本项目当前的一个已知风险**：验证脚本默认连接线上库，没有独立的测试环境配置。建议在演示前统一执行一次数据清理，并核对 `t_course`、`t_document`、`t_question`、`t_kp_embedding` 等关键表的计数。

## 6.6 安全与凭据问题

### Q1：忘记引导账号的密码

**推荐做法**：优先使用管理端的「重置密码」功能（需另一个可用的管理员账号）。

**备选做法**：查看后端启动日志——随机密码在账号首次创建时打印过一次。日志文件位于 `backend/_uvicorn.log`，搜索「管理员」或「演示教师」。

**应急做法**（仅限开发环境，见 [7.2](#72-账号与密钥管理)）：删除该账号后重启后端重建。

### Q2：怀疑凭据泄露

**处理步骤**：

1. **更换 `SECRET_KEY`**（会使全部已签发的登录凭证失效，所有用户需重新登录）
2. 重置相关账号密码
3. 检查审计日志（管理端 → 审计日志）确认是否有异常操作
4. 按 [7.3](#73-日志及系统监控) 处理可能泄露密码的日志文件

### Q3：日志中是否有敏感信息

**说明**：当引导账号使用**随机密码**创建时，该密码会被打印到启动日志。这是为了让部署者能够获取初始凭据，但也意味着**日志文件中可能包含有效凭据**。

**处理建议**：见 [7.3 日志及系统监控](#73-日志及系统监控)。

# 第七章 数据管理与系统维护

## 7.1 数据备份与恢复

### 7.1.1 需要备份的数据

系统的数据分布在**三个位置**，**缺一不可**：

| # | 数据 | 位置 | 内容 |
|---|---|---|---|
| 1 | SQLite 数据库 | `backend/data/app.db` | 用户、课程、文档元数据、题库、学习记录、全部向量 |
| 2 | 上传的原始文件 | `backend/data/uploads/` | 按 `{课程ID}/{文档ID}_{文件名}` 组织 |
| 3 | Neo4j 数据 | Neo4j 的 `data/` 目录 | 知识图谱本体（节点与关系） |

> ⚠️ **只备份其中一项是不够的**：SQLite 里没有图数据，Neo4j 里没有用户和向量，uploads 里只有原始文件。**三者缺一，系统都无法恢复到可用状态。**

### 7.1.2 备份方法

**SQLite 与上传文件**：

1. **先停止后端服务**（避免备份过程中数据正在写入）
2. 直接复制 `backend/data/` 整个目录

> **为什么建议停服**：SQLite 采用 WAL 模式，运行中直接复制文件可能出现主库文件与 WAL 文件不一致的情况。停服是最稳妥的方式。

**Neo4j**：

- **Neo4j Desktop**：使用其内置的 Dump / Backup 功能
- **命令行**：停库后复制整个数据目录，或使用 `neo4j-admin database dump`

### 7.1.3 恢复流程（含顺序要求）

**必须按以下顺序恢复**，否则可能出现「有文档记录但文件不存在」或「有用户但图谱为空」的不一致状态：

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 停止后端服务 | 避免恢复期间有写入 |
| 2 | 停止 Neo4j | |
| 3 | 恢复 **SQLite**：将备份的 `app.db` 覆盖到 `backend/data/app.db` | |
| 4 | 恢复 **上传文件**：将备份的 `uploads/` 覆盖到 `backend/data/uploads/` | |
| 5 | 恢复 **Neo4j 数据**：通过 Dump 载入或覆盖数据目录 | |
| 6 | 启动 Neo4j，确认状态正常 | |
| 7 | 启动后端，观察启动日志是否有迁移报错 | |
| 8 | 执行恢复后验证（见下表） | |

### 7.1.4 恢复后的一致性验证

| # | 验证项 | 方法 | 期望 |
|---|---|---|---|
| 1 | 后端启动无异常 | 观察启动日志 | 无迁移报错 |
| 2 | 健康接口 | `curl http://localhost:8000/health` | 返回 `{"status":"ok"}` |
| 3 | 图谱数据完整 | Neo4j Browser：`MATCH (n:KnowledgePoint) RETURN count(n)` | 与备份前一致 |
| 4 | 文档记录与文件一致 | 打开若干文档的「在线阅读」 | 均能正常打开 |
| 5 | 用户可登录 | 用备份前的账号登录 | 登录成功 |
| 6 | 问答可用 | 对已抽取的文档提问 | 返回回答与引用来源 |

> ⚠️ **版本兼容性**：从**较新版本的 Neo4j 备份**恢复到**较旧版本**通常不可行（Neo4j 不支持降级恢复）。恢复前请确认目标环境的 Neo4j 版本不低于备份时的版本。

## 7.2 账号与密钥管理

### 7.2.1 密码重置（推荐方式）

**优先使用管理端功能**：

1. 进入「用户管理」
2. 找到目标用户
3. 执行「重置密码」
4. 将新密码告知用户（用户下次登录会被要求修改）

**优点**：不直接操作数据库，不影响关联数据，且会触发「强制修改密码」流程。

### 7.2.2 密码重置（应急方式，仅限开发环境）

**仅在以下情况使用**：没有任何可用的管理员账号，且已确认无法通过其他途径恢复。

> ⚠️ **直接删除数据库中的用户记录会带来副作用**：
>
> - 该用户的学习记录、收藏、作答记录等**引用该用户 ID 的数据会变成孤立数据**；
> - 与审计日志中记录的该用户操作**失去对应关系**；
> - 若该用户是课程创建者，课程将失去归属。
>
> **操作前必须完整备份 `app.db`。**

**步骤**（开发环境应急）：

1. 停止后端服务
2. 备份 `backend/data/app.db`
3. 确认该账号确实需要重建，并记录其 `user_id` 以便后续清理孤立数据
4. 通过 SQLite 客户端删除该用户记录
5. 配置 `DEFAULT_ADMIN_PASSWORD` 或 `DEFAULT_TEACHER_PASSWORD` 环境变量
6. 重启后端，账号将以新密码重建

> **注意**：环境变量**仅在账号不存在时生效**，不会覆盖已有账号的密码。

### 7.2.3 密钥管理

| 密钥 | 存放位置 | 轮换影响 |
|---|---|---|
| `SECRET_KEY` | `backend/.env` | 更换后**全部登录凭证失效**，所有用户需重新登录 |
| `LLM_API_KEY` | `backend/.env` | 无影响，直接替换 |
| `EMBEDDING_API_KEY` | `backend/.env` | 无影响，直接替换 |
| `NEO4J_PASSWORD` | `backend/.env` | 需同时在 Neo4j 侧修改 |

**建议**：

- `.env` **不纳入版本控制**，限制文件权限为仅运行账号可读
- 定期轮换 API Key
- 演示环境与生产环境使用不同的密钥

## 7.3 日志及系统监控

### 7.3.1 日志中的敏感信息

| 场景 | 是否包含敏感信息 |
|---|---|
| 引导账号使用**随机密码**创建 | ⚠️ **是**——密码会打印到启动日志，且仅打印一次 |
| 引导账号使用**环境变量密码**创建 | 否 |
| 运行期常规日志 | 通常不含凭据 |

**处理建议**：

| 措施 | 说明 |
|---|---|
| 访问控制 | 限制日志目录的读取权限，仅运维人员可访问 |
| 保留期限 | 保留必要期限后删除，不建议长期留存 |
| 安全删除 | 确认不再需要后，彻底删除含初始密码的日志 |
| 及时改密 | 首次登录后立即修改密码（系统会强制要求），使日志中的密码失效 |

> **最根本的解决办法**：正式部署时显式配置 `DEFAULT_ADMIN_PASSWORD` 与 `DEFAULT_TEACHER_PASSWORD`，从源头避免密码被写入日志。

### 7.3.2 系统监控

**入口**：管理端 → 「系统监控」

**指标**：请求量、响应耗时、错误数。

**重要说明**：这些指标来自**内存中的实时计数**，不写数据库、不落日志。这样设计的目的是避免监控本身成为新的性能负担或故障点。**因此进程重启后计数清零**，它反映的是本次运行期间的情况。

**如果需要长期监控**：应接入外部监控系统（如 Prometheus），从应用日志或新增的指标接口采集。

## 7.4 数据清理与版本升级

### 7.4.1 删除操作的影响范围

删除课程或文档时，系统会执行**级联清理**，同时清理两套数据库中的相关数据。

**删除文档时清理的内容**：

```
① Neo4j 中该文档的知识图谱（节点与关系）
② SQLite 中该文档的向量
③ 该文档相关的学习记录
④ 该文档相关的收藏
⑤ 该文档的题目及其作答记录、题目收藏
⑥ 服务器上的原始文件
⑦ 文档记录本身
```

**两点需要注意**：

1. **学生的相关学习记录会被一并删除**——删除文档不只是删掉一份文件，还包括学生在这份文档上的学习痕迹。
2. **课程通用题会被保留**——不属于任何文档的题目（`document_id` 为空）不会随文档删除而消失。

### 7.4.2 版本升级注意事项

| 事项 | 说明 |
|---|---|
| 升级前备份 | **必须先完整备份**（见 7.1） |
| 数据库迁移 | 系统启动时会自动执行幂等的表结构迁移，无需手工操作 |
| 依赖版本 | 不要单独升级 `starlette`（见 [6.1 Q2](#61-安装部署问题)） |
| 回滚 | 若升级失败，用备份回滚；注意 Neo4j 不支持降级恢复 |

## 7.5 故障应急处理

### 7.5.1 服务无法启动

| 步骤 | 操作 |
|---|---|
| 1 | 确认 Neo4j 已启动 |
| 2 | 确认 `.env` 配置完整 |
| 3 | 查看后端终端报错 |
| 4 | 参照 [6.1](#61-安装部署问题) 定位具体问题 |
| 5 | 若无法解决，从最近备份恢复 |

### 7.5.2 外部服务不可用

| 服务 | 影响 | 应对 |
|---|---|---|
| DeepSeek 不可用 | 无法抽取新文档；问答无法生成回答 | 等待恢复，或临时切换到其他兼容 OpenAI 接口的模型 |
| 向量服务不可用 | 问答**自动降级**为关键词检索，功能可用但质量下降 | 检查 key 与余额；恢复后下次问答会自动重建索引 |

> **降级是静默的**，不会报错。排查「回答质量变差」时请优先检查此处（见 [6.5 Q3](#65-大模型向量检索与数据库问题)）。

### 7.5.3 演示前检查清单

| # | 检查项 | 命令/操作 | 通过 |
|---|---|---|---|
| 1 | Neo4j 运行中 | 访问 `http://localhost:7474` | ☐ |
| 2 | 后端健康 | `curl http://localhost:8000/health` | ☐ |
| 3 | 前端可访问 | 打开 `http://localhost:5173` | ☐ |
| 4 | 图谱非空 | Neo4j：`MATCH (n:KnowledgePoint) RETURN count(n)` | ☐ |
| 5 | 演示文档已抽取完成 | 课程文档列表显示知识点数 > 0 | ☐ |
| 6 | **索引已热身** | 提前对演示文档提一个问题 | ☐ |
| 7 | 演示账号可登录 | 教师账号与学生账号各登录一次 | ☐ |
| 8 | 清理测试数据 | 核对课程/文档/题目计数 | ☐ |
| 9 | 网络通畅 | 能访问 DeepSeek 与 SiliconFlow | ☐ |

> **第 6 项尤其重要**：提前提问可以把向量索引构建好，避免现场演示时第一次问答耗时过长（见 [4.4.4](#444-索引的构建与失效)）。

## 附录 F 术语表

| 术语 | 英文/原文 | 通俗解释 |
|---|---|---|
| 知识图谱 | Knowledge Graph | 用「节点 + 连线」表示知识及其关联的结构 |
| 知识点 | Knowledge Point | 图谱中的一个节点，如「二叉树」「快速排序」 |
| 实体 | Entity | 同上，指抽取出的知识点对象 |
| 关系 | Relation | 知识点之间的连线，本系统有四种 |
| `PRECEDES` | 前置关系 | 「先学 A 才能学 B」的依赖关系，是路径推荐的基础 |
| `CONTAINS` | 包含关系 | 「A 包含 B」，如「线性表包含栈」 |
| `APPLIES_TO` | 应用关系 | 「A 用于解决 B」，如「哈希算法应用于查找问题」 |
| `RELATED_TO` | 相关关系 | 密切相关但不是以上三类 |
| 前置知识 | Prerequisite | 学习某知识点前需要先掌握的知识点 |
| 根节点 / 入门知识点 | Root Node | 没有任何前置关系的知识点，是学习的起点 |
| RAG | Retrieval-Augmented Generation | 检索增强生成：先检索资料，再让大模型依据资料作答 |
| 向量 / Embedding | Embedding | 把文字转换成一串数字，使语义相近的文字在数值上也接近 |
| 余弦相似度 | Cosine Similarity | 衡量两个向量方向接近程度的指标，用于判断语义相关度 |
| 索引（向量索引） | Vector Index | 为知识点预先算好的向量集合，问答时用于快速查找 |
| 懒构建 | Lazy Build | 不提前做，等到真正需要时才做（本系统用于向量索引） |
| 降级 | Graceful Degradation | 某个功能不可用时自动切换到较弱但可用的替代方案 |
| 抽取 | Extraction | 从文档中识别出知识点及其关系的过程 |
| 分块 | Chunking | 把长文档切成较小的段落，以便交给大模型处理 |
| 悬空边 | Dangling Edge | 连线的一端指向不存在的节点，属于数据错误 |
| 级联删除 | Cascade Delete | 删除主数据时一并清理其关联的从属数据 |
| P95 | 95th Percentile | 把耗时可从小到大排序，95% 的请求都快于这个值 |
| 幂等 | Idempotent | 同一操作执行多次与执行一次的结果相同 |
| ANN | Approximate Nearest Neighbor | 近似最近邻：用精度换速度的向量检索方式，本系统规模下未使用 |
