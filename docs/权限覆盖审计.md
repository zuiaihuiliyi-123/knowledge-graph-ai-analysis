# 权限覆盖审计（阶段 1C）

> 目的：把「哪些接口靠什么拦住越权」逐模块记录清楚，避免下次改代码时把闸门拆掉却没人发现。
> 审计范围：`backend/app/api/*.py` 的全部路由。判定依据是**代码里实际生效的检查**，
> 不是接口文档的描述。

## 1. 审计方法

1. 用脚本把每条路由连同 `Depends(...)` 依赖、函数体内是否出现 `Permissions.*` 列成表；
2. 对「带 `course_id` 但没有 `Permissions`」的接口逐个回溯：
   - 是否通过本地 helper 转调（如 `graph.py` 的 `_guard()`）；
   - 是否在 service 层做课程归属校验（如 `document_service` / `question_service`）；
   - 如果都没有 → 判为缺口。

## 3. 本次修复：学生端练习接口跨课程越权（`practice.py`）

### 问题

`/api/v1/practice/*` 的 9 条路由里，凡带 `course_id` 的都只校验「已登录」，不校验「是不是这门课的人」：

```
GET  /questions?course_id=<任意>      → 返回题干 + 选项
POST /recommend  {course_id:<任意>}   → 同上，还带推荐理由
POST /submit     {question_id:<任意>} → 返回标准答案 + 解析
```

把这三条串起来就是一条完整的**题库/答案导出链路**：随便填一个 `course_id` 拿到题目 id，
再对每个 id 调 `/submit` 就能拿到正确答案。题目本身不含答案的白名单投影形同虚设。

### 修复

新增 `_guard_course()`，统一走 `Permissions.require_course_content`
（课程创建者 / 协作教师 / 已通过审核的学生成员），并铺到全部 9 条路由：

| 路由 | 处理 |
|---|---|
| `GET /questions`、`POST /recommend` | 参数 `course_id` 校验成员关系 |
| `GET /wrong-book`、`GET /stats`、`GET /favorites`、`POST /favorites`、`DELETE /favorites/{id}` | 同上 |
| `GET /records` | 仅在显式传 `course_id` 时校验（不传 = 查自己的全部记录，本来就只能看到本人数据） |
| `POST /submit` | 先按 `question_id` 反查题目所属课程，再校验成员关系——这是唯一会下发答案的入口，必须逐题校验 |

判定口径与 `documents.py` / `graph.py` 完全一致，非成员统一 4003；课程不存在仍返回 2001。

### 验证

新增 `backend/test_practice_scope.py`（临时库、不生成自动备份、不连图库）：

| 断言 | 结果 |
|---|---|
| 非成员：出题 / 推荐 / 错题本 / 统计 / 收藏列表 / 收藏 / 提交作答 → 全部 4003 | ✓ 7 项 |
| 已通过审核的学生：出题、统计、提交作答 → 正常（0） | ✓ 3 项 |
| 课程创建者：出题 → 正常（0） | ✓ |
| 不存在的课程 → 2001 | ✓ |

`通过 14/14`；`ruff check .` 通过；后端离线回归 **11/11** 仍全绿。

## 4. 已识别但不构成越权的项（记录在案）

| 接口 | 现状 | 为什么先不改 |
|---|---|---|
| `DELETE /api/v1/learning/mark` | 只校验登录，按 `user_id + course_id + kp_id` 删**自己的**学习记录 | 影响面仅限本人数据；即便传入未加入的课程，也只能删到不存在的记录。为保持与 `POST /mark` 一致可后续补 `require_course_content` |
| `DELETE /api/v1/favorites/{kp_id}`（知识点收藏） | 同上，只删本人收藏 | 同上 |
| `POST /api/v1/invites/accept` | 只校验登录 | 令牌本身绑定课程与单次使用（`status=used`），接受行为即「加入课程」，不需要额外成员前置条件 |
| `POST /api/v1/courses/{course_id}/apply` | 只校验登录 | 申请入课本就面向「非成员」；service 内已校验课程可见性（公开/加课码） |
| `GET /api/v1/profile/avatar/{user_id}` | 无鉴权 | 头像按 `user_id` 公开读取，属于产品层面的选择；若后续要求隐私化需单独评估（前端 `<img>` 无法带 Authorization） |

## 5. 后续建议

1. 把 `test_practice_scope.py` 纳入每次改动的必跑清单（已在 `docs/阶段0-基线.md` §3.1 登记）。
2. 涉及权限的改动，在**专用环境**补跑 `test_permission_matrix.py`（它覆盖教师/学生/公开课/待审核四类关系，
   需要真实 app.db 副本 + Neo4j）。
3. 新增带 `course_id` 的接口时，先在 `Permissions` 里选一档（read / content / manage / owner），
   不要只写 `get_current_user`。
