`core/sql_database.py` 只做显式 re-export：

- `sql_db`、`SQLDatabase`；
- 17 个外部实际导入的名字（含私有 `_vec_to_blob` / `_blob_to_vec`）；
- 其余枚举常量、`_SCHEMA_SQL`、`_T_QUESTION_DDL`、`_now`、`JOURNAL_MODE`、`BUSY_TIMEOUT_MS`；
- `sql_db.db_path` 与四个私有查询方法仍保留在实例上（测试/脚本直接使用）。

因此 25 个现有 import 点与 74 个 `test_*.py` **无需改 import**；Phase 1 可单独回退。

## 4. Phase 3：Pydantic 请求模型抽离

### 4.1 结果

42 个 `BaseModel` 中 **40 个**迁到 `app/schemas/`：

```text
schemas/admin.py courses.py course_members.py favorites.py grading.py graph.py
        invites.py learning.py learning_path.py practice.py profile.py qa.py
        questions.py auth.py fusion.py
```

**两个例外**：`api/learning_path.py` 与 `api/practice.py` 的 `RecommendRequest` 保留在原 API 模块。
原因：两个类同名，Pydantic v2 用 `模块名__类名` 生成 `$ref`；如果都移到 schemas，OpenAPI 的
`$ref` 会从 `app__api__...` 变成 `app__schemas__...`，破坏“契约零变化”的验收口径。
保留后，其余 40 个模型移动不影响 `$ref`（类名唯一，Pydantic 只用类名）。

## 7. 已知环境问题（非本次改动引入）

1. `test_profile_api.py` / `test_course_member_flow.py` 会复制 `backend/data/app.db`；
   当前 `.env` 的库在仓库外 `kg-data/app.db`，该文件不存在，脚本在进入业务断言前即失败。
   需要按 `docs/阶段0-基线.md` 在副本库环境运行。
2. `test_sqlite_wal.py` 假定库中已有表（它复制“线上库”做 A/B）；直接对空临时库运行会
   `no such table: t_question`。先执行 `sql_db.init_tables()` 即可。
3. 需要真实 Neo4j / LLM 的脚本未在本轮全量运行；验证以临时库 + 图库桩为主。
4. 测试脚本仍可能写库；必须使用临时库/副本库，**不要**指向 `kg-data/app.db`。
