# 知识抽取方案 v3 对比报告

> 对比对象：现行单阶段「本体约束抽取」（`backend/app/services/knowledge_extractor.py`）与外部提供的 `knowledge_extraction_v3`（两阶段：实体 → 关系）。
>
> 结论：**在项目现有四章人工金标准上，现行方案全面且显著更好，不建议切换到 v3。** v3 的理念（证据字段、方向依据、漏抽实体回传、领域规则分包）有可取之处，但其交付形态存在实体过度抽取、证据逐字校验误杀、输出上限过低等问题，四章关系 F1 均值仅 0.3467（现行 0.9066）。

---

## 一、评测口径

为排除提示词内容差异的干扰，除「主对比」外另做两组消融：

| 方案 | 说明 |
|---|---|
| 现行 | 现行单阶段抽取器，原样运行 |
| v3 原样 | v3 交付代码 + 自带领域规则包（树用 `computer_science`，其余用 `complexity` / `physics` / `chemistry`） |
| v3 去证据门 | 在 v3 原样基础上，把被 `invalid_evidence` 丢弃的关系加回（纯离线重评，不重新调模型） |
| v3 + 现行规则 | 保留 v3 两阶段架构，把现行 Prompt 的领域规则逐段迁入 v3 的实体/关系 Prompt |

统一条件：

- 同一源文本、同一份人工 Gold、`temperature=0`、单轮、`chunk=6000 / overlap=400`
- 关闭抽取缓存（`EXTRACT_CACHE=0`），确保真实调用
- 评分一律使用 `backend/eval_accuracy.py`（仓库唯一评分实现），未修改 Gold、别名表与匹配规则
- v3 代码仅把相对导入改为 `app.*` 绝对导入，未改动任何常量与提示词

四章 Gold 规模：树 49 实体/33 关系，复杂度 40/47，运动学 38/60，化学 62/74。

## 三、根因分析

### 3.1 两阶段拆分让实体阶段变成「召回最大化」，误抽激增

v3 实体阶段只要求输出实体，不再同时承担「哪些实体值得建关系」的取舍。结果是实体数量远超 Gold：

| 章节 | Gold 实体 | 现行 | v3 原样 | v3 + 现行规则 |
|---|---:|---:|---:|---:|
| 树 | 49 | 55 | 51 | 56 |
| 复杂度 | 40 | 38 | 45 | 40 |
| 运动学 | 38 | 36 | **86** | **85** |
| 化学 | 62 | 66 | **139** | **134** |

运动学多出的 50 个实体主要是公式、变量和动作短语，例如 `v = v_0 + at`、`x = x_0 + v̄t`、`识别已知量`、`检查答案合理性`、`摩擦`、`竖直位移`。化学同理。现行方案在同一条 Prompt 里同时要求「实体要能支撑关系」与「宁少勿滥」，因此实体精度高得多（运动学 P=1.0）。

> 注：把现行实体规则迁入 v3 实体 Prompt 后，运动学仍抽出 85 个实体，说明主因是**任务拆分本身**，不是规则缺失。

### 3.2 「evidence 必须逐字出现在原文」是硬门，误杀大量正确关系

v3 在合并阶段要求关系 evidence 是原文连续片段（空白折叠后 `in` 判定），否则丢弃。实测四章共丢弃 49 条，其中 **36 条与 Gold 三元组完全一致（73.5%）**：

| 章节 | invalid_evidence 丢弃 | 其中 Gold 正确 |
|---|---:|---:|
| 树 | 6 | 6 |
| 复杂度 | 26 | 19 |
| 运动学 | 10 | 7 |
| 化学 | 7 | 4 |

被误杀的包括 `二叉树 CONTAINS 完全二叉树`、`时间复杂度 CONTAINS 常数阶`、`矢量 CONTAINS 速度`、`元素周期表 CONTAINS 族` 等。原因是模型常把原文改写成更规范的证据句（如「二叉树包括完全二叉树」），语义正确但不再是逐字片段。

离线去掉该门后：树 F1 0.310→0.469、复杂度 0.377→0.600；运动学基本持平（0.257→0.250），化学基本持平。**该门在部分章节能压 FP，但整体是钝器，净损失大于收益。**

### 3.3 实体粒度与命名不一致，连带丢失关系

v3 倾向把属性/表示法拆成更长、更具体的名字：

| v3 输出 | Gold / 现行输出 |
|---|---|
| 节点的度 | 度 |
| 二叉树的高度、节点高度 | 高度 |
| 节点的深度 | 深度 |
| 二叉树数组表示 | 数组表示 |
| 满二叉树 | 完满二叉树（Gold 用名） |

这些名称在冻结归一化后仍不相等，既算实体 FP/FN，也让以其为端点的关系全部匹配失败。现行 Prompt 对此有明确的命名与粒度约束（如「名称不要带冗余后缀」「不要过度拆分」），这是其 F1 更高的直接原因之一。

### 3.4 关系阶段只能从冻结的候选池里选，实体漏抽会永久变成关系漏抽

v3 关系阶段的 source/target 必须来自实体阶段候选池。树章候选池漏了 `链表`、`多级索引`、`红黑树` 等 Gold 实体，对应关系 `链表 RELATED_TO 二叉树`、`二叉搜索树 APPLIES_TO 多级索引`、`平衡二叉搜索树 CONTAINS 红黑树` 直接无法生成。v3 用 `unmatched_mentions` 记录了 1~7 条漏抽实体，但它只做记录，不会回补候选池，也不会进入最终结果。

现行方案一次生成实体与关系，模型可以在写关系时自然补齐端点，不存在这个「先冻结、后受限」的损失。

### 3.5 输出上限 6000 偏低，化学章真实发生截断

v3 的 `ENTITY_MAX_OUTPUT_TOKENS = RELATION_MAX_OUTPUT_TOKENS = 6000`，现行是 8192。化学章两次 v3 运行（自带规则、现行规则）都出现 **1/4 分块 `finish_reason=length` 截断**，该分块整块结果作废。v3 的实体阶段输出更长（139 个实体），更容易触发上限。

### 3.6 领域规则包偏薄，且一次只能选一个域

v3 自带规则包普遍只有 200~400 字符：

| 领域包 | 字符数 |
|---|---:|
| general | 45 |
| computer_science | 406 |
| data_structure | 170 |
| complexity | 281 |
| chemistry | 278 |
| physics | 241 |

现行 Prompt 约 10,890 字符，包含各章的分类树、正反例与「历史高频错误禁止清单」。树章同时属于数据结构与算法，v3 只能二选一（`data_structure` 或 `computer_science`），无法像现行 Prompt 一样合并规则。把现行规则完整迁入后，实体 F1 能恢复到 0.85~0.89，但关系 F1 仍只有 0.58~0.65，说明规则内容不是唯一瓶颈。

## 四、v3 中值得保留的设计

1. **`unmatched_mentions`**：显式记录「原文有、候选池没有」的实体，是很好的实体召回诊断信号。现行方案没有这个字段。
2. **实体级 `evidence`**：现行只有关系级 evidence，实体级证据可用于人工审核与融合消歧。
3. **`direction_basis`**：把方向判断结构化（上位/下位、前置/后续、方法/对象），便于审计；实测两套方案方向错误率都是 0，但结构化依据对人工复核有价值。
4. **领域规则分包**：工程上比一个超长 Prompt 更易维护，前提是规则内容完整、支持多域组合。

---

## 五、建议

1. **生产与评测继续使用现行单阶段抽取器**，本次不切换 v3。
2. 若要把 v3 作为下一版候选，至少需要：
   - 输出上限提到 8192，或按实体密度动态调整；
   - 取消「evidence 逐字命中」硬门，改为归一化包含 / 模糊匹配 / 独立校验；
   - 在实体阶段加入与现行同等强度的精度约束，或允许关系阶段把 `unmatched_mentions` 提升为正式端点；
   - 领域规则支持多域组合，并完整迁入现行规则；
   - 重跑四章 Gold，要求关系 F1 不低于现行（≥0.90）再考虑切换。
3. **低成本回灌**：把 `unmatched_mentions` 和实体级 evidence 作为诊断字段加到现行抽取结果里（只记录、不过滤），不改变现有指标。

## 六、复现

沙箱与驱动脚本：

- `backend/scripts/extract_compare/untrusted_v3/extraction.py`（v3 副本，仅改导入）
- `backend/scripts/extract_compare/run_compare.py`（同一文本依次跑两套抽取器，记录 token/调用数）
- `backend/scripts/extract_compare/out/`（预测、原始结果、评分报告、统计 JSON）

命令（`backend/` 目录下）：

```bash
# 主对比：现行 vs v3 自带规则
EXTRACT_CACHE=0 python scripts/extract_compare/run_compare.py \
  --text eval_data/第7章_树.txt --text-id "Hello算法_第7章_树" \
  --out-prefix scripts/extract_compare/out/tree --domain computer_science --temperature 0

# v3 + 现行规则（架构消融）
EXTRACT_CACHE=0 python scripts/extract_compare/run_compare.py \
  --text eval_data/第7章_树.txt --text-id "Hello算法_第7章_树" \
  --out-prefix scripts/extract_compare/out/tree_v3cur --domain computer_science \
  --temperature 0 --only v3 --v3-rules current

# 评分（两套预测各评一次）
python eval_accuracy.py --gold eval_data/gold_第7章_树.json \
  --pred scripts/extract_compare/out/tree_current_pred.json \
  --output scripts/extract_compare/out/tree_current_report.json
```

## 七、局限

1. **单轮单样本**：本次每个配置只跑 1 轮（`temperature=0`）。现行结果与仓库 v1.8 报告（3 轮、`temperature=0.3`）一致或落在其波动范围内（树 0.925 vs 0.866，v1.8 三轮为 0.8493/0.9552/0.7945；复杂度 0.932 vs 0.915；运动学 0.879 vs 0.879；化学 0.890 vs 0.908）。v3 与现行的差距为 0.24~0.56，远超温度/采样波动（v1.8 树章标准差 ±0.0817）。
2. **主场优势**：现行 Prompt 的领域规则是在这四章 Gold 上迭代出来的，本对比对现行有利。但「v3 + 完全相同的现行规则」仍落后 0.24~0.35，说明架构层面的结论在本数据集上成立；**跨领域泛化能力仍未验证**。
3. **OOV 命名差异**：Gold 的实体粒度与命名是人工约定，v3 的部分差异属于约定不一致而非语义错误。但这些名称会直接影响图谱 MERGE 键与用户可见的一致性，因此仍计入真实损失。
4. **未做人工复标**：本次直接使用仓库已有四章人工 Gold，未新建标注集；如需评估 v3 在未见领域上的表现，应另建封存集。
