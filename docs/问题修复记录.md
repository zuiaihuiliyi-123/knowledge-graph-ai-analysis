## 1. 图谱「聚焦节点」调用不存在的 G6 v5 API（`focusItem` → `focusElement`）

- **日期**：2026-09-02
- **阶段**：P6 图谱 UX（前端表现层）
- **涉及文件**：`frontend-vue/src/components/GraphCanvas.vue`

### 现象

教师端「知识点列表 → 图谱定位」以及问答跳转聚焦节点时，浏览器控制台抛运行时错误：

```
TypeError: graph.focusItem is not a function
```

原代码（`GraphCanvas.vue` 的 `focusNode`）写的是：

```js
await graph.focusItem(targetId, { animation: { duration: 300 } })
```

由于 `focusNode` 是异步 fire-and-forget 调用，该异常在**构建期（`vite build`）无法被发现**——构建只做静态编译，不执行运行时逻辑，因此此前「构建通过」掩盖了这处真实 Bug。

### 定位

`@antv/g6` 实际安装的是 **v5**，其运行时 `Graph` 对象提供的方法为 `focusElement`，而非 v4 的 `focusItem`。通过对照类型定义文件 `node_modules/@antv/g6/lib/runtime/graph.d.ts` 确认：

```ts
focusElement(id: ID | ID[], animation?: ViewportAnimationEffectTiming): Promise<void>;
// 无 focusItem 方法
```

同时确认了 v5 的更新类 API（本仓库其他图谱功能依赖）：

| 用途 | 正确 API（v5） |
|------|----------------|
| 聚焦/居中元素 | `graph.focusElement(id, animation)` |
| 更新节点样式 | `graph.updateNodeData(data[])` |
| 更新边样式 | `graph.updateEdgeData(data[])` |
| 全量数据 + 布局 | `graph.setData(data)` + `await graph.render()` |
| 仅重绘（不动布局） | `await graph.draw()` |

### 修复

将 `focusItem` 改为 `focusElement`，并顺带将「聚焦」收敛为一个统一的 `focusNode` / `setFocus` 入口（见 P6 重写）：

```js
await graph.focusElement(String(id), { animation: { duration: 300 } })
```

### 验证

- 对照 G6 v5 官方类型定义（`graph.d.ts`）确认方法名与签名；
- `frontend-vue` 下 `npm run build` 通过（3532 modules，无报错）。

### 结论

这是**真实运行时 Bug**（原实现与 G6 v5 API 不兼容），而非 UI 美化。修复遵循「现象 → 定位（对照类型定义）→ 修复 → 构建验证」的完整链路，作为「使用 AntV G6 做图谱可视化」之外更硬核的工程证据。

## 2. 教师端上传文档时，同一篇文档在列表中重复显示两行

- **日期**：2026-10-01
- **阶段**：教师端课程管理 → 上传并构建知识图谱
- **涉及文件**：`frontend-vue/src/views/TeacherView.vue`（`pollDocuments` / `doUpload`）

### 现象

教师端「课程管理」上传文档并构建知识图谱时，文档列表里会**同时出现两行同名文档**；等解析/抽取结束，其中一行又自己消失了。整个过程没有报错，表头计数（`文档列表（N）`）在此期间比实际文档数多 1。刷新页面后恢复正常，因此只在「上传进行中」这一时间窗内可见。

### 定位

这不是后端插入了重复记录，而是**前端把同一篇文档渲染成了两行**。

先排除后端：`DocumentService.process_upload` 对一次上传只调用一次 `sql_db.create_document`，且 `t_document` 没有任何去重逻辑。若后端真的写了两行，那第二行会持久存在、不会自行消失——与现象不符。

再看前端的两条数据来源：

1. **本地占位行**。上传接口是同步的（解析 + 抽取全部跑完才返回，前端 timeout 设了 600s），请求挂起期间前端拿不到 `document_id`。于是 `doUpload` 先往列表头部插一行本地占位行，让进度条立刻有反馈：

   ```js
   documents.value = [placeholder, ...documents.value]   // doc_id: `local-${Date.now()}`, is_placeholder: true
   ```

2. **后端真实行**。关键点在 `document_service.py` 的步骤顺序：

   ```python
   # 5. 建文档记录（file_path 保存后回填）
   doc_id = sql_db.create_document(...)      # ← 解析【之前】就已入库
   ...
   # 7. 解析（parse_status: UPLOADED -> PARSING -> PARSED/FAILED）
   sql_db.update_document(doc_id, parse_status="PARSING")
   ```

   `t_document` 的默认值是 `parse_status='UPLOADED' / extract_status='PENDING'`，且该行**立刻可被 `list_documents_by_course` 查到**。也就是说，在耗时的解析/抽取全过程中，后端列表里本来就有这一行。

于是轮询 `pollDocuments()` 每 3 秒取回的一次「真实列表」，与列表里遗留的占位行**没有做任何合并**，直接累加：

```js
// 旧代码
const placeholders = documents.value.filter((d) => d.is_placeholder)
documents.value = [...placeholders, ...list]     // 占位行 + 真实行 → 同名两行
```

同一篇文档因此同时渲染两行：顶部是占位行（假进度「解析中 30%」），下方是后端真实行（真实状态）。等上传请求返回，`doUpload` 里的

```js
documents.value = documents.value.filter((d) => d.doc_id !== placeholderId)
```

把占位行滤掉，于是「另一行又消失了」。至此现象完全解释清楚。

**根因是一处错误的注释假设。** 旧代码在该处写着「后端在解析完成前不会返回该记录」——事实恰好相反：后端在**解析之前**就建好了记录，且带 `UPLOADED/PARSING` 状态出现在列表里。这个假设不成立，占位行的存在意义也就只到「后端建档」为止，之后必须让位。

### 修复

把「占位行照留 + 真实行照加」改为**让真实行顶替占位行**——保留占位行在列表顶部的可见位置，但内容与状态换成后端真实行，一篇文档始终只占一行：

```js
const claimed = new Set()
const heads = []
for (const ph of documents.value.filter((d) => d.is_placeholder)) {
  const matchReal = (inFlightOnly) =>
    list.find(
      (r) =>
        !claimed.has(r.doc_id) &&
        isSameDocument(r, ph) &&
        (!inFlightOnly || r.extract_status !== 'COMPLETED'),
    )
  // 优先认领「处理中 / 已失败」的行：同课程里构建完成的同名同大小旧记录不算本次上传
  const real = matchReal(true) || matchReal(false)
  if (real) {
    claimed.add(real.doc_id)
    heads.push(real)   // 真实行接管占位行的位置与进度条，状态以后端为准
  } else {
    heads.push(ph)     // 后端还没建档（大文件上传中），继续用占位行撑住即时反馈
  }
}
documents.value = [...heads, ...list.filter((r) => !claimed.has(r.doc_id))]
```

配套的 `isSameDocument` 用**文件名 + 字节数**判定是否为同一篇文档；二者在两个数据源间必然相等——后端 `file_name` 取的是 basename（`_clean_filename`），与浏览器 `File.name` 相同；`file_size` 是 `len(content)`，与 `File.size` 相同。之所以优先认领「处理中/已失败」的行，是为了避免同课程里**构建完成的同名同大小旧记录**把本次上传的占位行顶掉（那时应继续显示占位行，直到本次的真实行出现）。

同时订正了 `doUpload` 里两处沿用同一错误假设的注释。

### 验证

用一个**只读、不触发真实 LLM、不写数据库**的 Playwright 脚本复现并验证（`%TEMP%/kg_doc_dup_check.js`）。它把两个网络请求拦成可控的：`POST /documents/upload` 扣住不返回（让页面停在出问题的那个窗口），`GET /documents` 放行到真实后端后再追加一行同名的「后端真实行」——精确复刻「占位行还在、真实行已出现」的时序。

| 断言 | 修复前 | 修复后 |
|---|---|---|
| 解析/抽取期间同名文档行数 | **2 行** ✗ | 1 行 ✓ |
| 表头计数（基线 3 篇） | **5** ✗（多出占位行） | 4 ✓ |
| 该行状态来源 | 占位行假进度「解析中」✗ | 后端真实行「抽取中 75%」✓ |
| 构建完成后行数 | 1 行 ✓（正是「另一行消失」） | 1 行 ✓ |
| 全程 JS 运行时错误 | 0 | 0 |

即：**先把修复前的旧逻辑装回去跑一遍，脚本如实报出 2 行 / 表头 5（7/10 通过）**，换回修复后再跑为 **10/10 全部通过**——证明该脚本确实能捕获此缺陷，而非空跑。

其他验证：

- `frontend-vue` 下 `npm run build` 通过（18.42s）。
- 数据零污染：脚本全程只读，结束后 `t_user 12 / t_course 12 / t_document 14 / t_question 6 / t_kp_embedding 276 / t_course_member 20`，与基线逐项一致；e2e 残留 0，模拟行 `doc_id=990001` 未落库。

### 结论

这是一处**真实的前端状态合并缺陷**，由一条与后端实现相反的错误注释假设引入：后端把「建档」放在「解析」之前，前端却按「解析完成才有记录」来设计占位行，于是两者在同一时间窗内各显示一行。修复没有动后端、没有改接口、没有引入去重副作用，只是让前端承认「后端记录出现得更早」这一事实，并据此把两个数据源合并成一行。

> 附注（非本次修复范围）：同一处逻辑还牵出一个潜在问题——`hasInFlightDoc` 判定「进行中」只看 `parse_status ∈ {UPLOADED, PARSING}` 或 `extract_status ∈ {PENDING, EXTRACTING}`，而解析失败时后端只把 `parse_status` 置为 `FAILED`、`extract_status` 仍是默认的 `PENDING`，因此**解析失败后轮询不会自动停止**，会空转到 10 分钟兜底超时。影响仅为多轮询若干次（无副作用），故本次未改。

## 3. 融合「撤销后重新应用」静默失效（`ON CONFLICT DO NOTHING` 撞上已撤销的旧行）

- **日期**：2026-10-01
- **阶段**：文档级知识融合 P2（`services/fusion/` + `core/sql_database.py`）
- **涉及文件**：`backend/app/core/sql_database.py`（`insert_fusion_map`）

### 现象

管理员撤销一条融合之后，再次点「应用融合」：接口返回成功、`applied_count` 也正常，
**但图谱没有任何变化** —— 该映射依然是「已撤销」状态，读图时不会折叠。

### 定位

融合映射表 `t_kp_fusion_map` 上有一条 `UNIQUE(course_id, document_id, source_kp_id)`，
用来保证「一个源最多折到一个目标」（目标唯一）。写入用的是：

```sql
INSERT INTO t_kp_fusion_map (...) VALUES (...)
ON CONFLICT(course_id, document_id, source_kp_id) DO NOTHING
```

本意是让「重复应用同一个决策」幂等。问题在于**撤销并不删行**（这是刻意的：撤销只把
`status` 改成 `REVOKED`，以便保留历史与审计）。于是那一行仍然占着 UNIQUE 槽位，
新的插入被判为冲突 → `DO NOTHING` → `rowcount = 0`。

而调用方只判断了「有没有抛异常」，没判断「插入是否真的生效」，于是这条静默失败
被包装成了成功响应。

### 修复

把冲突分支改成**只对已撤销的行生效**的复活逻辑：

```sql
ON CONFLICT(course_id, document_id, source_kp_id) DO UPDATE SET
    target_kp_id = excluded.target_kp_id,
    ... (快照与本次运行信息一并更新) ...,
    status = 'ACTIVE', revoked_at = NULL, revoked_by = NULL
WHERE t_kp_fusion_map.status = 'REVOKED'
```

- 行仍是 `ACTIVE`（同一源重复 apply）时 `WHERE` 不成立 → 依旧零副作用，幂等性不变；
- 行是 `REVOKED` 时被复活，并沿用原 `fusion_id`（历史操作记录由 `t_kp_fusion_run` 与审计日志承担）。

顺带修掉一个隐患：`cursor.lastrowid` 在 **UPDATE** 路径下不会更新，原先用它当返回值会拿到陈旧值；
改为写入后回查一次 `fusion_id`。

### 验证

`test_fusion_chain_revert.py` 的 Step 4「撤销后重新应用，结果必须与首次一致」直接覆盖该路径；
`test_fusion_idempotency_undo.py` 另加了「复活后不新增行、`revoked_at` 被清空、图谱与首次一致」四条断言。
修复前该断言报「图谱与首次不一致」，修复后通过。

## 4. 两个会清空真实数据的测试脚本（其中一次已造成事故）

- **日期**：2026-10-01
- **阶段**：回归验证过程中的发现
- **涉及文件**：`backend/test_upload_flow.py`、`backend/test_courses_crud.py`

### 现象

按仓库惯例在 `backend/` 下跑一遍 `test_*.py` 做回归。跑了 9 个脚本之后，
Neo4j 里的 `KnowledgePoint` 节点数从 **626 变成了 0**（`MATCH (n) RETURN count(n)` = 0），
而所有脚本看起来只是"有几个用例没过"。

### 定位

两个脚本在**任何断言之前**就执行了破坏性清理，且都不局限于自己的测试数据：

| 文件 | 位置 | 破坏性代码 |
|---|---|---|
| `test_upload_flow.py` | 第 32 行 | `db.query("MATCH (n) DETACH DELETE n")` —— **Neo4j 全库清空** |
| `test_courses_crud.py` | 第 25-29 行 | 同上，**并且**对线上 `app.db` 执行 `DELETE FROM t_learning_record / t_document / t_course` |

**为什么长期没被发现**：`test_upload_flow.py` 写于「上传会自动建课」的年代，
调用的是 `process_upload(course_name=...)`；而当前契约是
`process_upload(content, filename, course_id, teacher_id)`（Phase 5 起必须指定已存在课程）。
它的**第一句业务调用**就会抛 `TypeError`，所以这个脚本"本来就跑不通"——
而那句全库清空恰恰排在它**前面**，于是每次运行都静默地清一次图，只留下一个看似无关的 TypeError。

`test_courses_crud.py` 更危险：它连线上 SQLite 一起清。

### 修复

拆除两处破坏性代码，只做最小安全改动、不改业务逻辑：

- `test_upload_flow.py`：全库删除改为只清本脚本自建的测试课程
  （`MATCH (n:KnowledgePoint {course_id: $cid}) DETACH DELETE n`），并在文件头写明
  该脚本已过时、需要按当前契约重写，以及这次事故的来龙去脉。
- `test_courses_crud.py`：Neo4j 全局删除**移除**（课程 CRUD 断言用的是新建课程自己的统计，
  本来就不需要清空图库）；SQLite 的清理改为在 `app.db` 的**临时副本**上执行，
  并在 `finally` 里把单例指回线上库。

### 数据恢复

被清空的图谱按用户决定，用项目自带的 `scripts/rebuild_missing_graphs.py --yes` 恢复
（该脚本的 docstring 正是为「记录说抽取完成、图里却没有节点」这一场景写的）。

**14/14 篇文档重建成功，恢复 451 节点 / 339 关系**（清空前为 626 / 655）。
差额来自重抽取的随机性与分块差异——**这是一次有损恢复，不是逐字还原**。
SQLite 业务数据（用户 / 课程 / 文档 / 题目 / 学习记录 / 收藏 / 成员）全程与基线逐项一致。

### 结论

这是**测试脚本本身的真实缺陷**，且属于最危险的一类：破坏性操作排在断言之前，
脚本又因年代久远而必然报错，于是一次次地清掉真实数据而无人察觉。
修复遵循「现象 → 定位（逐条核对每个脚本的清理范围）→ 最小修复 → 恢复数据 → 验证」的完整链路。

> 附注（未改，属既有状态）：`test_permission_matrix.py` 有一条断言硬编码 `document_id=4`，
> 而课程 5 现在的文档是 100/128，文档 4 不存在，该断言恒失败；`test_graph_edit.py` 同样依赖
> 课程 5 的旧文档号而无法执行。两者都与本轮改动无关，未在本次修复。
