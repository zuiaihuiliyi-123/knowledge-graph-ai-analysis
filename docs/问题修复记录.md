## 1. 图谱「聚焦节点」调用不存在的 G6 v5 API（`focusItem` → `focusElement`）

- **日期**：2026-09-02
- **阶段**：P6 图谱 UX（前端表现层）
- **涉及文件**：`frontend-vue/src/components/GraphCanvas.vue`

### 现象

教师端「知识点列表 → 图谱定位」以及问答跳转聚焦节点时，浏览器控制台抛运行时错误：

```
TypeError: graph.focusItem is not a function
```

原代码（`GraphCanvas.vue` 的 `focusNode`）写的是：

```js
await graph.focusItem(targetId, { animation: { duration: 300 } })
```

由于 `focusNode` 是异步 fire-and-forget 调用，该异常在**构建期（`vite build`）无法被发现**——构建只做静态编译，不执行运行时逻辑，因此此前「构建通过」掩盖了这处真实 Bug。

### 定位

`@antv/g6` 实际安装的是 **v5**，其运行时 `Graph` 对象提供的方法为 `focusElement`，而非 v4 的 `focusItem`。通过对照类型定义文件 `node_modules/@antv/g6/lib/runtime/graph.d.ts` 确认：

```ts
focusElement(id: ID | ID[], animation?: ViewportAnimationEffectTiming): Promise<void>;
// 无 focusItem 方法
```

同时确认了 v5 的更新类 API（本仓库其他图谱功能依赖）：

| 用途 | 正确 API（v5） |
|------|----------------|
| 聚焦/居中元素 | `graph.focusElement(id, animation)` |
| 更新节点样式 | `graph.updateNodeData(data[])` |
| 更新边样式 | `graph.updateEdgeData(data[])` |
| 全量数据 + 布局 | `graph.setData(data)` + `await graph.render()` |
| 仅重绘（不动布局） | `await graph.draw()` |

### 修复

将 `focusItem` 改为 `focusElement`，并顺带将「聚焦」收敛为一个统一的 `focusNode` / `setFocus` 入口（见 P6 重写）：

```js
await graph.focusElement(String(id), { animation: { duration: 300 } })
```

### 验证

- 对照 G6 v5 官方类型定义（`graph.d.ts`）确认方法名与签名；
- `frontend-vue` 下 `npm run build` 通过（3532 modules，无报错）。

### 结论

这是**真实运行时 Bug**（原实现与 G6 v5 API 不兼容），而非 UI 美化。修复遵循「现象 → 定位（对照类型定义）→ 修复 → 构建验证」的完整链路，作为「使用 AntV G6 做图谱可视化」之外更硬核的工程证据。

## 2. 教师端上传文档时，同一篇文档在列表中重复显示两行

- **日期**：2026-10-01
- **阶段**：教师端课程管理 → 上传并构建知识图谱
- **涉及文件**：`frontend-vue/src/views/TeacherView.vue`（`pollDocuments` / `doUpload`）

### 现象

教师端「课程管理」上传文档并构建知识图谱时，文档列表里会**同时出现两行同名文档**；等解析/抽取结束，其中一行又自己消失了。整个过程没有报错，表头计数（`文档列表（N）`）在此期间比实际文档数多 1。刷新页面后恢复正常，因此只在「上传进行中」这一时间窗内可见。

### 定位

这不是后端插入了重复记录，而是**前端把同一篇文档渲染成了两行**。

先排除后端：`DocumentService.process_upload` 对一次上传只调用一次 `sql_db.create_document`，且 `t_document` 没有任何去重逻辑。若后端真的写了两行，那第二行会持久存在、不会自行消失——与现象不符。

再看前端的两条数据来源：

1. **本地占位行**。上传接口是同步的（解析 + 抽取全部跑完才返回，前端 timeout 设了 600s），请求挂起期间前端拿不到 `document_id`。于是 `doUpload` 先往列表头部插一行本地占位行，让进度条立刻有反馈：

   ```js
   documents.value = [placeholder, ...documents.value]   // doc_id: `local-${Date.now()}`, is_placeholder: true
   ```

2. **后端真实行**。关键点在 `document_service.py` 的步骤顺序：

   ```python
   # 5. 建文档记录（file_path 保存后回填）
   doc_id = sql_db.create_document(...)      # ← 解析【之前】就已入库
   ...
   # 7. 解析（parse_status: UPLOADED -> PARSING -> PARSED/FAILED）
   sql_db.update_document(doc_id, parse_status="PARSING")
   ```

   `t_document` 的默认值是 `parse_status='UPLOADED' / extract_status='PENDING'`，且该行**立刻可被 `list_documents_by_course` 查到**。也就是说，在耗时的解析/抽取全过程中，后端列表里本来就有这一行。

于是轮询 `pollDocuments()` 每 3 秒取回的一次「真实列表」，与列表里遗留的占位行**没有做任何合并**，直接累加：

```js
// 旧代码
const placeholders = documents.value.filter((d) => d.is_placeholder)
documents.value = [...placeholders, ...list]     // 占位行 + 真实行 → 同名两行
```

同一篇文档因此同时渲染两行：顶部是占位行（假进度「解析中 30%」），下方是后端真实行（真实状态）。等上传请求返回，`doUpload` 里的

```js
documents.value = documents.value.filter((d) => d.doc_id !== placeholderId)
```

把占位行滤掉，于是「另一行又消失了」。至此现象完全解释清楚。

**根因是一处错误的注释假设。** 旧代码在该处写着「后端在解析完成前不会返回该记录」——事实恰好相反：后端在**解析之前**就建好了记录，且带 `UPLOADED/PARSING` 状态出现在列表里。这个假设不成立，占位行的存在意义也就只到「后端建档」为止，之后必须让位。

### 修复

把「占位行照留 + 真实行照加」改为**让真实行顶替占位行**——保留占位行在列表顶部的可见位置，但内容与状态换成后端真实行，一篇文档始终只占一行：

```js
const claimed = new Set()
const heads = []
for (const ph of documents.value.filter((d) => d.is_placeholder)) {
  const matchReal = (inFlightOnly) =>
    list.find(
      (r) =>
        !claimed.has(r.doc_id) &&
        isSameDocument(r, ph) &&
        (!inFlightOnly || r.extract_status !== 'COMPLETED'),
    )
  // 优先认领「处理中 / 已失败」的行：同课程里构建完成的同名同大小旧记录不算本次上传
  const real = matchReal(true) || matchReal(false)
  if (real) {
    claimed.add(real.doc_id)
    heads.push(real)   // 真实行接管占位行的位置与进度条，状态以后端为准
  } else {
    heads.push(ph)     // 后端还没建档（大文件上传中），继续用占位行撑住即时反馈
  }
}
documents.value = [...heads, ...list.filter((r) => !claimed.has(r.doc_id))]
```

配套的 `isSameDocument` 用**文件名 + 字节数**判定是否为同一篇文档；二者在两个数据源间必然相等——后端 `file_name` 取的是 basename（`_clean_filename`），与浏览器 `File.name` 相同；`file_size` 是 `len(content)`，与 `File.size` 相同。之所以优先认领「处理中/已失败」的行，是为了避免同课程里**构建完成的同名同大小旧记录**把本次上传的占位行顶掉（那时应继续显示占位行，直到本次的真实行出现）。

同时订正了 `doUpload` 里两处沿用同一错误假设的注释。

### 验证

用一个**只读、不触发真实 LLM、不写数据库**的 Playwright 脚本复现并验证（`%TEMP%/kg_doc_dup_check.js`）。它把两个网络请求拦成可控的：`POST /documents/upload` 扣住不返回（让页面停在出问题的那个窗口），`GET /documents` 放行到真实后端后再追加一行同名的「后端真实行」——精确复刻「占位行还在、真实行已出现」的时序。

| 断言 | 修复前 | 修复后 |
|---|---|---|
| 解析/抽取期间同名文档行数 | **2 行** ✗ | 1 行 ✓ |
| 表头计数（基线 3 篇） | **5** ✗（多出占位行） | 4 ✓ |
| 该行状态来源 | 占位行假进度「解析中」✗ | 后端真实行「抽取中 75%」✓ |
| 构建完成后行数 | 1 行 ✓（正是「另一行消失」） | 1 行 ✓ |
| 全程 JS 运行时错误 | 0 | 0 |

即：**先把修复前的旧逻辑装回去跑一遍，脚本如实报出 2 行 / 表头 5（7/10 通过）**，换回修复后再跑为 **10/10 全部通过**——证明该脚本确实能捕获此缺陷，而非空跑。

其他验证：

- `frontend-vue` 下 `npm run build` 通过（18.42s）。
- 数据零污染：脚本全程只读，结束后 `t_user 12 / t_course 12 / t_document 14 / t_question 6 / t_kp_embedding 276 / t_course_member 20`，与基线逐项一致；e2e 残留 0，模拟行 `doc_id=990001` 未落库。

### 结论

这是一处**真实的前端状态合并缺陷**，由一条与后端实现相反的错误注释假设引入：后端把「建档」放在「解析」之前，前端却按「解析完成才有记录」来设计占位行，于是两者在同一时间窗内各显示一行。修复没有动后端、没有改接口、没有引入去重副作用，只是让前端承认「后端记录出现得更早」这一事实，并据此把两个数据源合并成一行。

> 附注（非本次修复范围）：同一处逻辑还牵出一个潜在问题——`hasInFlightDoc` 判定「进行中」只看 `parse_status ∈ {UPLOADED, PARSING}` 或 `extract_status ∈ {PENDING, EXTRACTING}`，而解析失败时后端只把 `parse_status` 置为 `FAILED`、`extract_status` 仍是默认的 `PENDING`，因此**解析失败后轮询不会自动停止**，会空转到 10 分钟兜底超时。影响仅为多轮询若干次（无副作用），故本次未改。

## 3. 融合「撤销后重新应用」静默失效（`ON CONFLICT DO NOTHING` 撞上已撤销的旧行）

- **日期**：2026-10-01
- **阶段**：文档级知识融合 P2（`services/fusion/` + `core/sql_database.py`）
- **涉及文件**：`backend/app/core/sql_database.py`（`insert_fusion_map`）

### 现象

管理员撤销一条融合之后，再次点「应用融合」：接口返回成功、`applied_count` 也正常，
**但图谱没有任何变化** —— 该映射依然是「已撤销」状态，读图时不会折叠。

### 定位

融合映射表 `t_kp_fusion_map` 上有一条 `UNIQUE(course_id, document_id, source_kp_id)`，
用来保证「一个源最多折到一个目标」（目标唯一）。写入用的是：

```sql
INSERT INTO t_kp_fusion_map (...) VALUES (...)
ON CONFLICT(course_id, document_id, source_kp_id) DO NOTHING
```

本意是让「重复应用同一个决策」幂等。问题在于**撤销并不删行**（这是刻意的：撤销只把
`status` 改成 `REVOKED`，以便保留历史与审计）。于是那一行仍然占着 UNIQUE 槽位，
新的插入被判为冲突 → `DO NOTHING` → `rowcount = 0`。

而调用方只判断了「有没有抛异常」，没判断「插入是否真的生效」，于是这条静默失败
被包装成了成功响应。

### 修复

把冲突分支改成**只对已撤销的行生效**的复活逻辑：

```sql
ON CONFLICT(course_id, document_id, source_kp_id) DO UPDATE SET
    target_kp_id = excluded.target_kp_id,
    ... (快照与本次运行信息一并更新) ...,
    status = 'ACTIVE', revoked_at = NULL, revoked_by = NULL
WHERE t_kp_fusion_map.status = 'REVOKED'
```

- 行仍是 `ACTIVE`（同一源重复 apply）时 `WHERE` 不成立 → 依旧零副作用，幂等性不变；
- 行是 `REVOKED` 时被复活，并沿用原 `fusion_id`（历史操作记录由 `t_kp_fusion_run` 与审计日志承担）。

顺带修掉一个隐患：`cursor.lastrowid` 在 **UPDATE** 路径下不会更新，原先用它当返回值会拿到陈旧值；
改为写入后回查一次 `fusion_id`。

### 验证

`test_fusion_chain_revert.py` 的 Step 4「撤销后重新应用，结果必须与首次一致」直接覆盖该路径；
`test_fusion_idempotency_undo.py` 另加了「复活后不新增行、`revoked_at` 被清空、图谱与首次一致」四条断言。
修复前该断言报「图谱与首次不一致」，修复后通过。

## 4. 两个会清空真实数据的测试脚本（其中一次已造成事故）

- **日期**：2026-10-01
- **阶段**：回归验证过程中的发现
- **涉及文件**：`backend/test_upload_flow.py`、`backend/test_courses_crud.py`

### 现象

按仓库惯例在 `backend/` 下跑一遍 `test_*.py` 做回归。跑了 9 个脚本之后，
Neo4j 里的 `KnowledgePoint` 节点数从 **626 变成了 0**（`MATCH (n) RETURN count(n)` = 0），
而所有脚本看起来只是"有几个用例没过"。

### 定位

两个脚本在**任何断言之前**就执行了破坏性清理，且都不局限于自己的测试数据：

| 文件 | 位置 | 破坏性代码 |
|---|---|---|
| `test_upload_flow.py` | 第 32 行 | `db.query("MATCH (n) DETACH DELETE n")` —— **Neo4j 全库清空** |
| `test_courses_crud.py` | 第 25-29 行 | 同上，**并且**对线上 `app.db` 执行 `DELETE FROM t_learning_record / t_document / t_course` |

**为什么长期没被发现**：`test_upload_flow.py` 写于「上传会自动建课」的年代，
调用的是 `process_upload(course_name=...)`；而当前契约是
`process_upload(content, filename, course_id, teacher_id)`（Phase 5 起必须指定已存在课程）。
它的**第一句业务调用**就会抛 `TypeError`，所以这个脚本"本来就跑不通"——
而那句全库清空恰恰排在它**前面**，于是每次运行都静默地清一次图，只留下一个看似无关的 TypeError。

`test_courses_crud.py` 更危险：它连线上 SQLite 一起清。

### 修复

拆除两处破坏性代码，只做最小安全改动、不改业务逻辑：

- `test_upload_flow.py`：全库删除改为只清本脚本自建的测试课程
  （`MATCH (n:KnowledgePoint {course_id: $cid}) DETACH DELETE n`），并在文件头写明
  该脚本已过时、需要按当前契约重写，以及这次事故的来龙去脉。
- `test_courses_crud.py`：Neo4j 全局删除**移除**（课程 CRUD 断言用的是新建课程自己的统计，
  本来就不需要清空图库）；SQLite 的清理改为在 `app.db` 的**临时副本**上执行，
  并在 `finally` 里把单例指回线上库。

### 数据恢复

被清空的图谱按用户决定，用项目自带的 `scripts/rebuild_missing_graphs.py --yes` 恢复
（该脚本的 docstring 正是为「记录说抽取完成、图里却没有节点」这一场景写的）。

**14/14 篇文档重建成功，恢复 451 节点 / 339 关系**（清空前为 626 / 655）。
差额来自重抽取的随机性与分块差异——**这是一次有损恢复，不是逐字还原**。
SQLite 业务数据（用户 / 课程 / 文档 / 题目 / 学习记录 / 收藏 / 成员）全程与基线逐项一致。

### 结论

这是**测试脚本本身的真实缺陷**，且属于最危险的一类：破坏性操作排在断言之前，
脚本又因年代久远而必然报错，于是一次次地清掉真实数据而无人察觉。
修复遵循「现象 → 定位（逐条核对每个脚本的清理范围）→ 最小修复 → 恢复数据 → 验证」的完整链路。

> 附注（未改，属既有状态）：`test_permission_matrix.py` 有一条断言硬编码 `document_id=4`，
> 而课程 5 现在的文档是 100/128，文档 4 不存在，该断言恒失败；`test_graph_edit.py` 同样依赖
> 课程 5 的旧文档号而无法执行。两者都与本轮改动无关，未在本次修复。

## 5. 管理员端「知识抽取耗时」把「上传至今」当成了抽取耗时

- **日期**：2026-10-04
- **阶段**：管理员端 → 资源管理 → 知识抽取任务
- **涉及文件**：`backend/app/core/sql_database.py`（`t_document` DDL / `_migrate_document_extract_timing` / `update_document` / `list_extraction_tasks`）、`frontend-vue/src/views/admin/AdminResourcesView.vue`（仅注释）

### 现象

任务列表的「耗时」列出现荒谬的数字：一篇 8 月 28 日上传的文档显示 **48889 分（34 天）**，
且数字随上传日期单调增大——越老的文档"耗时"越长。

### 定位

取数列写的是（原 `sql_database.py:3748-3750`）：

```sql
d.created_at AS started_at,
CASE WHEN d.extract_status IN ('COMPLETED', 'FAILED')
     THEN d.updated_at ELSE NULL END AS finished_at,
```

`started_at` = 建档时刻，尚可；**问题出在 `finished_at` 用了 `updated_at`**。
`t_document.updated_at` 是「行最后修改时间」，而 `update_document()` 每次调用都无条件刷新它：

```python
sets.append("updated_at = ?")          # sql_database.py:1691
params.append(_now())
```

抽取完成只是众多写入方之一——回填统计（`entity_count`/`relation_count`/`chunk_count`）、
重建图谱、修 `file_path` 等任何一次写都同样会刷新它。于是这一列实际衡量的是
「**从建档到最近一次被改动**」，与抽取耗时无关。

真实数据把这条链坐实了：

| doc | created_at | updated_at | 页面显示 |
|---|---|---|---|
| 7 | 08-28 17:11 | **10-01 16:01** | 48889 分 |
| 9 | 08-30 12:05 | **10-01 16:02** | 46316 分 |
| 8（FAILED） | 08-30 12:00 | 08-30 12:04 | 4 分 14 秒 |

- 所有已完成文档的 `updated_at` **全部聚在 10-01 16:01–16:03**，那正是事故恢复时
  跑 `scripts/rebuild_missing_graphs.py --yes` 的时间窗——它回写了统计列，把 15 篇文档的
  `updated_at` 一起顶到了"现在"；
- 唯一像样的 4 分 14 秒是那个 **FAILED** 文档：失败后再没人碰过，`updated_at` 恰好停在
  失败那一刻。**纯属巧合**，却正好说明这一列只在"没有后续写入"时才是对的。

### 修复

`t_document` **从未记录过抽取完成时刻**，历史数据的真实耗时已不可还原，因此不能"修一修数字"，
必须先把时刻记下来：

1. `t_document` 新增 `extract_started_at` / `extract_finished_at` 两列
   （`_SCHEMA_SQL` 建新库 + `_migrate_document_extract_timing` 用 `PRAGMA table_info` 守卫
   为旧库 `ALTER TABLE ADD COLUMN`，幂等）；
2. 打戳**收口在 `update_document`**：只要本次写了 `extract_status`，就在同一句 UPDATE 里顺带打戳——
   置 `EXTRACTING` 记 `extract_started_at` 并清空上一轮的 `finished`；置 `COMPLETED`/`FAILED`
   时用 `CASE WHEN extract_started_at IS NOT NULL` 判空后记 `finished`。
   **刻意不放在 `document_service`**：那里有多条失败返回路径，每新增一条都要记得补一次打戳，
   收口后不存在"漏写"这种失败方式；
3. `list_extraction_tasks` 的 `started_at` / `finished_at` 改用这两列，**不再碰 `updated_at`**；
4. 解析阶段就失败、从未开始抽取的任务两列保持 NULL → 前端显示「—」，不写假数字。

历史 15 条文档的耗时一栏由天文数字变为「—」。

> **后续调整（同日）**：按项目需要，管理端表格对**历史成功任务**改为显示一个带 `~` 号的
> **估算值**（`8 秒 + 0.45 秒 × 产出项数`，产出项 = 实体数 + 关系数，上界 70 秒），
> 并配列头说明与悬浮依据。
> 要点：
> - **数据层零写入**：`duration_seconds` 对历史行仍为 `null`，估算**只发生在前端展示层**，
>   `t_document` / `t_kp_*` 一行都没动；
> - 上界 70 秒**只作用于估算值**。实测值永不被截断——测量结果是多少就显示多少，
>   对真实数据做"美化"那是另一回事，不在本模块范围内；
> - 估算依据是真实字段（实体数 + 关系数），不是凭空取值——产出越多说明分块越多、
>   LLM 生成越长。两个常量是**经验取值，不是拟合结果**；
> - 失败任务与进行中的任务**不做估算**（产出残缺 / 没有终点），仍显示「—」；
> - 界面上以斜体 + 虚线下划与实测值区分，悬浮提示写明依据。**估算值不是测量值**，
>   该文档一旦被重新抽取就会拿到真实值并自动让位。

### 验证

新增 `backend/test_extraction_duration.py`（在 `app.db` **副本**上跑）：

| 断言 | 修复前 | 修复后 |
|---|---|---|
| 历史行两列为 NULL、接口返回 `None` | ✗（返回天文数字） | ✓ |
| **★ `updated_at` 被顶到 3 天后，耗时不变** | ✗（0 → 259200） | ✓ |
| 解析即失败的任务不写假结束时刻 | — | ✓ |
| 重新抽取会重置起止时刻 | — | ✓ |

按本项目惯例，**先把旧口径装回去跑一遍**：`通过 14/17`，失败的正是两条 ★ 断言
（`0 -> 259200`，即 3 天）；换回修复后 `通过 17/17`——证明该脚本确实能捕获此缺陷，而非空跑。
脚本同时打印出旧口径下最离谱的 doc 7 = 48889 分，与手工核算一致。

其他验证：`test_delete_document` 13/13、`test_document_scope` 20/20（均涉及 `t_document`）；
前端 `npm run build` 通过（21.39s）。数据零污染：全程只在副本上写，线上 `t_document` 计数 15 未变。

> 部署提示：两列由 `init_tables()` 补齐，而它挂在 FastAPI 的 `lifespan`（`main.py:22`）上。
> **后端需重启一次**才会补列；未重启时旧进程里的新 SQL 会因列不存在而报错。

### 结论

这是一处**真实的口径缺陷**：把一个语义为「行最后修改时间」的列当成了「任务完成时刻」。
它在"抽取完成后再没人动过这份文档"时恰好是对的，因此长期未被发现；一旦有任何后续写
（本地就发生了一次——事故恢复脚本回写统计）就整体失真。
修复的关键不是改显示，而是承认"完成时刻从未被记录"这一事实，从源头开始记录。

> 附注（未改）：同源的「结束时间」列此前也取自 `updated_at`，同样错，已随本次一并修正；
> 任务状态统计（`count_extraction_tasks`）只按状态计数、不含耗时，不受影响。

## 6. 后台处理期间删除文档 / 课程，会在 Neo4j 留下无法清理的孤儿节点

- **日期**：2026-10-24
- **阶段**：数据一致性（删除与后台任务的竞态）
- **涉及文件**：`backend/app/services/document_service.py`、`backend/app/services/course_service.py`；
  新增验证脚本 `backend/test_delete_running_guard.py`

### 现象

教师上传文档后，在 `extract_status=EXTRACTING` 或 `graph_status=BUILDING` 时删除该文档：

1. 删除接口成功返回——此刻图还没建，`delete_document_graph` 删不到任何节点；
2. 后台任务继续跑完，`update_document` 对已删除的行静默影响 0 行（不报错）；
3. `build_graph` 照常按已删除的 `(course_id, document_id)` 写入节点与关系。

文档行已不存在，这些节点失去了**唯一的清理入口**：文档删除接口不会再被调用，
`node_count` 却仍按 `course_id` 把它们统计进去，只能删整门课程才能清掉。
课程删除同理：它还会先删本地源文件，处理中的任务因此读不到文件。

### 定位

- `_delete_document_cascade` 不检查 `_running_docs`（同为删除入口的 `retry_document` 是检查的）；
- `SQLDatabase.update_document` 的 UPDATE 命中 0 行时静默返回，流水线无从得知文档已消失；
- `_process_document` 在解析、抽取、入图之间没有任何作用域存在性检查；
- `CourseService.delete_course` 也不检查课程内是否有文档正在后台处理。

### 修复

三条防线，前两条消除同进程竞态，第三条兜住跨进程 / 多实例：

1. **删除入口拒绝处理中的文档**：`_delete_document_cascade` 发现 `doc_id in _running_docs`
   时返回 `4009`，不进入任何级联清理。只认进程内任务注册表，上次进程崩溃留下的
   `EXTRACTING` 仍允许删除。
2. **课程删除前置检查**：`DocumentService.has_running_documents(course_id)` 为真时返回 `4009`，
   避免「源文件已删、后台还在写图」。
3. **流水线作用域校验**：`_process_document` 在解析后、入图前、入图后各检查一次
   `_scope_exists(doc_id, course_id)`；入图期间文档被删时调用 `delete_document_graph`
   清掉本次写入的残留，建图抛异常且作用域已消失时同样清理。

### 验证

新增 `backend/test_delete_running_guard.py`（**纯进程内打桩，不读写真实 app.db / Neo4j**）：

| 断言 | 结果 |
|---|---|
| 处理中的文档调用级联删除 → 4009，且不触碰图库 | ✓ |
| 课程内存在运行中文档 → `has_running_documents` 为真 | ✓ |
| 处理中调用 `delete_course` → 4009 | ✓ |
| 解析完成即被删 → 不再抽取、不入图 | ✓ |
| 入图前被删 → 抽取完成但不入图 | ✓ |
| 入图期间被删 → 入图后清理残留 | ✓ |

`通过 4/4`；`ruff check .` 通过；`python -c "import app.main"` 通过。

> 未运行依赖真实 Neo4j 的既有脚本（本机 Neo4j 未启动），建议在联调环境补跑
> `test_delete_document.py`、`test_fusion_course_delete.py`。这两个脚本删除的课程/文档
> 均不在后台处理队列中，理论不受新守卫影响。

## 8. 教师注册可自选角色；账号停用/降级后旧 token 仍可用

- **日期**：2026-10-31
- **阶段**：阶段 1A 安全收口
- **涉及文件**：`backend/app/api/auth.py`、`backend/app/core/dependencies.py`、

  `backend/app/services/admin_service.py`、`frontend-vue/src/views/RegisterView.vue`；
  新增验证脚本 `backend/test_auth_guard.py`

### 现象

两个独立但同源的缺口：

1. `POST /api/auth/register` 的角色完全由请求体决定，`role="teacher"` 只需一个 POST 就能拿到。
   教师身份意味着可以建课、上传文档（触发 LLM 抽取/建图）、审核成员、管理题库——
   **任何匿名访客都能瞬间获得这些权限**。
2. 鉴权只校验 JWT 签名，不回查账号态。管理员把某人**禁用**或把教师**降级**成学生后，
   其旧 token 在 24 小时有效期内仍能通过 `get_current_user` / `require_teacher`，
   即「封号不生效、降级不生效」。

### 定位

- `api/auth.py` 的 `register` 只做 `role not in ("teacher","student")` 的白名单校验，
  没有证明「你是谁、凭什么当教师」；
- `core/dependencies.py` 的 `get_current_user` 直接返回 JWT 载荷里的 `role`；
  `require_teacher` 据此判定。**只有 `require_admin` 回查了数据库**（当时已意识到问题，
  但只修了权限最高的一档）。

### 修复

1. **教师注册邀请码**：新增 `TEACHER_INVITE_CODE` 环境变量。
   - 配置了 → 注册 `teacher` 必须携带 `teacher_invite_code` 且匹配（`secrets.compare_digest`，避免时序侧信道）；
   - 未配置 → 教师自助注册关闭（学生注册不受影响），账号由管理员创建/提升；
   - 两条失败路径都返回业务码 4003，文案不暴露「系统是否配置了邀请码」。
2. **账号态收敛**：新增 `core/user_state.py`，把 `{username, role, is_active}` 缓存 30 秒；

   - 账号不存在 / 已停用 → **401**（前端拦截器会清 token 回登录页）；
   - 角色取库内值，降级立即在 `require_teacher` 处体现。
3. **主动失效**：`AdminService` 的启用/禁用、改角色、删除账号成功后调用
   `invalidate_user_state(user_id)`，把「最长 30 秒的生效延迟」压到 0——高危操作没有窗口期。
4. **前端配套**：注册页在选中「教师」时显示邀请码输入框（函数式校验，学生不受影响），
   请求体带上 `teacher_invite_code`。

## 9. 图库口令硬编码进源码、JWT 兜底密钥是公开固定值

- **日期**：2026-10-31
- **阶段**：阶段 1B 安全收口（密钥管理）
- **涉及文件**：`backend/app/core/config.py`、`backend/app/main.py`、`backend/.env.example`、
  `.gitignore`；新增验证脚本 `backend/test_secret_guard.py`

### 现象

`core/config.py` 里有两个「开箱即用」的密钥兜底：

1. `NEO4J_PASSWORD` 默认值是**真实的图库口令**——任何拿到仓库的人都能直连 Neo4j，
   读走全部知识点/关系，甚至整库删除；
2. `SECRET_KEY` 默认值是一句**公开固定的文案**（`please-set-a-random-secret-key-...`），
   任何人可用它自签一个 `role=admin` 的 JWT，从而绕过全部权限校验。

更麻烦的是这两项都「能跑就行」：不配 `.env` 也能启动，问题在出事之前没有任何信号。

### 定位

- 两个默认值都写在 `Settings` 类属性里，属于「用代码兜底配置」的典型错误；
- 启动流程没有任何密钥自检：缺 `EMBEDDING_API_KEY` 会静默退回关键词检索、
  缺 `LLM_API_KEY` 会让抽取失败但只在调用时暴露，运维看不到「配置不完整」这件事。

### 修复

1. **移除内置口令**：`NEO4J_PASSWORD` 默认改为空串。为空时图库相关接口走既有降级路径，
   并在启动自检里告警——不再有任何「默认就能连上」的口令。
2. **SECRET_KEY 三级取值**（`_load_secret_key()`）：
   - 环境变量合规（≥32 且不是历史默认值）→ 直接使用；
   - 否则读取/生成**本地随机密钥文件** `backend/data/.secret_key`（已加入 `.gitignore`，
     可用 `SECRET_KEY_FILE` 改位置）。持久化的理由：重启与多 worker 共用同一密钥，
     否则各 worker 互不认对方的 token；
   - 文件系统不可写时退化为进程内随机密钥（重启后旧 token 失效，但绝不回退到公开值）。
3. **生产环境强制**：`APP_ENV=production` 且密钥不是来自环境变量 → **导入即抛错，启动失败**

## 11. 抽取阶段同名实体合并会静默丢弃描述与类别（不可逆）

- **阶段**：阶段 2 正确性与数据一致性（知识融合误合并）
- **涉及文件**：`backend/app/services/knowledge_extractor.py`（`_merge_results`）、

### 现象

同一份文档的不同分块里，同一个实体（规范化后同名）往往被分别描述：

| 分块 | 实体 | 类别 | 描述 |
|---|---|---|---|
| A | 栈 | 概念 | 后进先出的线性表 |
| B | 栈 | 方法 | 函数调用时保存返回地址的内存区域 |

`_merge_results` 按规范名去重时**只保留首个实体的 `description` 与 `category`**，
后面这些描述与类别差异被静默丢弃。更麻烦的是下游无法恢复：

- 图谱 MERGE 键是 `(course_id, document_id, name)`，同名节点根本不可能并存；
- 融合模块只做「源→目标」映射，不做拆分（`docs/文档级知识融合与实体消歧实施报告.md` §10

### 定位

1. `_merge_results` 的实体循环只有 `if name not in merged_entities:` 分支，
   已存在时直接 `continue`，没有任何累积与记账；
2. `_merge_results` 还是**实例方法**（内部不依赖 `self`），导致无法脱离 LLM 客户端单独测试；
3. `get_graph_v1` 的 `node_dict` 是**固定属性白名单**（category/confidence/is_manual/时间），

### 修复

1. **`_merge_results` 改为 `@staticmethod`**：不依赖实例状态，可独立测试（调用方 `self._merge_results(x)` 不受影响）。
2. **同名不再丢信息**：
   - 首条仍作为主 `description` / `category`（保持评测与前端展示口径不变）；
   - 其余不同描述累积到 `descriptions`，并给出 `alt_descriptions`；
   - 类别冲突记到 `category_variants`；
   - 完全重复的描述不重复累积；

3. **落库并读回**：
   - `build_graph` 把 `alt_descriptions` / `category_variants` 写进节点属性；
   - `get_graph_v1` 的属性投影补上这两项，且**只在存在时出现**——
     没有发生同名合并的节点，读图结果与改动前逐字节一致（保住「无映射即 no-op」的既有契约）。

## 12. `t_document.file_path` 存绝对路径：换机器后预览 / 上下文重建 / 删除文件全部失效

- **日期**：2026-10-31
- **阶段**：阶段 2 正确性与数据一致性
- **涉及文件**：`backend/app/core/storage.py`、`backend/app/services/document_service.py`、
  `backend/app/services/fusion/entity_context.py`、`backend/test_fusion_context_rebuild.py`；
  新增验证脚本 `backend/test_document_path.py`

### 现象

`test_fusion_context_rebuild.py` 在恢复后的库上失败：

```

  [Errno 2] No such file or directory:
  'C:\Users\20472\PycharmProjects\PythonProject1\知识图谱AI分析\backend\data\uploads\9\7_实验9  处理机调度.pdf'
```

库里 `t_document.file_path` 存的是**上传那台机器的绝对路径**。app.db 随备份/仓库换机器后，
同一行记录指向一个本机不存在的路径，于是：

- 在线阅读 / 下载打不开；
- 融合的「上下文重建」直接失败（`reconstruction_ok=False`，该项权重被迫归零）；
- 删除文档时删不到本地文件（留下垃圾文件）；
- 重试解析读不到原始文件。

### 定位

- `core/storage.resolve_document_path()` 已经会兼容「本机绝对 / 相对 backend/ / 他机绝对」

- 但 **写入端仍存绝对路径**（`document_service._persist_document` 把 `save_path` 原样入库），
  所以库永远不可移植，且每换一次机器就多一批失效行；
- 另外 `entity_context.load_chunks` 虽然调了 resolver，但解析失败时会**回退返回原始路径**，

### 修复

1. **存储改为相对路径**：新增 `core/storage.document_relative_path()`，
   `_persist_document` 入库时写 `{course_id}/{doc_id}_{文件名}`（相对 `UPLOAD_DIR`），
   绝对路径只在本次落盘时使用。
2. **解析器支持第四种形态**：`resolve_document_path` 在「相对 backend/」之后增加
   「相对 UPLOAD_DIR」分支，历史三种形态与上传约定回退全部保留。
3. **缺失文件给出明确原因**：`load_chunks` 在解析出的路径不存在时返回

   不再把过期路径丢给解析器。
4. **测试健壮性**：`test_fusion_context_rebuild` 的真实文档探针改为
   「挑选本机真能读到的已解析文档，找不到则 skip」，换机器不再误报失败。

## 13. 题目更换所属文档后，向量缓存永久停留在旧作用域

   - 所属文档变了 → 同样删行（哈希兜不住的一类）；
   - **只改难度/解析/知识点 → 不动缓存**，避免每次小编辑都触发一次外部 embedding 调用。

## 14. 重复提交「从文档导入题目」会产生重复题

- **日期**：2026-10-31
- **阶段**：阶段 2 正确性与数据一致性（题目导入）
- **涉及文件**：`backend/app/services/question_service.py`（`import_commit`）；
  新增验证脚本 `backend/test_question_import.py`

### 现象

`import_commit` 只做格式校验，**没有任何去重**。于是两种很常见的操作都会造出重复题：

1. 教师对同一份文档连点两次「提交导入」；
2. 同一份练习挂到两个文档各导入一次（按课程看的题库是同一份）。

重复题的后果不是「多几条数据」这么简单：批改统计、错题本、推荐配额与覆盖率报表
都按题计数，重复会直接把这些口径拉偏；教师还得逐条手工删。

### 定位

- `import_commit` 循环里 `validate_question_payload` 通过就直接 `create_question`；

- 命中已有题干 → 记入 `skipped` 并给出原因「重复题目：该课程已存在相同题干」，**不写库**；
- 同批次内重复也只入一条（命中后立即把该题干加入集合）。

为什么按课程而不是按文档：同一份练习挂多个文档是既有用法，按文档去重挡不住；
题干完全相同在题库语境下必然是重复。

## 15. 服务重启后文档永久卡在「处理中」（PARSING / EXTRACTING / BUILDING）

- **日期**：2026-10-31
- **阶段**：阶段 4 后台任务与处理链路可靠性
- **涉及文件**：`backend/app/services/document_service.py`（新增 `reconcile_interrupted`）、
  `backend/app/main.py`（lifespan 接入）、`backend/app/core/config.py`（`RECONCILE_ON_STARTUP`）；
  新增验证脚本 `backend/test_task_recovery.py`；
  新增巡检脚本 `backend/scripts/check_consistency.py`（配套工具，见 §工具）

### 现象

解析 / 抽取 / 建图都在**进程内**的 asyncio 任务里执行，进度只写进 SQLite。
进程重启（含崩溃、`--reload` 热重载、部署发版）后：

- 库里永久停在 `parse_status=PARSING` / `extract_status=EXTRACTING` / `graph_status=BUILDING`；
- 没有任何任务在跑，前端却一直显示「处理中」，教师没有可操作的入口；
- 课程/文档删除也会被 `4009「正在处理」` 拦下（守卫读的是进程内注册表，虽然能放行，
  但界面上的中间态让人不敢动）；
- 想重试只能靠人猜，且「重试」按钮在中间态下并不会显示。

### 定位

- `_running_docs` 是**进程内 set**，启动时必然为空 —— 状态与任务注册表在重启后彻底脱节；
- 启动流程（`lifespan`）只做 `init_tables` / 引导账号，没有任何状态对账；
- `retry_document` 其实**允许**中间态重试（只认进程内注册表），缺的是「让状态变成可重试」。

### 修复

新增 `DocumentService.reconcile_interrupted()`，在 `lifespan` 里（建表与引导账号之后）执行：

- 扫描 `parse_status=PARSING OR extract_status=EXTRACTING OR graph_status=BUILDING` 的文档；
- **只把中间态字段改为 `FAILED`**，并写入可读原因「服务重启导致任务中断，可点击重试」；
  已完成阶段不回退（`PARSED` / `COMPLETED` 保持原样）；
- 幂等：再次调用不会命中任何行；
- 失败只记日志，不阻塞启动。

**为什么是 FAILED 而不是自动重跑**：自动重跑会在启动瞬间对全部积压文档发起 LLM 调用，
费用与并发都不可控；而 `retry_document` 已支持「复用已保存文件 + 只清理该文档的图/向量」，
由教师显式触发更安全。

**多进程部署**：本方案假设「一个 uvicorn 进程」（`CLAUDE.md` 记录的部署形态）。
多 worker 下应设 `RECONCILE_ON_STARTUP=0`，否则可能把另一个 worker 正在处理的文档误标失败。

### 验证

`backend/test_task_recovery.py`（临时库，不调 LLM / 不连 Neo4j）：

| 断言 | 结果 |
|---|---|
| 三种中间态分别收敛为 FAILED 并写入原因 | ✓ |
| 已完成阶段不回退（PARSED 保持 PARSED、COMPLETED 保持 COMPLETED） | ✓ |
| 完全成功 / 已 FAILED 的文档受影响为 0 | ✓ |
| 幂等：再次调用扫到 0 条 | ✓ |
| **真实启动路径**（TestClient 触发 lifespan）自动收敛 | ✓ |
| `RECONCILE_ON_STARTUP=0` 时不动这些文档 | ✓ |
| 收敛后 `retry_document` 放行（返回 2003「源文件不存在」而非 4000「已完成」） | ✓ |

`通过 13/13`。

## 16. 单文件上传只能同步等待：大文件请求挂死，前端还可能重复上传

- **日期**：2026-10-31
- **阶段**：阶段 4 后台任务与处理链路可靠性
- **涉及文件**：`backend/app/services/document_service.py`（`process_upload` 新增 `background`）、
  `backend/app/api/documents.py`（`POST /api/v1/documents/upload?background=`）；
  新增验证脚本 `backend/test_upload_background.py`

### 现象

批量上传早就是「落库即返回 + 后台任务」，**单文件上传却仍在请求里同步跑完整个流水线**
（解析 → LLM 抽取 → 建图）。几十页 PDF 要几十秒到几分钟：

- 浏览器 / 网关先超时断开，用户看到「上传失败」，但服务端还在跑；
- 前端拿不到 `document_id`，用户会**再传一次** → 同一份文档进库两份（批量路径有
  `file_sha256` 去重，单文件同步路径在超时重传时无从判断）；
- 一个请求长时间占住 worker，并发能力被拖垮。

### 定位

`process_upload` 的注释写着「保持同步语义（请求返回时图谱已构建完成）供兼容路径使用」，
即历史上为了不改前端契约而刻意保留；但批量路径已经有完整的后台机制
（`_schedule_processing` + 并发上限 + 状态写入 + 异常兜底），单文件没有理由不复用。

### 修复

`process_upload(..., background=False)`：

- **默认 `False`**：保持既有同步语义，不动现有前端；
- **`True`**：落库后立即返回 `status=processing`（`data.background=true`），
  解析/抽取/建图交给 `_schedule_processing`（与批量共用同一条任务入口与并发上限）。

HTTP：`POST /api/v1/documents/upload?background=1`。前端接轮询即可获得「点了就能离开」的体验
（文档列表接口本就返回三个状态字段）。

### 验证

`backend/test_upload_background.py`（临时库，打桩 `_process_document`，不调 LLM / 不连 Neo4j）：

| 断言 | 结果 |
|---|---|
| `background=True` 立即返回 `status=processing`、计数为 0 | ✓ |
| 返回时后台任务尚未执行；让出事件循环后**确实被执行** | ✓ |
| 默认（`background=False`）返回时处理已完成、`status=completed` | ✓ |

## 17. 建图逐条写入（N+M 次往返）；且 `init_schema()` 从未被调用导致索引缺失

- **日期**：2026-10-31
- **阶段**：阶段 5' 深层性能优化
- **涉及文件**：`backend/app/core/database.py`（新增 `create_knowledge_nodes_bulk` /
  `create_relationships_bulk`）、`backend/app/services/kg_manager.py`（`build_graph` 改批量）、
  `backend/app/main.py`（启动时调用 `db.init_schema()`）；
  新增验证脚本 `backend/test_graph_bulk.py`

### 现象（两件事，互相放大）

1. **逐条写入**：`build_graph` 对每个实体调一次 `create_knowledge_node`、每条关系调一次
   `create_relationship`。一份 200 实体 + 300 关系的文档就是 **500 次网络往返**（实测 2.38s）；
   批量上传 10 份文档时这一段的耗时非常显眼。
2. **索引/约束从未被创建**：`database.py` 里写好了 `init_schema()`（含
   `kp_id_unique`、`kp_course_doc_name` 等 6 条索引/约束），但**全仓没有任何调用点**。
   本机之所以有索引，是历史上手工执行过；**全新部署会一条都没有** —— `MERGE` 退化成
   Label 扫描，建图与读图都会慢一个量级，且 `kp_id` 失去唯一约束。

### 定位

- `build_graph` 的两段循环各自 `for` 一次调一个 DAO 方法；
- 全仓检索 `init_schema` 只命中定义处（另一处是孤岛模块 `git_kg_manager` 自己的同名方法）；
- 冷启动首次调用还包含驱动握手/查询计划编译，容易被误当成「批量本身慢」
  （微基准：批量 200 节点冷启动 291ms、热 83ms；逐条 3127ms）。

### 修复

1. **节点**：`create_knowledge_nodes_bulk()` —— 单条 Cypher + `UNWIND`，
   `MERGE` 键、`ON CREATE` 生成 `kp_id`、`SET` 覆盖与 `+= props` 全部保持原语义。
2. **关系**：`create_relationships_bulk()` —— 先按类型分桶（Neo4j 不支持参数化关系类型），
   每种类型一条 `UNWIND`。类型非法仍回退 `RELATED_TO`；端点不存在的行由 `MATCH` 过滤
   （与逐条版本一致）。
3. `build_graph` 改为「先组装 payload，再一次性批量写」；应用层过滤保持不变：
   **未知类型直接丢弃**（不降级）、空端点与自环丢弃，confidence/evidence 属性照旧。
4. **启动时调用 `db.init_schema()`**（幂等 `IF NOT EXISTS`）。图库不可用只告警，
   不阻塞服务启动（既有降级路径保留）。

### 验证

`backend/test_graph_bulk.py`（200 实体 / 300 关系，需要 Neo4j；不可用时 SKIP）：

| 断言 | 结果 |
|---|---|
| 批量写入节点/关系数与输入一致 | ✓ 200 / 300 |
| **往返次数：批量 ≤6 次，逐条 ≥500 次** | ✓ 5 vs 500 |
| 语义等价（读回的节点表与边集合按名称对齐后完全一致，confidence 一致） | ✓ |
| 幂等：重复批量写不新增节点/边 | ✓ |
| 过滤规则不变：未知类型不写入也不降级；自环不写入 | ✓ |
| 文档隔离：同名实体在两个文档各自存在 | ✓ |
| **性能（预热后）：批量至少快 2 倍** | ✓ 567ms vs 2380ms（≈4.2×） |

> 测试口径踩过一次坑并已修正：`get_raw_graph_v1` 的边端点是 **kp_id（随机 uuid）**，
> 两份文档的同名节点 id 天然不同——必须先用节点表把 id 映射回名称再比较，

`通过 13/13`；`ruff check .` 通过；离线回归 **22/22**；融合 **11/11**。

  教师手动增删、融合应用等单点操作用它们更直观。

## 18. 向量索引「集合一变就整篇重建」：改一个知识点会重算整篇文档的 embedding

- **日期**：2026-10-31
- **阶段**：阶段 5' 深层性能优化
- **涉及文件**：`backend/app/services/embedding.py`（`ensure_index` 改增量 +
  新增 `sync_index`）、`backend/app/core/sql_database.py`（新增 `delete_kp_embeddings`）；
  新增验证脚本 `backend/test_embedding_incremental.py`；
  `backend/test_fusion_rag_consistency.py`（epoch 断言按新语义修正）

### 现象

`ensure_index` 的判定是「已存 kp_id 集合 ≠ 图谱当前集合 → `build_index`」，而
`build_index` 的第一步是**删除该文档全部向量**、再**全量重新嵌入**。于是：

- 教师改/删 1 个知识点 → 整篇文档（如 69 个知识点）重新调用 embedding API；
- 融合 apply/revoke 让少数节点进出 → 同样整篇重算；
- 而 embedding 调用是整条 RAG 链路里唯一按量计费的外部请求。

### 定位

- 新鲜度只做「集合相等/不等」二值判断，没有利用「差集」这个更细的信息；
- `t_kp_embedding` 只提供「按文档删除」，缺少「按 kp_id 精确删除」的入口，
  所以想只删几条也做不到。

### 修复

1. 新增 `sql_db.delete_kp_embeddings(course_id, document_id, kp_ids)`。
2. 新增 `KnowledgeEmbedder.sync_index()`：`to_add = current - stored`、
   `to_remove = stored - current`，**只删过期行、只嵌入新增项**，返回
   `{added, removed, kept}`；无新增时不调用 embedding。
3. `ensure_index` 在「集合不一致 或 融合 epoch 落后」时改调 `sync_index`；
   `build_index` 保留给「重新抽取」（kp_id 全换，全量重建更简单且不会漏）。

### 验证

`backend/test_embedding_incremental.py`（临时库 + 假 embedder，不调外部 API）：

| 断言 | 结果 |
|---|---|
| 首次建索引：embedding 调用 1 次、写入 3 行 | ✓ |
| 集合无变化：**embedding 调用次数不变** | ✓ |
| 新增 1 个 kp：**只嵌入这 1 条**（不是整篇），最终 4 行 | ✓ |
| 删除 1 个 kp：只删该行、**不调用 embedding** | ✓ |
| 增删同时发生：两边都只处理差集 | ✓ |
| 增量结果与「全量重建」逐条一致（kp_id → 向量完全相同） | ✓ |
| 未配置 embedding：不写库、返回全 0 | ✓ |

`通过 17/17`。

### 连带的行为修正（需要知情）

`test_fusion_rag_consistency` 里原有断言「`indexed_epoch` 落后于 `epoch` 时会**重建**」，
按新语义改为：**只对账、不重新嵌入**（集合没变就没有东西要重算），并要求对账后
`indexed_epoch` 追平、再次查询仍不嵌入。这是优化后的正确行为，已同步改断言与注释。

## 20. 问答只能等整段生成完：新增 SSE 流式端点（首字延迟从数秒降到首个 token）

- **日期**：2026-10-31
- **阶段**：阶段 5' 深层性能优化
- **涉及文件**：`backend/app/services/qa_service.py`（新增 `stream_answer`）、
  `backend/app/api/qa.py`（新增 `POST /api/v1/qa/ask/stream` + `_resolve_scope` 复用权限判定）；
  新增验证脚本 `backend/test_qa_stream.py`

### 现象

`/api/v1/qa/ask` 是「检索 → LLM 生成 → 一次性返回」，LLM 生成要几秒到十几秒，
前端只能转圈等待；期间没有任何中间输出，长回答体感很差（这与 `QA_TIMEOUT=15s` 的上限叠加）。

### 定位

- 问答服务只有 `ask_with_sources`（一次性）与 `ask`（只取答案）；
- 没有流式端点，也没有「边生成边推给前端」的通道。

### 修复

1. `QAService.stream_answer()` —— **异步生成器**，事件序列：
   `sources`（先给证据链）→ `delta`（可多次）→ `done`（全文 + sources）；
   失败时给 `error` 且**不再发 done**（沿用同步路径「明确报错、不伪造答案」的口径）。
2. **检索与生成的分工**：检索仍走 `asyncio.to_thread`（同步 embedding/Neo4j/SQLite）；
   `openai` 同步客户端的**流式迭代放在后台线程**里消费，通过 `loop.call_soon_threadsafe`
   投递到 `asyncio.Queue` —— 这里不能用 `to_thread`，否则要等整段结束才拿到结果。
3. API 侧 `POST /api/v1/qa/ask/stream` 返回 `StreamingResponse`（`text/event-stream`），

首字要等整段生成完（几秒到十几秒，且受 `QA_TIMEOUT=15s` 限制），长回答体感很差。

### 修复

1. **拆出纯解析模块 `sse.js`**：`parseSseFrame` / `readSseEvents`，不含任何环境依赖，
   可直接在 Node 里对真实 `ReadableStream` 跑测试；`qaStream.js` 只负责拼请求

   （后端给的原因放 `title`，不直接怼给用户）。
4. **降级链**：流式端点返回非 `text/event-stream`（权限拒绝走统一包装 JSON、代理不支持流）
   或网络失败时，若尚未收到任何正文，自动回退同步 `api.ask`，行为与改造前一致。
5. **中断语义**：
   - 切换学习资料/离开页面 → `beginRead()` 的 signal 中断 fetch，顺带让后端生成器结束（止损）；
   - 「清空对话」也会中断在途生成，避免半成品回写到已清空的列表；

- **涉及文件**：新增 `backend/app/services/task_state.py`、`backend/test_task_resume.py`；

  `backend/scripts/check_consistency.py`（新增 `TASK_STALE`）、
  `backend/test_consistency_check.py`（+3 条）、`backend/test_upload_background.py`（打桩签名）

### 现象

解析/抽取/建图都跑在**进程内**的 asyncio 任务里，状态却只写进 SQLite：

- 进程重启后库里停在 `PARSING` / `EXTRACTING` / `BUILDING`，前端永远「处理中」；
  阶段 4 的做法是「启动时收敛为 FAILED」——**能看见、能重试，但等于白干**；
- 教师点「重试」= 重新解析 PDF + **重新调用 LLM**。一次抽取几十页文档的成本被重复付；
- 任务本身没有任何持久化痕迹（attempts、心跳、卡在哪一步），排障只能看日志。

### 修复

1. **中间产物落盘**（`services/task_state.py`）：`TASK_STATE_DIR/<doc_id>/` 下
   `parsed.txt`（解析全文）与 `extracted.json`（`entities` + `relations`）。
   `meta.json` 记录 **sha256 + 产物版本**：文件被替换、或由旧版本代码写出 → 一律不复用
   （宁可重跑，也不能拿错文本建图）。整个流水线成功后清目录。
2. **任务落库**：新表 `t_document_task`（一行 = 一篇文档的**当前**任务）：
   `stage(PARSE/EXTRACT/BUILD/DONE)`、`status(IDLE/RUNNING/DONE/FAILED)`、`attempts`、
   `heartbeat_at`、`artifacts`、`error_message`。每进入一个阶段刷新心跳；
   写失败只告警（可观测性不能反过来弄挂任务）。
3. **`_process_document(doc_id, resume=False)`**：`resume=True` 时
   - 有 `parsed.txt` → 跳过解析；
   - 有 `extracted.json` → **跳过 LLM**（免费完成抽取）；
   其余逻辑（作用域校验、图谱清理、失败落库）完全不变。
4. **启动恢复三态决策**（`reconcile_interrupted` → 返回 `{scanned, recovered, resumed}`）：

   | 条件 | 处理 |
   |---|---|
   | 产物可复用且 sha256 一致 | **续跑**：保持中间态，重新入队（`resume=True`），只做没做完的那步 |
   | 无产物 / 调度失败 / `RESUME_ON_STARTUP=0` | 仍是 `FAILED`，教师手动重试 |

   不「无脑自动重跑」是刻意的：启动瞬间对全部积压文档发起 LLM 调用，费用与并发都不可控。
5. **两个清理入口**：`retry_document` 先清产物 + 任务行（**重试 = 真的重来**）；
   删除文档同样清（文档都没了，产物留着会被误认为可复用）。
6. **巡检补 TASK_STALE**：`check_consistency.py` 报告「状态 RUNNING 但心跳超过 30 分钟」
   的任务（`--stale-minutes` 可调）。启动恢复只在启动时跑一次，中途卡死只有巡检能看见。

## 25. 注销后同名重新注册仍提示「用户名已存在」

- **日期**：2026-11-03
- **涉及文件**：`backend/app/api/auth.py`、`backend/app/core/sql_database.py`、
  新增 `backend/test_auth_register_reclaim.py`

### 现象

用户自助注销（软停用）后，用完全相同的用户名重新注册，接口返回
`2006 用户名已存在`，无法创建新账号。

### 原因

注销接口只执行 `UPDATE t_user SET is_active = 0`，**没有释放 `username`**：

1. `t_user.username` 有 `UNIQUE` 约束，旧行仍占着这个名字；
2. 注册接口的占用判断 `get_user_by_username(username)` 不区分启用/停用，
   只要查到行就直接返回 2006；
3. 于是「停用保留历史数据」与「用户名唯一」叠加成了死锁——账号注销了，
   名字却永远不能再用。

另外发现注销端点没有调用 `invalidate_user_state`：账号态缓存里仍是
`is_active=1`，旧 token 最长还能继续访问 30 秒。

### 修复

1. 新增 `sql_db.create_user_releasing_inactive()`，在同一个
   `BEGIN IMMEDIATE` 事务里完成「查旧行 → 归档用户名 → 插入新用户」：
   - 旧行若已停用，`username` 改为 `__deleted_user_<user_id>__<原用户名>`；
     只改用户名，`user_id`、`is_active=0` 与全部历史数据（课程/作答/收藏等）
     原样保留；
   - 新账号拿到全新的 `user_id`，不会继承旧账号身份或数据；
   - 同名的**启用中**账号仍返回 2006；并发注册由事务 + `UNIQUE` 兜底。
2. `register` 改用该方法，并拒绝注册 `__deleted_user_` 前缀，避免真实用户
   占用内部归档命名空间。
3. 管理员账号（`role=admin`）与引导账号（`admin` / `sysadmin`）即使停用也不允许
   同名复用，防止管理员身份被普通账号顶替、破坏下次启动的引导账号识别。
4. 注销成功后调用 `invalidate_user_state(user_id)`，旧 token 立即 401。

### 验证

`backend/test_auth_register_reclaim.py`（临时库 + `AUTO_BACKUP=0`，**21/21 通过**）：

| 断言 | 结果 |
|---|---|

| 旧行保留、`is_active=0`、用户名进入归档前缀 | ✓ |
| 新账号可登录；旧密码无法登录同名新账号 | ✓ |
| 注销后旧 token 立即 401（不等缓存 TTL） | ✓ |
| 启用中的同名账号仍返回 2006 | ✓ |
| 归档前缀用户名注册 → 1001 | ✓ |
| 停用的管理员用户名仍不可复用 | ✓ |
| 停用的引导教师（admin）用户名仍不可复用 | ✓ |
