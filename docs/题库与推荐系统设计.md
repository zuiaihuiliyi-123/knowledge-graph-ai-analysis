## 一、定位与范围

### 1.1 现状（L1）

推荐入口：`POST /api/v1/practice/recommend` → `PracticeService.recommend_questions`
→ `QuestionRecommender.recommend()`（`backend/app/services/question_recommender.py` L343-466）。

现有建模是**单层全量打分**：

```
Step 0  候选池 = 全量题库（page_size=100000）          ← 无召回层
Step 1  再拉 3 份全量数据（全课题库 / 全班统计 / 我的作答）
Step 2  kp_mastery()     时间衰减加权正确率 + 自评融合（L83-156）
Step 3  graph_context()  图谱名称 + 归一化度数（L159-188）
Step 4  next_knowledge_ids()  路径「下一步」（L191-199）
Step 5  6 信号线性加权打分（L223-291）
Step 6  区分度乘性惩罚（×0.7）
Step 7  分桶：review / new / weak / advanced（L263-270）
Step 8  桶配额 + 同 kp 上限 + 题型均衡 + 三级回填（L294-332、L408-433）
Step 9  投影下发（_public_view 白名单，防泄题）
```

### 1.2 现状的 7 个缺口

| # | 缺口 | 位置 | 影响 |
|:--:|---|---|---|
| 1 | **无召回层**，全量打分 `O(N)` | L356-363 | 单请求 4 次全量查询；规模线性恶化 |
| 2 | 权重为手写常量，**无离线校准** | L40-45 | 无法随数据进化 |
| 3 | `review` 桶优先级碾压一切 | L263-264 级联 `if` | 过度偏向错题 |
| 4 | 区分度仅单一乘性 0.7 + 粗阈值 | `QUALITY_LOW/HIGH=0.2/0.95` | 中间灰区无法表达 |
| 5 | 掌握度**读时全量重算** | L370 | 作答量增长后成为瓶颈 |
| 6 | 难度为手填 1~5 整数 + 线性目标 | L243-244 | 表达力弱于 IRT |
| 7 | **同 kp 内所有题 `need` 完全相同** | L236 | 组内无区分，排序几乎只由 `diff_fit` 决定 |

> 缺口 7 是**结构性**的：同一知识点下的若干道题，`need` / `importance` / `wrong_flag` 完全相同。

### 1.3 本文档的定位

- 补**漏斗第一层（召回）**，并顺带修掉缺口 1、7
- 把权重从「手写常量」变成「离线校准」
- 引入学习科学结构（外缘/内缘、掌握状态、遗忘概率），使召回有学理依据
- **不改推荐目标、不改判分口径、不改组卷约束的业务语义、不改防泄题纪律**

## 二、目标形状

### 2.1 四阶段漏斗 + 双闭环

```
层 0 · 信号层   掌握状态 / p_recall / outer-inner fringe / 题目校准
      ↓
层 1 · 召回层   多通道并行（R1~R6）：全库 → 300~500 题
      ↓
层 2 · 精排层   7 信号打分 + 区分度惩罚
      ↓
层 3 · 策略层   桶配额 · 按知识点交错 · 题型均衡 · 三级回填 · 防泄题
      ↓
    学生作答
      ↓
闭环 A · 反馈   作答 → 答题记录 → 能力 / 遗忘参数
闭环 B · 评测   召回日志 → 离线指标 → 权重 / 阈值 / 粒度
```

**复杂度目标**：单次推荐耗时与题库规模**基本无关**（层 1 之后只对候选子集操作）。

## 三、层 0 · 信号层

### 3.1 掌握度：拆成「能力」与「保留概率」两个量

现状把两件事混在一个数里（`kp_mastery`，L83-156）：时间衰减加权正确率 + 自评融合。

**目标态拆开**：

```python
# 能力（ability）：你「会不会」—— 保留现有自评融合，语义不变
ability = clamp(0.5 * acc_weighted + 0.5 * manual_score)   # 有练习 + 自评
          acc_weighted                                      # 只有练习
          manual_score                                      # 只有自评
          None                                              # 无证据

# 保留（retention）：你「还记不记得」—— HLR 式概率（Duolingo 思想）
p_recall = 2 ** (-Δdays / HL)
HL       = 2 ** (theta_kp + theta_stu)   # 半衰期可训练；初期先验 theta_kp = log2(14)

# 证据量（新增）：用于置信度与冷启动判定
evidence = 已批改作答条数（按 kp 聚合）
```

**为什么必须拆**（对应缺口 2、5）：

| 信号 | 教学含义 | 现状 | 目标态 |
|---|---|---|---|
| 薄弱度 | 这知识点你本来就弱 | `(100 − mastery)/100` | `1 − ability` |
| 遗忘到期 | 你会但快忘了 | `clamp(Δ/7)` 硬阈值 | `1 − p_recall` |

→ 两者对应**不同的教学动作**（补基础 vs 复习巩固），现状无法区分，且信息高度重复。

> ⚠️ `theta` 拟合需 ≥ 数千条作答/课程。当前 757 条仅够演示 → **theta 拟合列为 L3**。
> L2 先用先验 `HL = 2^log2(14) = 14`，**与现状 `HALF_LIFE_DAYS=14` 等价，保证 L2 不引入行为变化**。

### 3.2 掌握状态门控（离散化）

给 UI 与召回层用的**状态机**，替代现状 `mastery < 60 → weak` 的单线阈值：

| 状态 | 判据 | 召回动作 |
|---|---|---|
| `NOT_STARTED` | `evidence == 0` | 进**诊断召回**（信息增益，见 §6.3） |
| `ATTEMPTED` | `ability < 0.5` | 进 R4，**最高优先** |
| `FAMILIAR` | `0.5 ≤ ability < 0.8` | 进 R4，中优先 |
| `PROFICIENT` | `ability ≥ 0.8 且 p_recall < 0.6` | 进 **R2 到期复习** |
| `MASTERED` | `ability ≥ 0.8 且 p_recall ≥ 0.6` | 不进召回（配额不足时才兜底） |

阈值来源：沿用现有 `WEAK_THRESHOLD=60` / `ADVANCED_THRESHOLD=70` 的口径，新增 `p_recall` 门控 0.6。

### 3.3 图谱特征（外缘 / 内缘）

**理论出处**：Knowledge Space Theory（ALEKS）—— `outer fringe` = 前置已满足但未掌握；`inner fringe` = 刚学会 / 不稳定掌握。

```python
outer_fringe = { kp | 前置(kp) ⊆ MASTERED 且 kp ∉ MASTERED }   # 「可学」
inner_fringe = { kp | kp ∈ PROFICIENT ∪ {最近新达 MASTERED} }   # 「该复习」
```

**本项目已有原料**：`PathRecommender.recommend_next()`（`backend/app/services/path_recommender.py` L162）
逐字就是 outer fringe 的定义（「所有前置已满足的节点」、「无掌握记录 → 无入边的根节点」、
「无 `PRECEDES` → 降级 `CONTAINS` 上层概念」）。

> **本次改造的核心动作之一**：把 `next_knowledge_ids()` 从「分桶条件（`bucket='new'`）」
> **升格为召回通道（R1）**。它现在只影响标签，不影响取数。

另加：
- **中心性**：`(n)--(m)` 无向度数 → **PageRank**（现状 `graph_context` L167-170 已算度数，可直接扩展）
- **路径深度**：到目标知识点的 `PRECEDES` 距离（可选）

### 3.4 题目校准

```
P(答对 | 能力 θ_s, 难度 b_i) = 1 / (1 + exp(−(θ_s − b_i)))
```

- 现状：`t_question.difficulty` 是教师手填 1~5 整数
- 目标态：用 `question_answer_stats()`（L1855，已有）做一参数 Logistic 校准 → 连续 `b`
- **列为 L3**（需数据量；758 条作答只够演示）。L2 保留整数难度 + 现有 `DIFF_SLOPE=4` 线性目标。

## 四、层 1 · 召回层（**已实现**，见 §13.6）

### 4.1 六个通道

| 通道 | 学理出处 | 触发条件 | 实现 | 依赖 | 优先级 |
|:--:|---|---|---|:--:|:--:|
| **R1** | ALEKS outer fringe | `outer_fringe ≠ ∅` | `next_knowledge_ids()` → 取题 | 已有 | 🥇 |
| **R2** | ALEKS inner fringe / SM-2 | `p_recall < 0.6` 或 `Δ > REVIEW_DUE_DAYS` | kp → 取题 | 纯 SQL | 🥇 |
| **R3** | 错题邻域 | 最近明确答错 | 错题 kp + 图谱一跳（复用 `kp_labeler._graph_expand` L179 思路） | Neo4j 只读 | 🥈 |
| **R4** | 掌握状态门控 | `ATTEMPTED` / `FAMILIAR` | kp → 取题 | 纯 SQL | 🥈 |
| **R5** | 语义近邻（**补充通道**） | 有 key 且向量可用 | numpy 矩阵（后期可换 HNSW） | §7.4 向量层 | 🥉 |
| **R6** | 兜底 | 以上皆空 | 高区分度题 | 纯 SQL | 保底 |

> **设计立场**：教育场景**标签召回为主、向量召回为辅**。题库天然带知识点标签，
> 标签召回的精度与可解释性均优于通用语义向量。R5 主要用于区分**同 kp 内的题目差异**（修缺口 7）。

### 4.2 编排纪律（6 条，实施后已按实测校准）

1. **每通道独立降级**：单通道失败只记 `meta.by_channel`，不影响其他通道（沿用 `kp_labeler` 纪律）
2. **kp 预算**：`kp_budget = max(20, want // 4)`，按通道配额分配；未用满的名额按优先级顺延
3. **`want` 上限**：`max(200, 10 × count)`，候选集不随题库无限膨胀
4. **全空回落**：所有通道皆空 → 回落全量路径（`meta.fallback_used = True`）
5. **通道配额**：`outer 35% / due 25% / weak 20% / wrong 10% / semantic 10%`
6. **作用方式（⚠️ 实施后修订）**：默认 **`RECALL_MODE="bias"`** —— 召回命中的 kp 保持原分、
   未命中的 kp 的题得分 ×`RECALL_PENALTY(0.7)`。**不丢题 → Recall@K 天然满足安全阀**，
   收益体现在排序与分桶上（实测 30 个场景里 10 个组卷结果不同）。
   `"filter"`（按 kp 硬过滤）**仅在题库极大时使用**，其覆盖损失经实测为 17.3%、
   Recall@K 均值 0.8267 / 最低 0.2000 —— 详见 §13.8。

### 4.3 降级矩阵

| Neo4j | Embedding Key | 可用通道 | meta 标记 |
|:--:|:--:|---|---|
| 有 | 有 | R1~R6 全开 | `graph_available=true, vector_available=true` |
| 有 | 无 | R1~R4、R6 | `vector_available=false` |
| 无 | 有 | R2、R4、R5、R6 | `graph_available=false`（R1/R3 失效） |
| 无 | 无 | R2、R4、R6 | 两者皆 false；若候选仍空 → `fallback_used=true` |

### 4.4 召回选择性测算（**必须先算这笔账**）

> **选择性 = 弱势知识点数 × 每知识点题数**

| 规模 | 弱 kp 数 | 每 kp 题数 | 候选集 | 相对全量 |
|:--:|:--:|:--:|:--:|:--:|
| 现状（120 题 / 40 kp） | 20 | 3 | 60 | 50% |
| 中等（1 万题 / 300 kp） | 20 | 33 | 660 | 6.6% |
| 大规模（10 万题 / 1000 kp） | 20 | 100 | 2000 | 2% |

**两条结论**：

1. **小规模时收益有限**（120 题只能砍一半）—— 不要用当前数据判断召回层无价值
2. **大规模时绝对量仍有 2000** → 必须依赖 `want` 上限 + **组内排序**（R5 语义 + 难度 + 新颖度）

> 组内排序策略决定 R5 是「可选」还是「必需」。**建议 R5 必需**，理由：它是唯一能修缺口 7 的机制。

**诊断工具（已有，零开发）**：`count_questions_grouped_by_kp()`（L1821）可直接输出每 kp 题数分布。

## 五、层 2 · 精排层

### 5.1 七信号（现状 6 → 目标 7）

| # | 信号 | 现状（L236-249） | 目标态 | L2 权重初值 |
|:--:|---|---|---|:--:|
| ① | 薄弱度 | `(100 − mastery)/100` | `1 − ability` | 0.30 |
| ② | 遗忘到期 | `clamp(Δ/7)` | `1 − p_recall` | 0.25 |
| ③ | 难度适配 | 整数难度 + 线性目标 | 保留（L3 换 IRT `b`） | 0.15 |
| ④ | 新颖度 | 三档（1.0 / 0.5 / 0.3） | 保留 | 0.08 |
| ⑤ | 错题优先 | 布尔 | 保留（L3 加连续答错次数） | 0.07 |
| ⑥ | 图谱重要性 | 归一化度数 | PageRank 中心性 | 0.05 |
| ⑦ | **语义相关度** | ❌ 无 | 题目向量 ↔ 错题 / 兴趣向量 余弦 | 0.10 |
| — | 区分度惩罚 | 乘性 ×0.7，阈值 0.2 / 0.95 | 改为**连续平滑函数** | 乘性 |
| — | **诊断信息增益** | ❌ 无 | **仅冷启动启用**（§6.3） | 覆盖式 |

> 权重值仅为**初值**，须经 §9 离线校准确定。L2 阶段行为应尽量贴近现状，
> 避免「一次改太多导致无法归因」。

### 5.2 权重来源（闭环的执行点）

```
手写常量 → 离线网格搜索（评测集上最大化 NDCG@k / Recall@K）
        → 线上 A/B（复用现有 seed 参数做分流与复现）
```

**已有基础**：`RecommendRequest.seed` + `eval_question_recommend.py`。

## 六、层 3 · 策略层

### 6.1 保留的机制（本次不动语义）

| 机制 | 位置 | 状态 |
|---|---|:--:|
| 桶配额 `mixed = 0.40 / 0.25 / 0.20 / 0.15` | `MIXED_RATIO` L59 | 保留（桶定义改为掌握状态） |
| 同 kp 题数上限 `ceil(count/3)` | `KP_QUOTA_DIVISOR` L56 | 保留；**多 KP 下按「任一命中」硬占用**（§12.1 决策 4a）；实测 `quota_relaxed` 仍为 0，故 **divisor 保持 3 不调整**（§12.1.1） |
| 题型均衡（两轮挑选） | `pick_with_quota` L310-332 | 保留 |
| 三级回填（桶内 → 其他桶 → 放宽配额） | L422-433 | 保留 |
| 去重（精确集合 + `used_qids`） | L410-433 | 保留（**不用 Bloom**，见 §11） |
| 防泄题（`_public_view` 白名单） | `question_service.py` | **零改动** |

### 6.2 新增：按知识点交错（interleaving）

现状 `mixed` 是「按桶拼卷」；目标态在桶内**按知识点交错**，让同一份卷子覆盖
尽可能多的**不同知识点**（交错练习有学习科学实证支持）。

> 与现有「同 kp 上限」方向一致，属强化而非冲突。

### 6.3 冷启动：信息增益最大化（替代「推一批弱题」）

现状：新学生 `mastery=None` → `m_eff=50` → 全进 `weak` 桶，理由写「建议先摸底练几题」（L218）。
**意图正确，但无方法。**

目标态（ALEKS 式，**不需要模型**）：

```
诊断信息增益代理 = 该题覆盖的「未观测知识点」数量
选题策略         = 优先覆盖最多未观测 kp 的题，且难度适中
```

> **重要推论**：一道挂 3 个知识点的题，诊断信息量是单 kp 题的 3 倍。
> → 这是「**一题多 KP**」的第二个理由（第一个是召回选择性）。

## 七、数据模型

### 7.1 新增表

```sql
-- 一题多知识点（关联表；替代 t_question.kp_id 的单值语义）
CREATE TABLE IF NOT EXISTS t_question_kp (
    question_id INTEGER NOT NULL,
    kp_id       TEXT    NOT NULL,
    score       REAL,                              -- 标注置信度（kp_labeler 产物）
    source      TEXT NOT NULL DEFAULT 'MANUAL',    -- MANUAL / AI / IMPORT
    is_primary  INTEGER NOT NULL DEFAULT 0,        -- 主知识点（列表展示 / 推荐理由文案）
    created_at  TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    PRIMARY KEY (question_id, kp_id),
    FOREIGN KEY (question_id) REFERENCES t_question(question_id)
);
CREATE INDEX IF NOT EXISTS idx_qkp_kp ON t_question_kp(kp_id);
-- 一题最多一个主知识点（SQLite 支持部分唯一索引；靠 DB 约束而非应用层自觉）
CREATE UNIQUE INDEX IF NOT EXISTS uq_qkp_primary
    ON t_question_kp(question_id) WHERE is_primary = 1;

-- 召回日志（评测闭环的基础；没有它无法回答「这次变化是因为改了哪个参数」）
CREATE TABLE IF NOT EXISTS t_recall_log (
    log_id        INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id       INTEGER NOT NULL,
    course_id     INTEGER NOT NULL,
    document_id   INTEGER,
    requested_at  TEXT NOT NULL DEFAULT (datetime('now', 'localtime')),
    mode          TEXT,
    want          INTEGER,
    count         INTEGER,
    seed          INTEGER,
    candidate_ids TEXT,     -- JSON：召回候选
    by_channel    TEXT,     -- JSON：各通道命中数
    picked_ids    TEXT,     -- JSON：最终组卷
    recall_ms     REAL,
    fallback_used INTEGER NOT NULL DEFAULT 0,
    params        TEXT      -- JSON：当时的权重 / 阈值快照 ← 可回溯
);

    ON t_recall_log(course_id, requested_at);
```

### 7.4 向量存储

## 十一、明确不做

| ❌ 不做 | 依据 |
|---|---|
| HNSW / Faiss 索引 | 向量层改造后 N=5k 仅 0.42ms；N=20k 起 HNSW 才 3.4× 优势，不值新依赖 + 索引重建（20k 建索引 3.3s、50k 17.6s） |
| 布隆过滤器去重 | 实测查询慢 199~263×、仅省内存；**普通 Bloom 不支持删除**，删作答 / 停用题后假阳性 = 1.0 → 题目永久不可推荐 |
| 0/1 标签向量 + λ 阈值召回 | 单标签下余弦只取 {0, 1}，λ∈(0.1, 1.0) 结果相同（真实数据退化）；多标签下 λ=0.8 覆盖率崩至 23%、Recall@10 0.021 → **直接做标签重叠召回，不绕向量** |
| CosMacBERT 复现 | bge-m3 出厂即对比学习产物，「距离区分度不足」是裸 MacBERT 的问题；重训无增量 |
| 协同过滤 | 教育场景标签召回精度更高；无用户-物品矩阵规模 |
| DKT / SAKT 深度知识追踪 | 数据量差 2~3 个数量级（现 757 条作答） |
| Django / MySQL / Redis 迁移 | 与现有 FastAPI + SQLite + Neo4j 栈冲突 |

### 13.2 实施期补充的关键设计决策

1. **`t_question.kp_id` 是投影、不是事实来源**：读侧行为不变，因此 `StudentView.vue` 的 kp 展示**无需改动**（原计划的前端改动被本次设计消解）。
2. **`update_question` 只在调用方显式传知识点字段时才写关联**——否则「教师只改难度」会把多 KP 题**塌缩**成单 KP。服务层已按此收口（仅当 `payload` 含 `kp_id` / `kp_ids` 才传 kp 字段）。
3. **`kp_id=X` 的过滤语义由「主知识点」改为「涉及该知识点」**（含次要知识点）。存量 126/126 题为单知识点，故在现有数据上**无可观测差异**；集中到 `_kp_filter()` 一个 helper 也是为防 4 个调用点各写一遍而漂移。
4. **空值统一为 `NULL`**：清空后 `t_question.kp_id` 落 `NULL`（与既有历史行 `question_id=373` 一致，全库仅此一种空值形态）。
5. **`MAX_KP_PER_QUESTION` 的双重作用**：除防误传超大数组，也为 §12.1 决策 4（任一命中即占用配额槽）留出上限。

`seed_practice_data.clean_previous_seed()` 用**原生 SQL** 直接 `DELETE FROM t_question`（**不走** `delete_question`）。
新表带指向 `t_question` 的物理外键、连接默认 `foreign_keys=ON`，而 `create_question` 现在**总会**写关联行
⇒ 该清理函数**必然抛 `FOREIGN KEY constraint failed`**，即 seed 脚本从第二次运行起就会失败。
已补「先删关联行」，并在 `test_question_kp.py` 第 12 组加了 4 项针对性回归。

**为什么第一轮没发现**：这个删除点**不在 `sql_database.py` 里**——最初的排查只覆盖了 DAO 层；
改成「**全仓库搜 `DELETE FROM t_question`**」才定位到。
**教训（应写进流程）**：**新增物理外键时，必须全仓库排查直接 DML，而不只是自己改动的那几个文件。**

**注意**：`test_permission_matrix.py` 会校验「线上 app.db MD5 未变」。若与 `test_courses_crud.py`（该脚本会清空业务数据）**并行**运行，该断言必然失败——这是脚本编排问题，不是产品缺陷。

### 13.8 向量路激活 + 召回层「作用方式」修订（**实测驱动的设计变更**）

#### ④ 假设二被证伪 + 真实设计缺陷：硬过滤不达安全阀（**改为 bias 默认**）

*假设*：召回按 kp 硬过滤候选池是默认做法。
*实测（把 course 65 临时扩到 3121 题）*：

| mode | Recall@30 均值 | 最小 | 低于 0.95 | 组卷是否改变 | 候选集 |
|---|:--:|:--:|:--:|:--:|:--:|
| OFF（基线） | 1.0000 | 1.0000 | 0/30 | — | 3120 |
| **bias（新默认）** | **1.0000** | **1.0000** | **0/30** | **10/30 场景不同** | 3120 |
| filter（旧的唯一做法） | **0.8267** | **0.2000** | **6/30** ❌ | 11/30 | **2673**（−14.3%） |

**修订**：
- `RECALL_MODE="bias"`（**新默认**）：召回命中的 kp **保持原分**，未命中的 kp 的题得分 ×`RECALL_PENALTY(0.7)`。
  → **不丢题**（Recall@K 天然 = 1.0000），收益体现在**排序与分桶**上（30 个场景里 10 个组卷结果不同，**不是空操作**）。
- `RECALL_MODE="filter"`：仍保留，供「题库大到全量打分不可接受」时使用，但**必须接受覆盖损失**；
  并按 `MIN_QUESTIONS_FOR_FILTER`（默认 2000）做规模门控——小规模时硬过滤是净负收益。

#### ① 修复：三处静默缺陷

| # | 问题 | 影响 | 修复 |
|:--:|---|---|---|
| 1 | `label_question` **逐题重算 embedding** | `label_questions` 已用 `ensure_question_vectors` **批量**算好并入库向量，却仍在 `label_question` 里逐题 `embedder.embed(...)` → **每题多一次 API 调用**（121 题 = 121 次多余调用，是标注耗时 22.5s 的主要来源） | 新增 `q_vec` 参数 + `_load_question_vectors()`（BLOB 快读，复用已入库向量）；批量与单题路径都改走它 |
| 2 | `eval_kp_labeling.eval_course()` **从不传 `embedder` / `kp_vectors`** | **向量路恒为关闭** → 历史报告（hit@1 = 0.102）只反映「字面 + 图谱」两层，**低估了标注器** | 新增 `use_vector` 参数（默认开启，无 key 自动回落）+ A/B 对照输出（存 `metrics.ab_without_vector`） |
| 3 | **`question_text()` 丢失选项**（最严重） | 见 ②，字面层与向量层**双双残疾** | `options` 兼容 JSON 字符串形态（函数入口统一 `json.loads`） |

#### ② `question_text()` 选项丢失 —— 静默最久的缺陷

`question_text()` 用 `isinstance(raw, list)` 判断选项。但**批量标注路径传入的是
`sql_db.list_questions()` 的原始行**，其中 `options` 是 **JSON 字符串**而非 list
→ 判断为假 → **选项被整体丢弃**，`question_text()` 只剩题干（实测：某多选题目
文本长度 **25 字符**，本应 187）。三个后果**同时静默发生**：

1. **字面层的「选项命中」从未生效**：`_lexical_scores()` 靠 `question_text()` 减去题干
   得到「额外文本」再配 `OPTION_WEIGHT=0.7` 打分；额外文本恒空 → 该权重形同虚设
2. **向量只嵌入题干**：题干相同、选项不同的题（如 seed 生成的
   「下列「知识点：描述」配对中，哪些是正确的？」）**向量完全相同**
3. **`text_hash` 不含选项** → **改了选项不会触发重算向量**（指纹失效）

**发现路径**：实现第 7 信号（§13.10）时，该信号的「最大余弦」对若干题**恰好 = 1.0000**；
追查发现它们是**题干相同、选项不同**的题 —— 余弦 1.0 说明向量一模一样，才反查到根因。

修复前后（同一题库、同一参数）：

| 指标 | 修复前 | **修复后** | 变化 |
|---|:--:|:--:|:--:|
| **有候选的题数** | 80 / 121 | **120 / 121** | **+40** |
| 候选的字面证据数 | 71 | **240** | **3.4×** |
| 候选的向量证据数 | 236 | **360** | +53% |
| 多标签题数 | 51 | **73** | +22 |

> **教训**：`question_text()` 是被字面层、向量层、`text_hash` 三方共用的**单一文本口径**；
> 它错，三个地方一起错，且**不会报错**（选项为空只是少一点证据，不抛异常）。
> 修复摆在函数入口做形态兼容，调用方无需感知。

### 13.10 阶段 F：精排第 7 信号「语义相关度」

#### ① 为什么加这条信号（修缺口 7「同 kp 内题目无区分」）

原有 6 个信号里，`need`/`due`/`importance`/`wrong` **都按知识点取值**——
同一知识点下的所有题目，这四项**完全相同**；只有 `diff_fit`/`novelty` 会变。
结果是「同 kp 内选哪道题」几乎由难度与是否做过决定，**与这道题到底考什么无关**。

第 7 信号直接补上这一维：**候选题目向量 ↔ 学生最近错题向量的最大余弦**。
与错题语义相近的题，更可能考的是同一类概念/同一类错法。

#### ② 权重调整：只让两个信号各出 5%（保证可归因）

| 信号 | 旧权重 | **新权重** | 说明 |
|---|:--:|:--:|---|
| ① 薄弱度 need | 0.35 | **0.30** | 让出 0.05 |
| ② 遗忘到期 due | 0.20 | 0.20 | 不变 |
| ③ 难度适配 diff_fit | 0.15 | 0.15 | 不变 |
| ④ 新颖度 novelty | 0.10 | 0.10 | 不变 |
| ⑤ 错题优先 wrong | 0.10 | 0.10 | 不变 |
| ⑥ 图谱重要性 importance | 0.10 | **0.05** | 让出 0.05 |
| **⑦ 语义相关度 semantic** | — | **0.10** | 新增 |
| 合计 | 1.00 | **1.00** | |

刻意**不动 due/diff_fit/novelty/wrong**：本次只回答「加第 7 信号会怎样」，
避免与权重调参混在一起无法归因（权重网格校准见 ⑧，是独立的下一步）。

#### ③ 实现

| 位置 | 内容 |
|---|---|
| `vector_index.question_max_similarity(course_id, document_id, query_vecs, query_ids=None, max_vectors=MAX_SIM_VECTORS)` | 新方法：一次矩阵乘得到「每个题目 × 每个查询向量」的相似度，逐题取最大。numpy 缺失时回落逐条余弦（`VECTOR_FORCE_BRUTE=1` 可强制走回落路径验证一致性） |
| `question_recommender.SEMANTIC_SIGNAL_QUERY_LIMIT = 20` | 查询向量取**最近 20 道**错题（按 `last_at` 升序取尾部） |
| `question_recommender._normalize_semantic()` | 把余弦按候选集分布映射到 [0,1]（见 ⑤） |
| `build_candidates(...)` | 新增 `sem_map` 参数 + `signals.semantic`（参与打分）+ `signals.semantic_raw`（原始余弦，**仅供观测**） |
| `meta` | `weights.semantic` / `semantic_available`（该信号是否生效） |
| 兜底 | 任一环节异常（无向量、无错题、库故障）→ `sem_map = None`，该信号取 0，**不影响其余 6 个信号** |

`score == Σ Wᵢ × signalsᵢ` 的审计不变量继续成立（`semantic` 才是参与打分的值）。

#### ④ 排除自匹配：一个必须做、否则重复计分的细节

初版实现里，若候选**就是**某道错题本身，它与自己余弦为 1.0 → 拿满分。
但「这道题刚做错过」**已由 `wrong` 信号与 `review` 桶表达**，语义信号再计一次是
**重复计分**。故 `query_max_similarity` 支持 `query_ids`：给定查询题号后，
把「题目=查询」那一格置为 `-1`，逐题取最大——只度量「与**其他**错题的相似度」。

> 实测确认：排除前 `max = 1.0000`（即自我匹配），排除后 `max = 0.9593`，
> 且 top-3 命中全部为非查询题。

**此处踩过一个坑**：调用方最初按 `zip(qids, vecs)` 配对，但**部分错题没有向量**，
`get_question_embedding_blobs` 返回的行数会短于 `qids` → 下标错位 → 屏蔽打偏，
自匹配仍然拿满分。改为**用行里实际的 `question_id` 与向量配对**（`pairs`）后才正确。

#### ⑤ 分布标准化：原始余弦会让名义权重失效

实测 course 65 的「最大余弦」分布：`min 0.230 / 中位 0.769 / max 0.959 / std 0.089`。
同域中文文本的 bge-m3 余弦**天然集中在 0.6~0.96**，直接用原始余弦时：

> 权重 0.10 × 实际波动 ≈ **0.009** 的分数区分度 —— **名义权重与实际影响力差一个数量级**。

故 `_normalize_semantic()` 按**候选集内**分布标准化：均值 → 0.5，**±2σ（`SEM_Z_SPREAD=0.25`）→ 1 / 0**，超出截断；
`std≈0` 时返回全 0.5（**不用噪声制造虚假差异**）。

- 代价（诚实记录）：信号值成为**相对值**，依赖候选池分布；对精排（排序）可接受，因为排序只关心集内相对顺序。
- 无向量证据的题取 **0.5（中性）**，与 `importance` 对未知 kp 的回落口径一致 —— **不因「缺向量」而受罚**。

**结论**：

#### ⑩ 顺带修复：题目向量在 3 个删除点漏清理（潜在泄漏）

**发现方式**：复核 `t_question_embedding` 的数据一致性时，grep `DELETE FROM t_question_embedding`
发现**全代码库只有 2 处**清理语句（`delete_course`、`delete_question_embeddings_by_document`），
而 `t_question_kp`（L2 新建）在 **4 个**删除点都有级联清理。逐函数核对确认：

| 删除点 | 清 `t_question_kp` | 清 `t_question_embedding` |
|---|:--:|:--:|
| `delete_question` | ✅ | ❌ **漏** |
| `delete_questions_by_course` | ✅ | ❌ **漏** |
| `delete_questions_by_document` | ✅ | ❌ **漏** |
| `delete_course` | ✅ | ✅ |

**为什么只有 `t_question_kp` 没漏**：它带**物理外键** + `foreign_keys=ON`，
漏删会**当场抛 FK 错误**（所以在阶段 A 被强制修好）；
而 `t_question_embedding` **无外键** → 漏删**不报错**，只静默留下孤儿向量行，
表现为「向量索引能检索到已删除的题号」。**「无外键」本身就是漏删的温床。**

**已修**：3 个删除点补 `DELETE FROM t_question_embedding ...`；
另外 `delete_course` 改为 `WHERE course_id = ?` **直删**（原「题号子查询」写法
漏掉孤儿行——题目已删而向量还在时，子查询就查不到它了）。

**诚实声明**：本机数据**当前是干净的**（`scan_consistency.py` 的 LEFT JOIN 检查 0 孤儿），
这属于**潜在缺陷**——由代码核对发现，而非由脏数据暴露。**不能宣称"修复了一个线上泄漏"。**

**防回归**：`scan_consistency.py` 新增 `t_question_embedding` 三项检查
（孤儿向量 / 课程不一致 / document_id 漂移），与既有的 `t_kp_embedding`、`t_question_kp`
检查同口径——这类「无外键表」的漏删以后会被扫描直接抓出来。

### 13.11 阶段 G：KP 粒度实验 + async/WAL 修复

本阶段交付三件互不相同的东西：**一个决策实验**（粒度-覆盖率曲线）、
**两个可用性修复**（事件循环阻塞、SQLite 并发写）——外加一个被 WAL 逼出来的
**备份路径修复**。三者都没有改变推荐算法本身。

#### ① KP 粒度实验：目的与结论

**为什么必须做**（文档 §4.4 与风险表早已写明）：召回收益 = 选择性 =
**弱势知识点数 × 每知识点题数**，而「每知识点题数」是个**从未被验证过**的参数
（当前 40 个 kp 是抽取算法顺带产生的，不是设计选择）。

**方法（数据库零写入）**：`recommend()` 的知识点身份**只**从三个取数点流出：

| 取数点 | 作用 |
|---|---|
| `sql_db.get_question_kps_map()` | 掌握度归因 / 召回 R3 / 打分 / 配额 |
| `sql_db.get_kp_embedding_blobs()` | kp 向量（召回 R5）——经 `vector_index._load` 读它 |
| `sql_db.list_records_by_user_course()` | 学生自评（掌握度融合项） |

`eval_kp_granularity.py` 🆕 用 `_Patches` **临时替换**这三处（退出即还原 +
`vector_index.invalidate()`），于是整条管线（掌握度 → 多通道召回 → 精排 → 分桶配额）
真实运行在**合成分区**上。合成规则：

- **合并（G < 40）**：按 `(category, kp_id)` 排序后切 G 段（同类别优先相邻）——
  **中性模拟**，非语义合并；
- **拆分（G > 40）**：每个 kp 按其题量比例分到若干子 kp，子内用**题向量的贪心
  k-center 聚类**（确定性）。为什么要语义聚类而非顺序切分：顺序切分下
  「子知识点的掌握度 ≈ 父知识点均值」，细粒度就观察不到任何差异；
- **G = 40 = 恒等**：不做任何替换，这就是**真实数据锚点**。

**曲线（course 65，5 学生 × weak/review/mixed，count=10，K=30，seed=2026）**

| G | kp 数 | 题/kp 中位/均值 | 弱 kp | 召回 kp | 预算 | 候选池 | 选择性 | R@K(bias) | R@K(filter) | 低于阀 | dist_kp | 回填率 |

| **40** | **40** | **4.0/5.5** | 10.4 | 34.8 | 50 | 112.0 | **0.9333** | 1.0000 | **0.9933** | 0 | 7.60 | 0.200 |

**结论（三条，都可机读于报告的 `safe_ceiling_g` / `breakpoint_g` / `curve_monotone`）**

1. **机制：召回命中的 kp 数受预算硬约束。** `picked_kps` 从 10.0（G=10）升到
   48.8（G=160），**始终 ≤ `kp_budget = want // KP_BUDGET_DIVISOR = 200 // 4 = 50`**。
   故 kp 总数超过预算后，召回覆盖率 ≈ 预算/kp 数，**随粒度单调下降**（实测单调 ✓）。
   `RECALL_MIN=200 题` 与 `KP_BUDGET_DIVISOR=4 题/kp` 这两个常量**jointly 定义了
   召回能覆盖的知识点上限（50）**——这是此前没有写进文档的隐含契约。
2. **真实粒度（G=40，每 kp 中位 4 题）在安全区内**：召回命中 34.8/40 个 kp →
   候选池 112/120（**选择性 0.9333**）、filter 口径 Recall@K **0.9933** ≥ 0.95。
   **安全上限就是 G=40**（全部 15 个场景达标）；**拐点是 G=48**（选择性 0.8966，
   3 个场景跌破安全阀），G≥80 明显跌破（0.68 / 0.91），G=160 严重跌破（0.37 / 0.77）。
3. **粒度只影响 `filter` 口径**：bias 模式的 Recall@K 在**所有**粒度恒为 1.0000——
   「不丢题」是 bias 的设计保证，与粒度无关。这条同时**纠正了一个我此前说错的判断**：
   我曾据「候选池 120→120」推断「召回层在本机是空操作」，但那只是 **bias 模式**的
   必然表现；**filter 模式下它确实裁掉了 6.7% 的题**。

**两个必须知道的局限（诚实记录）**：

- 合成 kp id 在 `t_question_kp` 里不存在 → **不能走 SQL 的 `kp_ids` 过滤**。
  实验因此改为**从映射推导候选池**（`pool = {题 : 合成 kp ∩ 召回 kp ≠ ∅}`），
  并在真实锚点做**交叉验证**：推导 112 == 真跑 filter 112 ✓（两条路径一致才可信）。
  初版真的去跑 filter，得到的是「候选池 0 / Recall@K 0」的**假曲线**。
- 合成粒度下图谱通道与 R5 会退化（合成 kp 不在图谱里、没有 kp 向量）。
  本机图谱为空（`available=False`），故**在当前环境下不产生额外偏差**；
  但**换到有图谱的环境重跑时，这条局限会真实生效**，结论需重新验证。
- 曲线依赖**数据快照**（作答记录/题库变化会小幅移动主值：两次运行在 G=48 上
  差 0.005）——与既有评测的纪律一致，只用趋势与相对比较，不引用绝对值的精度。

#### ② async 修复：`qa_service.ask()` 不再阻塞事件循环

**问题**（`CLAUDE.md` 已知问题第 1 条）：检索与 LLM 调用都是**同步阻塞**的
（openai 同步客户端 / Neo4j 同步驱动 / SQLite），却在 `async def` 里直接执行 →
一个请求占住整个事件循环，同进程内其他请求全部排队。

**位置与修复**：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| `qa_service.ask()` | `async def` 内直接调 `search_related_knowledge()` + `client.chat.completions.create()`（**同步 openai 客户端**，`QA_TIMEOUT=15s`） | 拆出同步实现体 `_ask_blocking()`；`ask()` 改为 `await asyncio.to_thread(self._ask_blocking, ...)` |
| `api/qa.py::ask_question` | `sources = qa_service.search_related_nodes(...)` **直接同步调用**（还会触发 `ensure_index` 建索引） | `await asyncio.to_thread(qa_service.search_related_nodes, ...)` |

**为什么用 `asyncio.to_thread` 而不是 `AsyncOpenAI`**：项目内已有两处先例
（`knowledge_extractor._extract_single`、`relation_completion._call_llm` 都用 `to_thread`）。
沿用同一手法保持一致性，且**不动业务逻辑与异常处理**（原 `try/except` 原样保留在同步体内）。
整体迁移 `AsyncOpenAI` 是更彻底的方向，但要同时改 Neo4j 与 SQLite 的调用方式，
超出本阶段范围（见 ⑥）。

**实测**（`test_qa_async.py` 🆕，**不联网**）：把真正耗时的部分换成 `time.sleep(0.6)`
（货真价实的阻塞调用），跑「2 个并发 `ask` + 1 个快协程」：

| 场景 | 总耗时 | 完成顺序 | 结论 |
|---|--:|---|---|
| **修复后**（`to_thread`） | **0.601s**（= 1 个阻塞时长） | `fast, ask1, ask0` | 并行执行 + **快协程最先完成**（事件循环未被占住） |
| **反证**（把同步体直接写进协程） | **1.203s**（= 2 个） | `ask0, ask1, fast` | 串行 + 快协程被压到最后 |

**反证的意义**：只报「修复后通过」无法排除「测试恒真」。故把修复前的写法也跑一遍，
确认它**必然失败**——A/B 结果相反才说明测试有效。测试 **12/12** 通过，
含端点侧**源码断言**（防止有人把 `search_related_nodes` 改回同步调用）。

#### ③ WAL 修复：SQLite 并发写

**问题**：`_connect()` 原先只设 `PRAGMA foreign_keys = ON`，既无 journal 模式也无
`busy_timeout`。默认 rollback journal 模式下**长读事务会挡住写者提交**
（写者取不到 EXCLUSIVE 锁 → `database is locked`）。而本项目部署形态是
「一个 uvicorn 进程 + 若干 CLI 脚本/评测」共写同一个 `app.db`，
L2 又引入了更长的写事务（121 条向量 / 全量替换关联行 / ≤5000 行 BLOB 回填）；
`sqlite3.connect` 默认 `timeout=5s` 对上述批量写**不够**。

**修复**：

| 项 | 做法 | 位置 |
|---|---|---|
| `journal_mode=WAL` | **库级持久属性**，只在 `init_tables()` 末端设置一次（此时库非空、无并发写事务，最易成功） | `_apply_journal_mode()` |
| `busy_timeout` | **连接级属性**，每连接设置（默认 15000ms） | `_connect()` |
| 可观测 | `pragma_status()` 暴露「请求值 / 实际值 / 错误」 | — |
| 失败处理 | **不抛异常**（网络盘不支持 WAL 时退回流式 journal 不影响正确性），但**不静默丢弃** | — |
| 回退 | `SQLITE_JOURNAL_MODE=delete` / `SQLITE_BUSY_TIMEOUT=0` | — |

**实测**（`test_sqlite_wal.py` 🆕，**13/13** 通过；全部在临时副本上做，不碰线上库）——
决定性 A/B（线程 A 持长读事务，线程 B 尝试写入）：

| 场景 | 结果 |
|---|---|
| **A 反证**：rollback journal + `busy_timeout=300ms` | **失败**：`OperationalError: database is locked` |
| **B 生产**：WAL + `busy_timeout=15000ms` | **成功** |
| A/B 结果相反 | ✓（证明本测试能区分两种 journal 模式） |
| 并发压力：4 线程 × 20 次读写（WAL） | 读 40 / 写 40 / **locked 0** / 其他错误 0 |

实测事实：线上库 `journal_mode` 由 `delete` → **`wal`**，`_connect()` 连接
`busy_timeout = 15000`，`init_tables()` 启动路径 `{'requested': 'WAL', 'actual': 'wal', 'error': None}`。

#### ④ 被 WAL 逼出来的前置修复：备份路径

**发现**：`scripts/backup_migration.py` 原先用 `shutil.copy2(app.db)` **裸拷文件**。
WAL 模式下**最近提交可能还留在 `app.db-wal`** 里 → 拷出来的是
「**静默少数据**」的备份（不报错，事后才发现）；若拷贝恰逢 checkpoint，
还可能拿到**内部不一致**的快照。而文档承诺的回滚方式正是「恢复 `backend/backup/*.bak`」——
**备份静默失效 = 回滚路径静默失效**。所以这件事必须与 WAL 同时落地，
否则本阶段就成了「为了并发可用性，悄悄弄坏了回滚能力」。

**修复**：新增 `sql_db.backup_to(dst)`，用 SQLite 官方 **backup API**
（`sqlite3.Connection.backup`：在写事务边界上取一致快照，且**不阻塞写者**），
并把备份文件的 journal 复位为 `delete` 使其**单文件自包含**；
`backup_migration.py` 改走它。实测（含在 `test_sqlite_wal.py` 内）：

- 备份覆盖**全部 37 张表**、**逐表行数与线上一致** ✓
- 备份文件 journal 已复位 `delete`、可独立打开并读到数据 ✓

> ⚠️ **本轮之前生成的 `backend/backup/app.db.pre_*.bak` 与 `sqlite_*.db` 仍然有效**——
> 它们产生于 WAL 启用**之前**（rollback journal 下主文件本身是完整的）。
> 但**从现在起**任何「裸拷 `.db`」的备份方式都不再可靠，必须走 `backup_to()`。

**顺带**：`.gitignore` 补 `backend/data/*.db-wal` / `*.db-shm`——WAL 边车文件是运行期文件，
不属于版本库；而 `backend/data/app.db` **是被跟踪的**，不过滤会诱导误提交。

#### ⑤ 开关与回滚

| 目的 | 开关 / 手段 |
|---|---|
| 关 WAL（回 rollback journal） | `SQLITE_JOURNAL_MODE=delete`（或对该库 `PRAGMA journal_mode=delete`） |
| 关等待（立刻报 locked） | `SQLITE_BUSY_TIMEOUT=0` |
| 粒度实验 | 本身只读，不改任何数据；删 `eval_data/eval_report_kp_granularity.json` 即可清除产物 |
| async 修复回退 | `git checkout -- backend/app/services/qa_service.py backend/app/api/qa.py` |

#### ⑥ 本轮未做（诚实交代）

- **`AsyncOpenAI` 全量迁移未做**：本阶段只把「问答题链路」移出事件循环；其余 `async def`
  端点里仍有同步 DB / Neo4j 调用（`CLAUDE.md` 第 1 条记录的是**全局**现状）。
  这是**已知未清零**的技术债，不是遗漏——全量迁移要同时处理 Neo4j 与 SQLite 调用路径，
  规模远超 G 的 1.5d 预算。
- **粒度实验的图谱 / 向量通道未补**：合成 kp 没有图谱节点、没有 kp 向量，
  故在**有图谱的环境**重跑时 R1/R3/R5 会退化（本机图谱为空，当前不产生偏差）。
  要在有图谱环境得到可靠曲线，需为合成 kp 补「成员图谱节点的并集」与「成员 kp 向量的均值」，
  或明确接受通道退化。
- **`scan_consistency.py` 未加 WAL 相关检查**：该脚本职责是**数据一致性**；
  pragma 事实已由 `pragma_status()` 提供自查入口，暂不混入。
