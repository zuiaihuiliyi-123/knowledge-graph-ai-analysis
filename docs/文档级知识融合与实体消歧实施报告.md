## 0. 一句话结论

模块已落地并通过全部自建测试与既有回归：**Neo4j 全程只读**，融合状态只落 SQLite，
读图时在 Python 层折叠；**文档级隔离由数据模型强制**；**Dry Run 零写入**；
**撤销不删任何数据**且读图逐字节恢复；在真实数据上**没有任何一次错误自动融合、没有任何跨文档候选**。

同时必须报告两件事：**一次由过时测试脚本导致的 Neo4j 清空事故（已按项目自带脚本恢复）**，
以及当前评测样本规模很小、且指标是在该样本上被改进过的，**不得当作系统整体准确率**。

## 1. 现有架构分析（改代码前核实的真实情况）

### 1.1 抽取链路与一个关键事实

```
POST /api/v1/documents/upload
  → services/document_service.py:70  process_upload（同步：解析→抽取→入图都在请求内完成）
  → utils/text_processor.py:67       chunk_text_for_llm(text, 6000, overlap=400) -> List[str]
  → services/knowledge_extractor.py:300  extract()（每块并发 4 路调 deepseek-chat）
  → services/knowledge_extractor.py:392  _merge_results()
  → services/kg_manager.py:30         build_graph(course_id, document_id, entities, relations)
  → core/database.py:104/132          create_knowledge_node / create_relationship
```

**`_merge_results` 决定了本任务能做什么、不能做什么**：

| 行为 | 位置 | 后果 |
|---|---|---|
| 实体按 `_normalize_entity_name` 后的名字去重，**保留首个的 description** | `knowledge_extractor.py:404-425` | 「同名不同义」在抽取阶段就被折叠，**不改冻结文件则无法拆分** |
| 关系按 `(source,type,target)` 去重，只留首条 evidence | `:472-477` | 跨 chunk 重复关系已去重过一轮 |
| 归一化后自环判为 `synonym_split` 丢弃 | `:465-466` | 与融合的「折叠后自环丢弃」同语义，沿用 |

→ **结论 1：抽取产物里完全没有 chunk 溯源**（无块号、无偏移），`_SYNONYM_MAP` 是空表。
→ **结论 2：本次融合的真正目标只有一类——「同义不同名」**。

### 1.2 存储结构

- **Neo4j**：节点 Label `KnowledgePoint`，MERGE 键 `(course_id, document_id, name)` —— 同名不同文档天然独立。
  节点属性 `kp_id / name / category(中文) / description / confidence / is_manual / created_at / updated_at`。
  关系为四种英文 Cypher 类型之一，中文名存属性 `relation_type`，另有 `confidence / evidence / is_manual`。
- **SQLite**：`t_document` 存文档与抽取状态；`t_kp_embedding` 存知识点向量；`t_kp_text` 是图谱不可用时的降级缓存。
  建表在 `_SCHEMA_SQL`，给已有表加列走 `_migrate_xxx()` + `PRAGMA table_info` 守卫。

### 1.3 文档隔离现状

`services/kg_manager.py:148 get_graph_v1(course_id, document_id, ...)` 的每条 Cypher 都以
`MATCH (n:KnowledgePoint {course_id:$course_id, document_id:$document_id})` 起手 —— **隔离本来就有**，
本模块只需沿用，不新建第二套隔离机制。

### 1.4 三处会造成返工的陷阱（核实后规避）

1. **管理员读不到课程图谱/文档列表**：`api/graph.py:45`、`api/documents.py:51` 走 `require_course_content`，
   管理员非课程成员 → `relation=NONE` → **4003**。故新增管理员专用只读端点与「用 `adminListDocuments` 做文档下拉」。
2. **RAG 索引只改一半会导致每次问答都重建索引**：`embedding.py:66 ensure_index` 用
   `get_embedding_kp_ids(...) != _current_kp_ids(...)` 判新鲜，若只过滤 `_load_kp_records`
   而不过滤 `_current_kp_ids`，两边集合永不相等。
3. **关键词兜底检索会命中已被融合的源节点**：`qa_service._keyword_search` 走
   `WHERE n.name CONTAINS $keyword`，向量索引的过滤挡不住它。

## 3. 融合算法

### 3.1 名称规范化

复用冻结抽取器的 `_normalize_entity_name`（全角→半角、折叠空白、纯英文无空格统一大写、查空 `_SYNONYM_MAP`），
**不覆盖原始名**。分桶键 `normalize_key` 只用于缩小比较范围，**不用于判定相等**。
`C++` 与 `C`、`AVL树` 与 `AVL 树` 刻意保持不同。

### 3.2 候选召回（严格限定同一 `(course_id, document_id)`）

分层，便宜→贵：**正文等价式** → 词面（jieba Jaccard + difflib 序列比值）→ 类别 → 重建上下文 → 可选 Embedding。
零新增依赖（不引入 rapidfuzz）。

**硬负门（命中即抑制，不看分数）**：两实体间存在 `CONTAINS`/`PRECEDES`/`APPLIES_TO` 边（上下位/依赖 ≠ 同义）；
`is_manual` 节点默认不允许被折掉。

### 3.3 评分模型（**曾经不可用，已重构**）

初版把「类别相同」做成 **+0.15 的加项**，实测在某 68 点文档上**产出 359 对候选**，榜首全是
`原子/原子核`、`金属/类金属` 这类上下位。根因是结构性缺陷而非参数问题：该文档类别几乎全是「概念」，
该类项对**所有**实体对恒为满分，等于垫了一层地板分；文档只切出 1 块时上下文项也恒为 1.0。

重构后：

- 类别一致性改为**乘性惩罚**（相同 1.0 / 概念↔方法 0.85 / 其余 0.60）；
- 上下文增加 `discriminative` 判据（单块文档、或命中全部分块 → 该项判为**不可用**而非满分）；
- 子串对按长度比打折（`原子/原子核` 重罚、`…命名法/…命名` 轻罚）；
- 新增**「正文等价式」**信号：文档正文里直接写出 `甲（乙）` 才算强证据；
- 包含式命中要求词长 ≥3（2 字中文词几乎出现在任何相关条目里，是噪声主源）。

**结果：359 → 24 对。** 这类判断的依据是"模型必须能解释自己为什么认为两个名字指同一个东西"。

### 3.4 决策与阈值（集中在 `fusion_config.py`，并快照进 `run.config_json`）

```
score >= AUTO_SAME(0.86)            → SAME
[REVIEW(0.62), AUTO_SAME)           → 送 LLM；LLM 不可用则 UNCERTAIN
[RECALL(0.45), REVIEW)              → UNCERTAIN（人工复核池）
< RECALL(0.45)                      → 不建候选
```

这些是**保守的工程参数**，不是经过验证的最优值。两次「托底」都刻意停在 REVIEW 档而不给 SAME：
命中正文等价式、以及两节点规范化后同名（`cnn`/`CNN` 这类 MERGE 键用原始名导致的漏网之鱼）。

### 3.5 LLM 语义消歧

仅对 REVIEW 档调用；**可注入**（测试用假实现，不真调外部 API）；严格 JSON 校验。
**降级契约：超时 / 非法 JSON / 字段不合规 / 服务不可用 / 未配置 key —— 一律 UNCERTAIN，绝不 SAME。**
该契约由 `test_fusion_resolver.py` 穷举六类异常断言。

### 3.6 重建的文本命中上下文（**不是原始抽取证据**）

抽取阶段没有保留 chunk 溯源，因此上下文只能"重新分块 + 按名称命中"重建。
API 字段、前端文案、报告一律称**「重建的文本命中上下文」**，并携带 `reconstruction_ok`；
重建失败时 `w_ctx` 权重**整体剔除**（而非当 0 分），且不得据此推断同义。

## 4. 文档隔离机制

| 层 | 如何保证 |
|---|---|
| 数据模型 | 五张融合表全部以 `(course_id, document_id)` 建行；`t_kp_fusion_map` 的 UNIQUE 是 `(course_id, document_id, source_kp_id)` |
| 服务层 | 所有入口先过 `_check_scope`：文档存在 && `t_document.course_id == course_id`，不符即 4001/4003 |
| 候选生成 | 只接收同一文档的 nodes/edges；`generate_candidates` 的输出端点必属于输入集合（有断言） |
| 应用 | 逐条校验候选归属；跨文档候选直接拒绝且**不写入任何映射** |
| 读图 | 折叠映射按 `(course_id, document_id)` 读取，无映射的文档是纯 no-op |
| 评测 | 对 14 个真实文档逐一扫描，**跨文档候选 0 个** |

## 5. 数据库变更

### 5.1 SQLite（5 张新表，全部写进 `_SCHEMA_SQL`）

`t_kp_fusion_run`（批次）、`t_kp_fusion_candidate`（候选，**跨 run 复用**）、
`t_kp_fusion_map`（**读图折叠的唯一数据源**）、`t_kp_fusion_conflict`（冲突）、
`t_kp_fusion_scope`（融合 epoch）。

- **新表用 `CREATE TABLE IF NOT EXISTS`，不需要 `_migrate_xxx`**（迁移仅用于给已有表加列或重建 CHECK）。
- `document_id` / `kp_id` **不设物理外键**（与 `t_kp_embedding`、`t_kp_text` 同一先例；`_connect()` 默认开
  `PRAGMA foreign_keys=ON`，设 FK 会让删文档的手工级联直接报错）。
- 唯一索引两处是**不变量的载体**：候选 `UNIQUE(course,doc,src,tgt)` 保证"驳回可记忆"；
  映射 `UNIQUE(course,doc,source)` 保证"目标唯一"。

### 5.2 Neo4j

**零变更**：不新增标签、不新增关系类型、不新增属性、不删任何节点或关系。融合结果通过读图折叠生效。

### 5.3 兼容性

所有新表在新库与旧库上都由 `init_tables()` 幂等创建，既有表结构与数据不受影响
（`test_fusion_migration.py` 在同一副本库上连跑三次 `init_tables()` 并逐表比对行数）。

## 9. 评估结果

### 9.1 样本

`eval_data/entity_resolution_gold.json`：**93 对（SAME 20 / DIFFERENT 73）**，来自 14 个真实文档。

- **正样本**：在真实正文里搜「实体名（另一种写法）」形态，且括号里的写法在本 doc 的实体表中不存在；
  构建后**逐条人工复核**，只保留确为"同一概念的另一名称"的（中文↔英文名/缩写/学名）。
  括号里写的是**定义**的（如「摩尔（论了物质的宏观质量…）」）一律剔除——这类占原始命中一多半。
- **负样本**：① 同文档内一个是另一个真子串的对（`原子`/`原子核`）；② 存在
  `CONTAINS`/`PRECEDES`/`APPLIES_TO` 关系的对；③ 共享缩写前缀的对（`CFS`/`FCFS`）。
  标签以**标注**为准：同一文档里被标成两个知识点的实体就是不同的两个。

### 9.2 指标

| 口径 | Precision | Recall | F1 |
|---|---|---|---|
| **候选闸门**（捞出给人看） | **0.909** | **1.000** | **0.952** |
| **自动融合闸门**（不经人直接融合） | 0.000 | 0.000 | 0.000 |

- **False Merge（把不同实体自动融合）：0 次**
- 落在 UNCERTAIN 档（进人工复核池）：2/93 = 2.1%
- 漏掉的真正同义对：0
- 文档隔离：检查 14 个文档的候选端点，**跨文档候选 0 个**
- 按类型：`explicit_alias` 进候选 100%；`relation` 0%；`substring` 6.5%；`symbol_clash` 0%

自动融合闸门全零是**预期的**：正确行为是"什么都不自动合并，把判断留给人"。

### 9.3 必须写明的限制

1. **样本量小（SAME 仅 20 条），不得据此宣称系统整体准确率。**
2. **本批数字偏乐观**：模块的「正文等价式」这一支，正是因为在本样本上第一版只跑到
   Recall 0.05（1/20）才补上的。指标与改进发生在同一批样本上，换一批文档不可能有这么高。
3. 正样本的「另一端」多数并非图节点，是按真实正文写出的别名重构的轮廓（类别与定义留空），
   这**低估**了模块在有完整定义时的表现。
4. 正样本规模小是**方法层面的上限**：抽取 Prompt 要求同义写法只保留一个规范名，人工标注也遵循
   同一约定，因此既有 gold 里几乎没有「同义不同名」的节点对——`gold_*.json` 13 份语料共 404 个实体，
   收割到的显式等价对为 **0**。
5. 得分与置信度是内部度量，**不等于准确率**。

### 9.4 一次事故与修复（必须记录）

**事故**：本轮跑既有回归时执行了 `test_upload_flow.py`。该脚本第 32 行是一句

与清空前的 626/655 存在差额，原因是重抽取的随机性与分块差异——**这是有损恢复，不是逐字还原**。
SQLite 业务数据（用户/课程/文档/题目/学习记录/收藏/成员）全程与基线逐项一致。

**排雷**：两处同类隐患已拆除——

## 10. 风险与后续建议

| 风险 | 现状与建议 |
|---|---|
| **同名不同义在抽取阶段已被合并，不可恢复** | `_merge_results:404-425` 按规范名去重只留首条 description。本模块无法拆分（不改冻结文件）。若要支持，需改造抽取器保留 chunk 级结果——属于 V1.2 的范围 |
| **重建上下文可能因重解析漂移而不一致** | 已标注为"重建"、携带 `reconstruction_ok`、失败时剔除权重且不参与同义推断。可选加固：上传时落一份解析文本缓存 |
| **管理端平台统计口径偏差** | `admin_service.py:502-512` 按课程直查 Neo4j、不折叠，与融合后的文档视图数字对不上。`/overview` 同时给两个口径并标注，**不静默改口径** |
| **教师删"折叠边"** | 删的是底层存活边（折叠不产生新边），UI 未特别标注，建议后续补提示 |
| **`LIMIT` 与折叠** | Cypher 的 LIMIT 发生在折叠之前，被折节点仍占配额。当前文档规模下无影响 |
| **LLM 非确定性** | 决策落库冻结；重扫不覆盖已审核候选（除非显式 `force`） |
| **评测样本不足以支撑结论** | 建议扩充方式：为若干文档做**独立的人工同义标注**（不看本模块输出），再跑一次；本批 gold 已被用于调参，不能作为最终成绩 |
| **跨文档知识对齐** | 明确**不在本次范围**，应作为独立功能设计 |
| **Neo4j 无备份机制** | 本次事故暴露：Neo4j 不进仓库、也没有定期备份，一次误操作即全损。建议加一个定期 `backup/neo4j_*.json` 的导出脚本（仓库里已有一份 2026-09-05 的手工导出，格式可沿用） |
