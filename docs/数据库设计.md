# 数据库设计说明

> 本文档汇总系统当前的数据存储设计，来源为代码与运行库实际定义：关系型数据见 `backend/app/core/sql_database.py`（建表 `_SCHEMA_SQL` + 幂等迁移 `_migrate()`），图数据见 `backend/app/core/database.py`。
>
> **最后校验：2026-09-23**（对照 `backend/data/app.db` 实际结构逐字段核对；含课程中心、题库、**L2 一题多知识点**与**L2 阶段 E 向量 BLOB**）
>
> 系统采用**双存储**：SQLite（关系型，存用户/课程/成员/文档/学习记录/题库/向量）+ Neo4j（图，存知识点与关系）。

---

## 一、存储架构

| 存储 | 类型 | 存什么 | 落地文件/模块 |
|------|------|--------|---------------|
| SQLite | 关系型 | 用户与资料、课程与成员、文档、学习记录、收藏、知识点向量、题库 | `backend/app/core/sql_database.py` |
| Neo4j | 图数据库 | `KnowledgePoint` 节点 + 四类关系 | `backend/app/core/database.py` |

- `course_id` 三端统一为**整数**：SQLite 自增整数 → Neo4j 存整数属性 → API 传整数。
- `t_learning_record.kp_id` / `t_student_favorite.kp_id` / `t_question.kp_id` / `t_question_kp.kp_id` 均为**逻辑外键**，指向 Neo4j 的 `KnowledgePoint`，不建物理外键（跨库无法建）。
- **L2 一题多知识点（2026-09-22）**：`t_question_kp` 是题目-知识点关联的**权威数据**（一题可挂 N 个 kp），`t_question.kp_id` 退化为它的**主知识点冗余投影**——两者由 `SQLDatabase.set_question_kps()` 同事务维护，因此读侧（前端 / 统计 / 兼容期调用方）看到的 `kp_id` 语义不变。详见 2.10 / 2.15。
- 第一阶段用 SQLite（零部署、Python 标准库）；第二阶段迁移 MySQL 仅替换 `sql_database.py` 底层连接实现，表名、字段名、方法签名保持不变，业务代码零改动。
- 新增列一律走 `_migrate()` 的 `ALTER TABLE`（不写进 `CREATE TABLE`），以保证「新建库」与「迁移库」表结构不分叉——详见第七章。

## 二、SQLite 关系型表（16 张）

按领域分组：用户与资料（2.1–2.2）、课程与成员（2.3–2.5）、文档（2.6）、学习数据（2.7–2.9）、题库（2.10–2.12、**2.15**）、向量与缓存（2.13–2.14）、级联清理（2.16）。

> 表数量以 `_SCHEMA_SQL` 实数（**16 张**）为准。其中 `t_question_import_batch`（Scope D 导入批次）尚未在此单列字段明细，字段定义见 `backend/app/core/sql_database.py` 与 [题库功能说明.md](题库功能说明.md)。

### 2.4 t_course_member 课程成员表

用户 ↔ 课程的多对多关系表，**替代「把学生硬编码进课程表」的做法**。教师与学生在同一张表内，用 `role` 区分。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| member_id | INTEGER | PK AUTOINCREMENT | 主键 |
| course_id | INTEGER | NOT NULL，FK → t_course(course_id) | 课程 |
| user_id | INTEGER | NOT NULL，FK → t_user(user_id) | 用户 |
| role | TEXT | NOT NULL DEFAULT 'student'，CHECK ∈ {teacher, student} | 课程内角色 |
| status | TEXT | NOT NULL DEFAULT 'pending'，CHECK ∈ {pending, approved, rejected, removed} | 成员状态 |
| join_source | TEXT | NOT NULL DEFAULT 'code'，CHECK ∈ {create, code, invite, apply, import} | 加入来源 |
| applied_reason | TEXT | | 申请理由（发现课程页申请时填写） |
| reviewed_by | INTEGER | 可空 | 审核人（教师） |
| reviewed_at | TEXT | 可空 | 审核时间 |
| review_comment | TEXT | 可空 | 审核意见 |
| joined_at | TEXT | 可空 | 正式加入时间（approved 时才写入） |
| created_at / updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 时间戳 |

约束：`UNIQUE (course_id, user_id)`——同一用户在同一课程至多一条关系，重复加入不产生脏数据
索引：`idx_cm_course_status (course_id, status)`、`idx_cm_course_role (course_id, role)`、`idx_cm_user_status (user_id, status)`

> **状态语义**：只有 `status='approved'` 才视为课程成员并放行**内容访问**（文档/图谱/问答/学习路径）；`pending` / `rejected` / `removed` 仅有**元数据级**读取权，用于查看自己的申请状态，访问内容一律 4003。被移除的学生再次用加课码加入时，服务层强制回落为 `pending`，不因 `join_mode='auto'` 自动放行——避免泄露出去的加课码撤销教师的「移除」决定。
>
> 教师创建课程时自动写入 `role='teacher', status='approved', join_source='create'`。

### 2.9 t_kp_embedding 知识点向量表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| course_id | INTEGER | PK（复合主键）NOT NULL | 课程 |
| kp_id | TEXT | PK（复合主键）NOT NULL | 知识点 |
| document_id | INTEGER | 可空 | 所属文档 |
| embedding | TEXT | NOT NULL | 向量（JSON 数组文本，**兼容保留**） |
| embedding_blob | BLOB | 可空 | **L2 阶段 E**：float32 小端向量；检索优先读它（体积 5.55×↓、免 JSON 解析）。为空时读取回落解析 `embedding` |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 更新时间 |

主键：`(course_id, kp_id)`

> 无外键。`document_id` 无索引（当前检索按 `(course_id, kp_id)` 走主键）。
> `embedding_blob` 由 `_migrate_embeddings_blob()` **限量回填**（每次启动 ≤5000 行，幂等续跑）；
> 写入方（`upsert_kp_embedding`）**双写**两列，因此未回填完的历史行也能正常读。

### 2.10 t_question 题目表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| question_id | INTEGER | PK AUTOINCREMENT | 主键 |
| course_id | INTEGER | NOT NULL，FK → t_course(course_id) | 归属课程 |
| document_id | INTEGER | 可空 | 空 = 课程通用题；非空 = 挂到具体文档 |
| kp_id | TEXT | 可空 | **主知识点（冗余投影）**：真正的关联见 `t_question_kp`（2.15）。本列由 `set_question_kps()` 同事务同步，读侧语义不变；空值统一为 `NULL` |
| q_type | TEXT | NOT NULL，CHECK ∈ {SINGLE, MULTI, JUDGE, FILL, ESSAY} | 题型（Scope B 扩两型主观题） |
| stem | TEXT | NOT NULL | 题干 |
| options | TEXT | | 选项/空位（JSON 文本）：选择 `[{"key":"A","text":"..."}]`；**填空** `[{"key":1,"label":"第1空","hint":"单位 kg","score":50,"answer":"浮点数"}]` |
| answer | TEXT | NOT NULL | 答案（JSON 文本）：单选 `"A"` / 多选 `["A","C"]` / 判断 `"true"` / 填空 `["浮点数","0.5"]`（参考答案数组）/ 解答 `"参考答案正文"` |
| analysis | TEXT | | 解析（提交后展示给学生） |
| difficulty | INTEGER | NOT NULL DEFAULT 3，CHECK BETWEEN 1 AND 5 | 难度 |
| source | TEXT | NOT NULL DEFAULT 'MANUAL'，CHECK ∈ {MANUAL, AI, IMPORT} | 来源 |
| created_by | INTEGER | NOT NULL，FK → t_user(user_id) | 创建教师 |
| is_active | INTEGER | NOT NULL DEFAULT 1，CHECK ∈ {0,1} | 启用状态（0 = 停用，等价软删） |
| created_at / updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 时间戳 |

索引：`idx_q_course_doc (course_id, document_id)`、`idx_q_kp (kp_id)`、`idx_q_type (course_id, q_type)`

> `options` / `answer` 用 JSON 文本而非拆表：题型差异大（拆表会产生大量空列）；且必须 `json.dumps` 统一序列化，否则单选答案 `"A"` 无法回读、判断答案 `"true"` 会被误读成布尔值。

### 2.11 t_answer_record 学生答题记录表

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| record_id | INTEGER | PK AUTOINCREMENT | 主键 |
| user_id | INTEGER | NOT NULL，FK → t_user(user_id) | 学生 |
| course_id | INTEGER | NOT NULL，FK → t_course(course_id) | 课程 |
| document_id | INTEGER | 可空 | 题目所属文档（课程通用题为空） |
| question_id | INTEGER | NOT NULL，FK → t_question(question_id) | 题目 |
| user_answer | TEXT | | 学生作答（JSON 文本，与 answer 同结构） |
| is_correct | INTEGER | NOT NULL DEFAULT 0，CHECK ∈ {0,1} | 是否答对（主观题未批改时为占位 0，须按 grade_status 过滤） |
| score | REAL | NOT NULL DEFAULT 0 | 得分（客观题 0/100；主观题批改后 0~100 可为部分分） |
| grade_source | TEXT | NOT NULL DEFAULT 'AUTO'，CHECK ∈ {AUTO, LLM, TEACHER} | 判分来源（主观题批改后为 TEACHER） |
| grade_status | TEXT | NOT NULL DEFAULT 'GRADED'，CHECK ∈ {PENDING, GRADED} | 批改状态：主观题提交写 PENDING（不判分） |
| graded_by | INTEGER | 可空 | 批改教师 user_id（逻辑外键，不设 FK：教师注销不应破坏记录） |
| graded_at | TEXT | 可空 | 批改时间 |
| comment | TEXT | 可空 | 教师评语（学生可见） |
| answered_at | TEXT | NOT NULL DEFAULT 本地时间 | 作答时间 |

索引：`idx_ans_user_q (user_id, question_id)`、`idx_ans_user_c (user_id, course_id, document_id)`

> **追加式**（不建 UNIQUE）：同一题可多次作答；错题本取「每题最近一次答错」，同时保留历史，便于统计正确率趋势。
>
> **Scope B 批改是「就地更新」**：教师批改直接 UPDATE 同一行（score/is_correct/grade_status/grade_source/graded_by/graded_at/comment），不留批改历史版本；重批即覆盖。
> 旧库迁移用 `ALTER TABLE ADD COLUMN`（默认 `GRADED`，保证历史行与客观题行为零变化）；SQLite 的 ADD COLUMN 不能带 CHECK，旧库取值合法性由应用层 `ANSWER_GRADE_STATUS` 兜底。

| name | TEXT | NOT NULL | 知识点名称（字面匹配用） |
| category | TEXT | | 类别 |
| description | TEXT | | 描述 |
| updated_at | TEXT | NOT NULL DEFAULT 本地时间 | 缓存时间 |

索引：`idx_kp_text_scope (course_id, document_id)`。写入时机：每次从 Neo4j 成功取到知识点清单后**覆盖式更新**。

> 独立于 `t_student_favorite`（知识点收藏）：后者 `kp_id NOT NULL` 且语义为「知识点书签」，混用会污染两侧统计口径。

### 2.15 t_question_kp 题目-知识点关联表（L2：一题多知识点）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| question_id | INTEGER | PK 之一，FK → t_question(question_id) | 题目 |
| kp_id | TEXT | PK 之一 | 逻辑外键 → Neo4j KnowledgePoint |
| score | REAL | 可空 | 标注置信度（`kp_labeler` 自动标注产物） |
| source | TEXT | NOT NULL DEFAULT 'MANUAL'，CHECK ∈ {MANUAL, AI, IMPORT} | 关联来源（与 `QUESTION_SOURCE` 同口径） |
| is_primary | INTEGER | NOT NULL DEFAULT 0，CHECK ∈ {0,1} | 是否「主知识点」 |
| created_at | TEXT | NOT NULL DEFAULT 本地时间 | 建立时间 |

主键：`(question_id, kp_id)`（同题同 kp 天然幂等）

索引：

- `idx_qkp_kp (kp_id)`——按知识点反查题目（出题 / 覆盖率）
- **`uq_qkp_primary`：`UNIQUE (question_id) WHERE is_primary = 1`**（**部分唯一索引**）——「一题最多一个主知识点」由 DB 层保证而非应用层自觉；SQLite 部分索引自 3.8.0 起支持

**写入纪律**：本表是题目-知识点关联的**唯一事实来源**，`t_question.kp_id` 是它的投影（见 2.10）。兼容期内**只有 `SQLDatabase.set_question_kps()` 一个写入口**，它在一个事务里完成「删除旧关联 → 重建新关联 → 同步投影」，并在应用层归一化（去空、去重、保序、`primary` 不在列表时兜底取首项）。`create_question` / `update_question` / `QuestionService.import_commit` 均经它落库；`update_question` **只在调用方显式传入 kp 字段时**才写关联——否则「教师只改难度」会把多 KP 题**塌缩**成单 KP。

**上限**：`question_service.MAX_KP_PER_QUESTION = 10`（防误传超大数组；同时为组卷的「任一命中即占用配额槽」留出上界）。

**迁移**：`_migrate_question_kp()` 只回填「关联表中无任何行」的题——若已有 `is_primary=1` 的行（教师后续编辑产生）再按 `t_question.kp_id` 插一行主 kp，会同时触碰 `uq_qkp_primary` 导致后端启动即崩。详见第七章。

> L2「一题多知识点」的完整设计、语义口径（决策 1/2/3/4）、验证结果与回滚方式见 [题库与推荐系统设计.md](题库与推荐系统设计.md) §13。

### 2.16 级联清理（防孤儿数据）

**SQLite 未开启外键级联**，所有级联删除都在 `SQLDatabase.delete_course()` / 文档删除路径内按「子表 → 主表」顺序显式执行。

| 触发 | 清理范围 | 说明 |
|------|----------|------|
| 删除题目 | 该题的**知识点关联** + 收藏 + 答题记录 → 题目本身 | `t_question_kp` 有物理外键且连接已开 `PRAGMA foreign_keys=ON`，**必须先删关联行**否则抛 FK 错误；已被作答过的题目由服务层降级为软删（`is_active=0`） |
| 删除文档 | 该文档精确挂载的题目 & 其**知识点关联**/收藏/答题记录 | 课程通用题（`document_id IS NULL`）刻意保留 |
| 删除课程 | 向量、知识点收藏、学习记录、**成员、邀请**、题目**知识点关联**/收藏/答题记录/题目、文档 → 课程本身 | 顺序不可颠倒，否则留下指向已删课程的孤儿行 |

> 成员/邀请的清理在课程中心改造时补入：此前删课会残留 `t_course_member` 行。
> `t_question_kp` 的清理在 L2「一题多知识点」改造时补入，覆盖 4 个删除点：`delete_question` / `delete_course` / `delete_questions_by_course` / `delete_questions_by_document`。

## 七、迁移机制（无 Alembic）

项目未引入迁移框架，schema 演进靠 `SQLDatabase.init_tables()` 在**每次后端启动**时执行，全程幂等：

```
init_tables()
├─ 逐条执行 _SCHEMA_SQL              # 全部 CREATE TABLE / CREATE INDEX IF NOT EXISTS
├─ _migrate()
│  ├─ 1) document_id 补列与回填       # t_learning_record / t_student_favorite / t_kp_embedding
│  ├─ 2) _migrate_question_bank()     # 题库：t_answer_record 批改列 + t_question 导入列
│  ├─ 3) _migrate_question_kp()       # L2：t_question.kp_id → t_question_kp 主知识点回填
│  ├─ 4) _migrate_embeddings_blob()   # L2 阶段 E：向量表补 embedding_blob + 限量回填
│  └─ 5) _migrate_course_center()     # 课程中心改造
└─ _migrate_question_types()          # t_question 重建（扩 q_type CHECK；需独立连接）
```

`_migrate()` 的各段都是「先探测、再变更」，重复执行结果一致：

1. **`document_id` 补列**：`PRAGMA table_info` 守卫，缺列才 `ALTER TABLE ADD COLUMN`；随后仅回填 `document_id IS NULL` 的行（历史数据「一课程 == 一文档」，可安全映射）。
2. **`_migrate_question_bank()`**：给 `t_answer_record` 补「批改」相关列（`_ANSWER_NEW_COLUMNS`；`grade_status` 默认 `GRADED`，保证历史记录口径不变），并给 `t_question` 补 Scope D 的导入批次/暂存状态列（`_QUESTION_NEW_COLUMNS`）——后者必须**先于** `_migrate_question_types()` 的重建，才能被一起拷过去。
3. **`_migrate_question_kp()`**（L2）：把 `t_question.kp_id` 回填为 `t_question_kp` 的 `is_primary=1` 行。**判据必须是 `NOT EXISTS (SELECT 1 FROM t_question_kp k WHERE k.question_id = q.question_id)`**——只回填「关联表中无任何行」的题；若只靠 `INSERT OR IGNORE`，已有主知识点的题会被再插一行 `is_primary=1`，同时触碰 `uq_qkp_primary` 部分唯一索引，导致**后端每次启动即崩**。
4. **`_migrate_embeddings_blob()`**（L2 阶段 E）：给 `t_kp_embedding` / `t_question_embedding` 补 `embedding_blob BLOB`，并把 `embedding`(JSON) **限量**转成 float32 BLOB（每次启动 ≤ 5000 行）。限量是刻意的：5 万条 JSON 全量解析约 18 秒，会拖慢启动；重复启动幂等续跑，`backfill_embedding_blobs()` 可显式全量执行。
5. **`_migrate_course_center()` 四步**：
   - `PRAGMA table_info(t_course)` 守卫，逐个补 `_COURSE_NEW_COLUMNS` 中的 6 列；
   - `CREATE UNIQUE INDEX IF NOT EXISTS uq_course_join_code`；
   - 仅为 `join_code IS NULL` 的课程生成加课码（冲突重试至多 20 次）——**教师已发出的码不会被重新生成**；
   - `INSERT OR IGNORE INTO t_course_member ... SELECT ... FROM t_course`，把每门已有课程的 `teacher_id` 变成 `role='teacher'/status='approved'` 成员。靠 `UNIQUE(course_id, user_id)` 保证幂等，且不覆盖教师后续手动改动过的成员行。

**四条重要约束**：

- 新增列**只写 `_migrate()`、不写 `CREATE TABLE`**。若两边都写，新建库与迁移库的表结构会分叉（列顺序、默认值不一致）。
- SQLite 的 `ALTER TABLE ADD COLUMN` **不允许带 UNIQUE / PRIMARY KEY**。`join_code` 若直接写成 `ADD COLUMN join_code TEXT UNIQUE`，后端会**启动即崩**。
- **新增「表」时相反：写进 `_SCHEMA_SQL` 的 `CREATE TABLE IF NOT EXISTS`**（连同 `CREATE INDEX IF NOT EXISTS`，天然幂等，不需要 ALTER）。`t_question_kp` 与 `uq_qkp_primary`（部分唯一索引）即按此办理。
- 新表若带**物理外键指向 `t_question`**，须注意两点：① `_migrate_question_types()` 会 DROP/重建 `t_question`（该连接内先关 `foreign_keys`，末尾用 `PRAGMA foreign_key_check` 兜底）；② 所有删除路径必须**先删新表的行、再删题目**——连接默认 `foreign_keys = ON`，顺序反了会直接抛 FK 约束错误。

**历史课程不猜测学生成员关系**：迁移只回填教师，学生需通过加课码 / 邀请 / 申请重新加入。

**回滚方式**：恢复 `backend/backup/app.db.pre_*.bak`；或按外键反序 DROP 新增表、DROP 索引、DROP 新增列。

## 八、连接与并发（pragma）+ 备份

### 8.1 连接 pragma（`_connect()`）

| pragma | 值 | 作用域 | 说明 |
|---|---|---|---|
| `foreign_keys` | `ON` | 连接级 | 级联与 FK 约束；**所有**删除路径依赖它，顺序错了会直接抛错 |
| `busy_timeout` | `15000` ms | 连接级 | 写者互斥时**等待**而非立刻报 `database is locked`。默认 `sqlite3.connect` 的 `timeout=5s` 对批量写不够 |
| `journal_mode` | `WAL` | **库级、持久** | 读不阻塞写、写不阻塞读（只有写-写串行）。只在 `init_tables()` 末端设置一次 |

**为什么需要 WAL**：部署形态是「一个 uvicorn 进程 + 若干 CLI 脚本/评测」共写同一个
`app.db`；rollback journal 模式下**长读事务会挡住写者提交**，而 L2 引入的批量写入
（121 条向量 / 全量替换关联行 / ≤5000 行 BLOB 回填）又让写事务变长 —— 两头一夹就撞锁。

- 失败**不抛异常**：网络盘等不支持 WAL 时退回流式 journal，正确性不受影响；
  但状态会被 `sql_db.pragma_status()` 保留（`requested` / `actual` / `error`），不静默丢弃。
- 回退开关：`SQLITE_JOURNAL_MODE=delete`、`SQLITE_BUSY_TIMEOUT=0`。
- **边车文件**：WAL 会产生 `app.db-wal` / `app.db-shm`（运行期文件，已加入 `.gitignore`）。
- ⚠️ **`backend/data/app.db` 被 git 跟踪**：WAL 下「主文件」可能不含最近提交，
  提交前应先让写事务结束/触发 checkpoint（最稳妥是出一份 `backup_to()` 快照再提交，
  或把该文件移出版本库）。这与 8.2 的裸拷问题是同一个坑。

### 8.2 备份必须走 `backup_to()`，不能裸拷文件

```python
fact = sql_db.backup_to("backup/sqlite_<ts>.db")   # 官方 backup API，WAL 安全
```

**为什么不能 `shutil.copy2(app.db)`**：WAL 模式下**最近提交可能还留在 `app.db-wal`** 里，
裸拷主文件会得到「**静默少数据**」的备份（不报错，事后才发现）；拷贝恰逢 checkpoint 时
还可能拿到内部不一致的快照。而回滚方式正是「恢复 `backend/backup/*.bak`」——
**备份静默失效 = 回滚路径静默失效**。

`backup_to()` 的行为：`sqlite3.Connection.backup` 取**写事务边界上的一致快照**（不阻塞写者），
并把备份文件 journal 复位为 `delete` 使其**单文件自包含**（无需连 `-wal` 一起拷）；
返回逐表行数便于与线上核对。`scripts/backup_migration.py` 已改走它。

> 启用 WAL **之前**生成的 `app.db.pre_*.bak` / `sqlite_*.db` 仍然有效
> （rollback journal 下主文件本身完整）；**之后**必须用 `backup_to()`。
