## 一、提示词工程总体设计

### 1.1 提示词在系统中的位置

系统主链路是：**课程文档 → 大模型抽取知识点与关系 → Neo4j 知识图谱 → 图谱可视化 / RAG 问答 / 学习路径推荐**。

大模型在这条链路上承担两个环节，对应两条**核心提示词**：

| 环节 | 提示词 | 作用 |
|---|---|---|
| 知识抽取 | **P1** | 把课程文本转成知识点实体与它们之间的关系，决定图谱里有什么 |
| 智能问答 | **P3** | 把检索到的图谱知识点组织成回答，决定学生看到什么 |

其余提示词或服务于**辅助能力**（P2 关系补全、P8 试题抽取），或属于**离线数据准备**（P6/P7），或属于**研发辅助**（P4/P5），均不参与产品主链路。本文档按此主次分层组织。

模型接入：统一使用 `openai` SDK 的 OpenAI 兼容接口。推理走 DeepSeek `deepseek-chat`；向量化走 SiliconFlow `BAAI/bge-m3`（DeepSeek 不提供 embedding 接口，故这一步必须用另一家）。配置位置 `backend/app/core/config.py`。

### 1.3 统一设计原则

全部提示词遵循四条共同原则：

1. **输出形态与下游消费方式匹配。** 凡输出要被程序解析的提示词（P1、P2、P4、P5、P7、P8），一律要求「严格只输出 JSON，不要 Markdown 代码块、不要解释文字」，并在 System Prompt 中重申；凡输出本身就是最终交付物的提示词（P3 问答、P6 翻译），则要求只输出目标内容、不附加解释或前后缀。两类约束的目标一致——**消除输出中的非交付内容**，区别只在交付物是结构化数据还是自然语言正文。
2. **宁缺毋滥（针对抽取类）。** P1、P8 明确「证据不足宁可不输出」「不要臆造」。图谱与题库一旦混入臆造内容，教师须逐条核对，自动化反而降低效率。
3. **证据可溯源。** P1 要求每条关系携带 `evidence`（原文短句）。这是抽取结果可人工核验的基础。需要区分的是：`evidence`/`confidence` 服务于**可核验性**，而**准确性只由人工标注的 Gold 数据计算的 P/R/F1 衡量**（见 6.2 节）。`confidence` 是模型自评，**在任何意义上都不等于准确率**。
4. **低温度采样。** 涉及分类判断的任务 temperature ≤ 0.15；仅开放生成类（问答）放宽到 0.3。降低温度降低的是**采样随机性**，**不等于结果严格确定**——即使 temperature=0，大模型输出仍不完全可复现。因此本项目采用**预测落盘**纪律：正式评测只跑一次并把模型输出写入 `pred_*.json`，此后所有评分、调参、出图都基于同一份预测文件（见 6.5 节）。

## 二、核心 Prompt

### 2.1 P1 知识抽取提示词

代码位置：`backend/app/services/knowledge_extractor.py`；版本号冻结于 `backend/eval_config.py`（当前 `PROMPT_VERSION = "v1.5"`）。完整原文见**附录 A**。

#### 2.1.1 为什么需要它

系统的所有下游能力都以图谱内容为前提：可视化展示的是它抽出来的节点和边，路径推荐遍历的是它抽出的 `PRECEDES` 边，RAG 问答检索的是它抽出的知识点描述。**抽取错了，后面全错**。因此 P1 是全系统唯一需要完整迭代记录与量化评测的提示词。

抽取任务本身有两个特点，决定了它的提示词不能简单：一是**粒度判断**（什么算一个「知识点」而不是一句普通叙述），二是**关系判定**——四种关系之间边界容易混淆，尤其是「X 是 Y 的一种」（包含）与「必须先学 X 才能学 Y」（前置）这两种在中文教材里句式高度相似。

#### 2.1.2 设计要点

P1 正文由十节构成（完整原文见附录 A），核心是下面五点。

**（1）关系判定用决策树，不用平行规则。** 对任意两个知识点，**按固定顺序**依次判断，命中即停：

```
① X 是 Y 的一种 / 子类 / 特殊形式 / 典型操作  → CONTAINS（source 为上位概念）
② 文本明确表达「学习 source 是理解 target 的必要前提」→ PRECEDES
③ source 是方法/算法/技术，且用于实现/解决 target 这类问题 → APPLIES_TO
④ 文本明确说明二者密切关联（工具-主体、并列类似）→ RELATED_TO
⑤ 以上均不满足或证据不足 → 不输出
```

固定顺序把「在四条平行规则里自由选择」变成「互斥的有序判定」，从机制上消除规则间冲突。这是 v1.2 的结构性改动，此后未再变动。

**（2）每一个易错边界都给反例。** 只给正例，模型会照搬句式；给反例，模型才知道边界在哪。例如：

| 文本 | 正确判定 | 常见错误 |
|---|---|---|
| 「栈是一种操作受限的线性表」 | 线性表 CONTAINS 栈 | 误判 PRECEDES |
| 「要学习多态，必须先掌握继承」 | 继承 PRECEDES 多态 | 误判 CONTAINS |
| 「深度优先遍历通常基于递归实现」 | 递归 APPLIES_TO 深度优先遍历 | 方向颠倒 |
| 「广度优先遍历借助队列实现」 | 队列 RELATED_TO 广度优先遍历 | 误判 APPLIES_TO（队列不是方法） |

**（3）方向必须自检。** CONTAINS 是全项目最高频的错误点。提示词要求每条 CONTAINS 输出前做一次方向自检：把关系读成「target 是 source 的一种」，读不通就翻转 source 与 target；翻转后仍不确定则删除。并直接点名禁止一组历史上反复出现的错误输出（如「AVL 树 CONTAINS 二叉搜索树」——正确方向是「二叉搜索树 CONTAINS AVL 树」）。

**（4）禁止把「组成」「属性」「表示法」当成关系。**

- 整体-部分（二叉树与根节点、叶节点）**不是** CONTAINS——只有当「X 是 Y 的一种」时才是；
- 属性（二叉树与高度、AVL 树与平衡因子）**不是** CONTAINS；
- 「X 用于表示 Y」（数组表示与映射公式）**不是** APPLIES_TO；
- 「X 通过 Y 机制维持性质」（AVL 树与旋转）**不是** CONTAINS。

这一组反例是压制「臆造关系」的主要手段（效果见 2.1.3）。

**（5）实体粒度与命名有明确规则。** 名称不带「算法」「方法」等冗余后缀（「二分查找」不写成「二分查找算法」）；不用裸动词（用「插入节点」不用「插入」）；同义词与中英文只保留一个规范名（CNN 与「卷积神经网络」合并）；不抽人名、页码、章节标题、指代词；不抽代码符号（`==`、`equals()`、`BUILD_TREE()`）。

> **本节的边界**：提示词与工程代码分工不同。提示词解决**语义理解**（什么算知识点、两节点间是什么关系），工程代码解决**系统可靠性**（JSON 三级容错解析、实体归一化与同义词合并、`_is_code_symbol` 代码符号过滤、悬空端点校验、重复关系去重、低置信度阈值过滤）。两者不重复。本文档 2.1.4 节报告的指标，是在**「提示词 + 工程规则」整条链路之后**的结果上计算的，含义是「系统最终产出的质量」，而非「模型裸输出的质量」。

#### 2.1.3 版本迭代

P1 共经历 6 个版本。迭代路径由真实评测驱动，每一步都遵循同一条流程：**先跑基线拿到错误归因，再定向修改，再复测**。触发这一次完整迭代的，是一个在早期被掩盖的问题。

**起点：玩具规模上的达标。** 最初的抽取测试用的是一段 **708 字节 / 11 行**的示例文本（Gold 为 5 实体 / 4 关系，脚本 `backend/test_extraction_accuracy.py`）。v1.0 在这段文本上关系 F1 = 0.4667，v1.1 加入 Few-shot 后升到 0.9333。此时看起来「已满足赛题」——问题在于这个规模根本代表不了真实教材。

**规模放大暴露真相。** 换到真实章节——《Hello 算法》第 7 章「树」（**15330 字符 / Gold 33 条关系**）——同一套链路、同一个 v1.1 的提示词，v1.2 基线的关系 F1 只有 **0.1614**。玩具规模的 0.93 完全无法支撑申报。

| 版本 | 改动 | 驱动它的问题 |
|:---:|---|---|
| v1.0 | 四类关系 + 基础约束（858 字符，无 Few-shot、无 evidence/confidence） | 初版 |
| v1.1 | 新增 PRECEDES Few-shot 示例；**新增两条硬性条款**：「必须使用 PRECEDES 不得降级 RELATED_TO」「PRECEDES 占比不应为 0」；temperature 0.1→0.3 | 首轮测试发现 PRECEDES 产出过少 |
| v1.2 | **决策树重构**；**删除 v1.1 的两条强制条款**；删除编号 Few-shot 改为分节反例；新增 evidence/confidence 强制；temperature 回 0.15 | 见下 |

**v1.1 的自我修正值得单独说明。** 那两条硬性条款确实治好了「PRECEDES 太少」，代价是**模型在没有前置关系的地方也开始硬造 PRECEDES**。v1.2 删掉它们，理由是：**产出量不是目标，准确率才是**。v1.1 的这段弯路直接构成了后面「臆造」类错误的一部分。

**v1.2 基线（决策树版）的错误归因**——这是整个迭代的转折点。三轮独立运行的均值：

| 错误类型 | 数量（三轮均值） | 逐轮 |
|---|---:|---|
| ① 臆造（节点对不在 Gold） | 34.0 | [31, 32, 39] |
| ② 方向颠倒 | 6.7 | [5, 8, 7] |
| ③ 类型混淆 | 2.3 | [4, 0, 3] |
| ⑤ 完全漏抽（Core） | 26.3 | [27, 26, 26] |
| 方向错误率（报告字段） | **0.1346** | — |

据此做了三次**定向修复**，每次只针对归因表中确认的问题动手：

- **v1.3**——CONTAINS 收紧为「类型包含 + 操作包含」两类（删掉被滥用的「整体-部分」分支）、新增方向自检与反例集、重写 APPLIES_TO 的「实现机制」映射、补 RELATED_TO 方向约定、新增「类别性总称必须抽取」（漏抽「遍历」「旋转」会连带丢失一批上位关系）。
  → 关系 F1 **0.1614 → 0.5647**；方向错误率 **0.1346 → 0.0621**；类型混淆清零。
- **v1.4**——新增 category 判定细则（遍历方式属「方法」不属「概念」）与命名规则；新增「历史反复出错输出」禁止清单；点名禁止组成/属性关系；**工程侧新增 `_is_code_symbol` 确定性兜底**（不依赖模型是否遵从提示词）。
  → 关系 F1 **0.5647 → 0.7742**（**首次站上 0.70**）；方向错误率**清零**；实体 F1 0.8890。
- **v1.5**——只加反例、不动正例的收敛微调：代码注释中的操作短语不抽、限定操作关系的主体、补「表示法不是 APPLIES_TO」反例、「仅共享词根不构成证据」反例。
  → 关系 F1 **0.7742 → 0.8312**。

> **v1.4 起，代码侧新增了 `_is_code_symbol` 过滤**（`knowledge_extractor.py`），拦截 `==`、全大写标识符、语言关键字等程序符号。这是**确定性兜底**：即使提示词要求「不要抽程序符号」，代码层仍会再拦一道。因此 v1.4 的指标提升是「提示词 + 工程规则」共同的贡献，不能全部归因于提示词。

| 真实章节 | v1.4 | 同 | 0.8890 | 0.6804 | 0.8990 | **0.7742** |

v1.5 的三轮逐轮关系 F1 为 **0.8485 / 0.8451 / 0.8000**，标准差 ±0.0271；三轮均站上 0.70。分关系类型看（第 1 轮）：CONTAINS F1 = **0.9388**（Gold 25 条），RELATED_TO = 0.6667，APPLIES_TO = 0.5000。

> **两点必须向评审说明的数字口径**：
> 1. 本表数字是**三轮均值**。`eval_report_第7章_树_v15.json` 顶层的 `summary` 字段保存的是**第 1 轮**结果（关系 F1 = 0.8485），与本文档的 0.8312 不是同一口径。三轮均值见该文件 `stability.relation_primary_f1.mean`。二者都不是错误，但混用会造成误读。
> 2. **0.8312 是 Gold 标注下的标准 F1**，**不是**赛题的「人工抽样准确率」。本项目当前**尚未开展**与赛题口径一致的人工抽样准确率测试，该数据标注为**待补充**（见 6.2 节与 7 节）。

**关系密度的正确位置。** P1 第九节含一句「参考密度为每 1000 字符正文 2~4 条关系」。它的原意是**抑制输出膨胀**（早期版本臆造偏多时靠它压掉一批证据不足的边），**不是**质量目标或 KPI。不同章节的合理密度差异很大，公式密集章节与概述性章节不可直接类比。就开发集而言，v1.5 三轮的**原始输出**为 36 / 41 / 47 条，折合约 2.3 / 2.7 / 3.1 条每千字符，均落在参考带内；Gold 本身为 33 条（约 2.15 条每千字符）。即在该开发集上，该条款**未出现需要触发的偏离**。

#### 2.1.5 已知边界与待补充

以下局限均**未在 v1.5 上改动**（正文已冻结），如实披露以便评审判断上述结论的适用范围。

1. **P1 中关于 PRECEDES 的规则，在开发集上未被检验。** 开发集第 7 章·树的 Gold 关系构成为 **CONTAINS 25 / RELATED_TO 5 / APPLIES_TO 3 / PRECEDES 0**——**Gold 中没有任何一条 PRECEDES 关系**。因此 2.1.4 的各项指标**不包含对 PRECEDES 判定能力的检验**。这一点尤其需要说明，因为 P1 历史上有相当篇幅的迭代（v1.1 的 Few-shot、v1.3 的 PRECEDES 反例）是围绕 PRECEDES 展开的。**PRECEDES 的实际抽取质量，需在含前置关系的章节上单独验证——待补充。**
2. **开发集为单一章节。** 2.1.4 的全部指标来自数据结构课程的「树」部分。**跨课程**（化学、物理、数据结构其他章节）与**跨文档格式**的泛化能力**尚未验证**。计划以封存集验证（见 6.1 节），结果**待补充**。
3. **双层 Gold 机制在开发集上未激活。** 开发集 33 条关系的 `core` 全为 `true`（Core = Full），「边界模糊关系」的裁量能力尚未在申报数据集上被真正检验。该机制的可用性在第 1 章·语句上得到验证（Core 40 / Full 45，Core 占 89%），但该章**不属于本次申报范围**（见附录 C.1）。
4. **关系召回存在结构性上限——这是评测口径的固有性质，不是模型缺陷。** 评分按三元组（节点对 + 类型 + 方向）匹配，**若某条 Gold 关系的任一端点未被抽为实体，该关系在本口径下不可能被记为命中**。因此关系 Recall 天然受制于实体抽取对关系端点的覆盖程度，两者会同时变动。诊断时应**先看实体层，再看关系层**；也不宜把关系 Recall 与实体 Recall 当作两项独立能力来对比。
5. **提示词对模型的遵从是隐性的。** 例如无法从最终输出中分离出「密度条款是否曾让模型主动少输出」。上述密度数据只能说明结果本身处于合理区间。

### 2.2 P3 智能问答提示词（RAG）

代码位置：`backend/app/services/qa_service.py`。完整原文见**附录 B.1**。

#### 2.2.1 为什么需要它

通用大模型回答课程问题时有两个问题：一是**没有本课程的内容**，只能凭训练数据泛泛而谈；二是**不知道就说不知道**——它更倾向于编一个听起来合理的答案。对教学场景而言，编造的知识点比「不知道」危害更大。

P3 与它前面的检索链路一起解决这两个问题：**先检索出本课程图谱里真正存在的知识点，再要求模型只基于这些内容作答，没有依据就明说。**

#### 2.2.2 检索链路

`QAService.ask_with_sources()` 是唯一入口：

```
学生问题
  → EmbeddingClient.embed([问题])            # SiliconFlow bge-m3，外部 API 调用
  → KnowledgeEmbedder.ensure_index(course_id, document_id)   # 新鲜度检查，返回该文档全部向量
  → 纯 Python 余弦相似度排序 → top_k=5
  → 按 kp_id 回查 Neo4j 取节点名与描述
  → 填入 QA_SYSTEM_PROMPT 的 {context}
  → DeepSeek 生成回答
```

返回结构为 `{answer, sources}`，其中 `sources` **就是本次实际喂给模型的上下文**，两者必然一致。

链路中的几处设计（改动问答功能时需要知道）：

- **`ensure_index` 是懒构建 + 懒重建。** 每次问答都用 Neo4j 当前的 `kp_id` 集合与 SQLite 已存集合比对，不一致才重建。这一点是刻意的：重新抽取会整体更换 `kp_id`，若只判断「表里有向量就跳过」，旧向量会永远指向不存在的节点。
- **新鲜度比对只读 `kp_id` 列**，不反序列化向量文本（后者实测占该步耗时约 70%）。
- **向量以 JSON 文本存 SQLite，余弦相似度为纯 Python 实现**（刻意不引入 numpy）。当前最大文档为 69 个知识点，单次检索约 20ms，规模远未到需要近似最近邻（ANN）的程度。
- **未配置 `EMBEDDING_API_KEY` 或调用失败时，会静默退回关键词检索**（Cypher `CONTAINS`）。降级本身是合理设计，但表现为「回答变差却不报错」——排查时先看 `qa_service` 的 warning 日志。

#### 2.2.3 提示词与设计要点

System Prompt 只有四条规则（原文见附录 B.1），逐条对应一个具体问题：

| 规则 | 解决的问题 |
|---|---|
| 1. 优先使用提供的知识内容回答 | 防止模型撇开课程内容自由发挥 |
| 2. 知识库中没有相关信息时诚实告知，不要编造 | 直接针对幻觉；这是赛题明确关注点 |
| 3. 回答准确、简洁、易于理解 | 面向学生，控制阅读成本 |
| 4. 合适时推荐相关知识点供进一步学习 | 把单次问答转化为学习导航入口 |

User Prompt 为学生原始问题原文，不做模板包装。temperature=0.3 是全项目唯一高于 0.15 的取值——问答属开放生成任务，过低温度会使回答生硬，0.3 是流畅度与事实约束之间的折中。

#### 2.2.4 问答测试框架与结果

问答质量已有独立测试集与实测结果，见 `docs/问答测试集.md`；复测脚本 `backend/test_qa_testset.py`，原始结果 `backend/test_qa_testset.json`。

**测试环境**：course_id=5《第 6 章 面向对象程序设计》（Python OOP），图谱规模 **69 个知识点节点 / 118 条关系**（CONTAINS 45 / RELATED_TO 35 / APPLIES_TO 32 / PRECEDES 6），top_k=5，生成 temperature=0.3。

**题目分类（21 题）与实测结果**：

| 类目 | 题号 | 题量 | 考察点 | 结果 |
|---|:---:|:---:|---|---|
| 概念定义 | 1–5 | 5 | 单一/复合概念的定义与关系 | 5/5 正确 |
| 方法用法 | 6–10 | 5 | 内置函数、装饰器、动态绑定 | 5/5 正确 |
| 对比辨析 | 11–14 | 4 | 易混概念的差异 | 4/4 正确 |
| 关系前置 | 15–17 | 3 | 依赖图谱 `PRECEDES` 边的前置知识 | 3/3 正确 |
| 运算符 | 18–20 | 3 | 运算符分类与重载 | 3/3 正确 |
| 边界诚实性 | 21 | 1 | 知识库外问题应拒答而非编造 | 1/1 正确拒答 |

**量化结果**：

| 指标 | 结果 |
|---|---|
| 回答正确率（课内 20 题） | **20/20 = 100%** |
| 边界诚实性（课外 1 题） | **1/1 = 100%**（正确拒答，未编造） |
| 检索 top-3 召回 ≥1 个预期知识点 | 19/20 = 95% |
| 检索 top-3 召回全部预期知识点 | 18/20 = 90% |

**测试暴露的不足（如实记录）**：

1. **前置知识类问题 top-3 召回不足**（Q16「类与对象是什么关系」缺「对象」、Q17「学习多态前需掌握什么」缺「继承」）。原因是向量相似度优先召回目标节点本身及其近义节点，而其**前置节点**排名靠后（第 4–5 位）。因为 `ask()` 使用 top_k=5，回答仍然正确；但若降低 top_k 就会漏答。
2. **知识库颗粒度限制**（Q19）。位运算符仅有描述、无示例，模型如实说明了「知识库无更详细示例」——属于图谱内容问题，非问答链路问题。

> **与赛题分类的对齐情况（待补充部分）**：本项目测试集覆盖了「概念解释」（概念定义）、「课程事实」（方法用法、运算符）、「易混淆知识」（对比辨析）与「多知识点关联」（关系前置，部分覆盖）。赛题口径中「**课程外问题**」与「**无相关知识问题**」是两种不同情形——前者问的是本课程范围之外，后者问的是课程内但图谱未收录。现有测试集**只设了 1 道课外题，未对这两种情形分别设题**，这部分覆盖**待补充**。

#### 2.2.5 已知边界与待补充

1. **无响应时间实测数据。** 赛题对智能问答有响应时间要求，但 `backend/eval_data/` 中没有对应的计时记录，**待补充**。
2. **前置知识类问题未做图召回增强。** 上述 Q16/Q17 的改进方向（对含「之前 / 先 / 前置 / 前提」的问题沿 `PRECEDES` 边做图召回增强，或动态调大 top_k）目前**尚未实现**，属后续优化项，见第七节。
3. **测试集规模有限（21 题）**，且集中于单一课程（Python OOP）。结论应理解为「在该课程图谱上的可用性验证」，而非普适的问答质量结论。

## 三、辅助 Prompt

### 3.1 P2 前置关系补全

代码位置：`app/services/relation_completion.py`。完整原文见**附录 B.2**。

**用途与定位。** 教材中「必须先学 A 才能学 B」的显式表述往往稀疏，仅靠 P1 抽取会导致 `PRECEDES` 边过少，影响路径推荐覆盖。P2 在图谱构建完成后，把全部知识点清单（名称 + 类别 + 描述）交给大模型，**基于教学逻辑常识**补全缺失的前置关系。

**接入状态：已实现，未接入。** 提示词、调用封装、结果校验与写库逻辑均完整，并提供 `__main__` 命令行入口（含 `--rollback` 子命令，可删除指定文档下全部 `is_inferred=True` 的 `PRECEDES` 边）。但当前**未挂载 API 路由、前端无对应界面**，无法通过产品操作触发；`app/core/metrics.py` 已将其列入 `UNTRACKED_LLM_SCOPES`。**因此当前的学习路径推荐所依赖的 `PRECEDES` 边，来自 P1 的原文抽取，不包含 P2 的补全结果。**

**与 P1 的证据标准差异——这是有意设计，不是自相矛盾。** P1 的核心原则是「禁止仅凭文本先后顺序、常识或名称相似性推断关系」；P2 恰恰要求基于教学逻辑常识补全 P1 抽不到的前置关系。二者不冲突，因为它们是目标不同、且**数据层相互隔离**的两个任务：

| | P1 知识抽取 | P2 前置关系补全 |
|---|---|---|
| 任务定位 | **抽取**——把文本已写明的知识结构化 | **补全**——在已有知识点上推断文本未写明的教学顺序 |
| 证据标准 | 仅接受**文本显式证据**（每条关系须带 `evidence` 原文） | 允许**教学逻辑推断**（无原文证据，故不要求 `evidence`） |
| 信任级别 | 视为可信的知识本体 | 视为**推断结果** |
| 数据隔离 | 正常入库 | 标记 `is_inferred=True`，可单独检索、可 `--rollback` 回滚 |
| 当前接入状态 | **主链路** | **未接入** |

也就是说：P1 的「不许推断」约束的是「把推断结果伪装成文本证据」这一行为；P2 从不声称其边来自文本，它显式标记自己为推断并与原文抽取边分区存放。**因此 P2 的输出不会进入 P1 的证据型统计，也不计入 2.1.4 节的抽取指标。**

**提示词要点**：负面清单显式列出「包含 / 相关 / 应用」三类易混淆情形并指向正确的关系类型，与 P1 的决策树思想一致；示例取教学场景中无争议的「继承 → 多态」。

### 3.2 P8 试题结构化抽取

代码位置：`app/services/question_extractor.py`。完整原文见**附录 B.3**。

**用途。** 把教师上传的试题文档（章末习题、试卷）解析为结构化题目（题干 / 题型 / 选项 / 答案 / 解析），输出字段直接对应题库表 `q_type`。

**接入状态：已实现、已评测，但产品内未使用。** 提示词、分块调用、三级容错 JSON 解析与合并逻辑均完整，并有量化评测脚本 `backend/eval_question_import.py`（temperature=0）。**但当前产品内的试题导入走的是确定性规则解析**——切「题目区 / 答案区」→ 按题号切块 → 答案映射 → 题型判定（见 `app/api/questions.py` 的 `import/preview`），**未调用该 LLM 提示词**。这一取舍的理由是中文本教材习题题号规整，规则解析足够稳定且无 API 成本与延迟。P8 的定位是「题号不规范、规则解析失效」场景下的 **LLM 兜底储备**。

**设计要点**：

1. **只抽真实存在的题**（规则 1）——「不要臆造题目；看不清或不确定的题直接跳过」，与 P1 的「宁缺毋滥」同源。
2. **禁止自行解题**（规则 2）——文本未给答案时 `answer` 填空串，并以「绝对不要自己解题」加重约束。这是本提示词与通用「解题助手」的关键分野：系统要的是**结构化**，不是**代做**。一旦让模型自行解题，答案便不再可溯源。
3. **题型枚举封闭**（规则 3）——`SINGLE / MULTI / JUDGE / FILL / ESSAY` 五类封闭取值，可直接映射到 `q_type` 字段。
4. **无选项时输出 `[]` 而非省略字段**（规则 4）——保证下游解析路径唯一。
5. **三级容错解析**——直接解析 → 剥离 Markdown 代码块 → 正则截取 JSON，单块解析失败不致整篇丢弃。

**为什么要区分开发集与封存集。** 开发集用于「发现问题 → 改提示词 → 复测」的迭代；封存集只在最后跑一次。若反复用封存集调提示词，它就不再是独立验证，其上的分数也就失去意义。这是本项目冻结纪律的核心（见第七节）。

### 6.2 评价指标

**主指标**：以人工标注 Gold 为基准的标准 **Precision / Recall / F1**（严格匹配：节点对 + 关系类型 + 方向三者全对才算命中）。

需要明确的三个层次：

| 层次 | 含义 | 本项目现状 |
|---|---|---|
| `confidence` | **模型自评置信度**，未经概率校准 | 仅用于工程过滤、人工复核排序，**不是任何形式的准确率**。模型自报 0.95 不代表该条 95% 正确 |
| P / R / F1 | **本项目的申报口径**——人工 Gold 标注下计算 | 开发集关系 F1 = 0.8312、实体 F1 = 0.9220（三轮均值） |
| 人工抽样准确率 | **赛题要求的口径** | **尚未开展，待补充** |

> **关于「准确率 ≥70%」的表述纪律。** 赛题要求的是人工抽样准确率 ≥70%。本项目当前给出的是 **Gold 标注下更细粒度的 P/R/F1**，其中开发集关系 F1 = 0.8312。**不能将 F1 直接等同于赛题的人工抽样准确率**——两者标注方式与抽样方式不同。本项目在提交前应补做与赛题口径一致的人工抽样准确率测试，并单独列出结果（见第七节第 1 条）。

**辅助指标（不作为申报主口径）**：报告同时输出「忽略类型与方向」的宽松节点对匹配，仅用于诊断「是否抽到了正确的节点对、只是类型或方向判定有误」。其数值不用于对外申报。

### 6.3 实验参数

| 参数 | 取值 | 来源 |
|---|---|---|
| 模型 | `deepseek-chat` | `settings.LLM_MODEL` |
| temperature（运行时 / 评测） | 0.15 / **0** | `eval_config.make_config(temperature=0)` |
| 分块 `chunk_tokens` | 6000 | `_CHUNK_MAX_TOKENS` |
| 重叠 `overlap_tokens` | 400 | `_OVERLAP_TOKENS` |
| 单次输出上限 `max_output_tokens` | 8192 | `_MAX_OUTPUT_TOKENS` |
| 并发 | 4 | `_MAX_CONCURRENCY` |
| 关系置信度阈值 | PRECEDES / RELATED_TO = 0.6；CONTAINS / APPLIES_TO = 0.5 | `_RELATION_CONFIDENCE_THRESHOLDS` |
| 独立运行轮数 | 3 | 报告 `runs` |

参数快照逐个版本存档于 `backend/eval_data/experiment_config_v1{3,4,5}.json`（含 `prompt_version`、`temperature`、`chunk_tokens`、`overlap_tokens`、`max_output_tokens`、`thresholds`）。

**关于「评测温度设为 0」。** 它的作用是**降低采样随机性、提高实验可重复程度**，**不是**「保证结果严格可复现」。因此本项目不依赖「重跑得到相同结果」，而是采用**预测落盘**：正式评测只跑一次并把模型输出写入 `pred_*.json`，此后所有评分、调参、出图都基于同一份预测文件。这样「提示词改动带来的分数变化」与「模型自身的随机波动」才不会混在一起。

**关于 `max_output_tokens = 8192`。** 该值即 `deepseek-chat` 的单次输出上限。此前曾设为 4096，实测在知识点密集的块（章末习题、公式密集章节）会导致 JSON 数组**中途被截断**（`finish_reason=length`），进而使**整个分块的抽取结果解析失败、该块知识点全部丢失**。这类损失在报告里表现为「完全漏抽」，极易被误诊为模型召回能力不足，因此上调至上限并记录在案。

## 附录 A. P1 v1.5 完整 Prompt

与 `backend/app/services/knowledge_extractor.py` 中的 `EXTRACTION_PROMPT` **逐字一致**（正文 6212 字符，已程序化比对）。System Prompt 为：`你是一个精确的知识图谱构建助手。请只输出JSON格式的结果。`

User Prompt（`{text}` 为分块后的课程文本）：

```
你是高校课程知识图谱构建专家。请从给定课程文本中抽取「可用于知识图谱与学习路径推荐」的知识点实体，并识别实体之间明确存在的语义关系。

## 核心原则
宁可少抽取，也不要臆造关系。禁止仅凭文本先后顺序、常识或名称相似性推断关系。
若对某条关系证据不足，直接不输出该关系。
每输出一条关系前自问：「换一个领域专家，只看 evidence 原文，会不会认同这条关系的类型与方向？」不确定就删除。

## 一、实体要求
每个实体包含：
- name：知识点名称，简洁、规范、稳定
- category：只能是「概念」「定理」「公式」「方法」之一（无法归类时用「概念」）
- description：一句话描述该知识点在课程中的含义

category 判定（易错区，务必注意）：
- 具体的遍历方式、算法步骤、操作、表示法 → 「方法」。例如：前序遍历、中序遍历、后序遍历、层序遍历、广度优先遍历、深度优先遍历、旋转、插入节点、数组表示，全部属于「方法」，不得标为「概念」。
- 「遍历」「旋转」这类类别性总称 → 「概念」。
- 数据结构、术语定义、性质名词 → 「概念」。例如：二叉树、队列、平衡因子、高度。

实体粒度：
- 一个实体应是一个「独立可学习的知识点」，不要过度拆分，也不要堆砌冗余修饰。
- 同义词、英文缩写与中文全称属于同一知识点时，只保留一个规范名称。例如 CNN 与「卷积神经网络」合并为「卷积神经网络」。
- 名称不要带「算法」「方法」「结构」等冗余后缀，除非该词是固定术语本身（如「二分查找」不要写成「二分查找算法」）。
- 名称不要用裸动词（如「插入」「删除」「查找」），必须带操作对象（如「插入节点」「删除节点」）。
- 不要抽取：人名、学校、公司、页码、章节标题本身、「本节」「上述方法」等指代词、普通名词、单纯例子名。
- 不要抽取代码示例中的函数名、变量名、运算符、类名、关键字等程序符号（如 ==、equals()、BUILD_TREE()、public、private），它们不是课程知识点。
- 不要抽取代码注释/代码清单里出现的操作描述短语（如「初始化二叉树」「构建二叉搜索树」），它们只是某段代码的用途说明，不是独立知识点。
- 注意抽取文中明确出现的「类别性总称」：当文本说「前序、中序、后序遍历统称/属于遍历」时，「遍历」这类上位总称本身也是一个实体，必须单独抽取（它是关系链的上位节点，漏抽会连带漏掉一批关系）。同理「右旋与左旋统称旋转」中的「旋转」。
- 注意抽取定义句中的上位类别词：如「树是一种非线性数据结构」中的「非线性数据结构」、「红黑树是一种平衡二叉搜索树」中的「平衡二叉搜索树」，这类总称同样是关系链的上位节点。
- 文中明确提出的方法论/思想（如「分治」）若作为方法讲解，应抽取为「方法」。

## 二、关系类型（仅限 4 种，英文大写，方向严格）
PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO

## 三、关系判定必须按下述顺序（决策树）
对任意两个知识点，按顺序判断：

1. 「X 是 Y 的一种/子类/特殊形式/变体/属于 Y」或「X 是 Y 的典型操作」？ → CONTAINS（source 是上位概念 Y，方向 source→target，详见第五节）
2. 否则，文本明确表达「学习 source 是理解 target 的必要前提」？ → PRECEDES（方向 source→target）
3. 否则，source 是方法/算法/技术，且文本明确说明其用于实现/解决/完成 target 代表的问题/任务？ → APPLIES_TO（方向 source→target，判定边界见第六节）
4. 否则，文本明确说明二者存在密切关联（工具-主体、并列类似）？ → RELATED_TO（方向约定见第七节）
5. 以上均不满足或证据不足 → 不输出关系

## 四、PRECEDES 只表示「学习依赖」，不表示「文本顺序」
只有文本明确表达以下语义才用 PRECEDES：学习 B 前须掌握 A；A 是理解 B 的基础；B 建立在 A 之上；掌握 A 后才能学 B。
典型触发词：「基础」「先修」「前提」「掌握…之后」「进一步学习」。

反例（以下禁止推断为 PRECEDES）：
- 「本章首先介绍线性表，然后介绍栈」→ 这是叙述顺序，不是学习依赖，不得输出「线性表 PRECEDES 栈」。
- 「卷积神经网络是神经网络的一种」→ 是包含关系，必须用「神经网络 CONTAINS 卷积神经网络」，不得用 PRECEDES。
- 「算法运行后生成结果」→ 时间先后，不是 PRECEDES。
- 「X 是理解 Y 的关键」「通过 X 判断 Y」「X 是 Y 的重要指标」→ 这只是"X 有助于理解 Y"，不等于"必须掌握 X 才能学 Y"，不得输出 X PRECEDES Y。
- 「回顾 X 的定义，下面介绍 Y」「上一节介绍了 X」→ 章节引用/复习指令，不是学习依赖声明。

## 五、CONTAINS 的方向与边界（最高频错误区，务必逐条核对）
### 5.1 方向规则（source 是上位概念，target 是下位概念）
- 「X 是 Y 的一种 / 特殊形式 / 变体 / 属于 Y」「Y 包含 X」「Y 包括 X」「Y 的常见类型有 X」→ **Y CONTAINS X**（上位概念在前，绝不反向）
  例：「栈是一种操作受限的线性表」→ 线性表 CONTAINS 栈
  例：「AVL 树是二叉搜索树的一种」→ 二叉搜索树 CONTAINS AVL 树
  例：「前序遍历是深度优先遍历的一种」→ 深度优先遍历 CONTAINS 前序遍历
  例：「完美二叉树也是一棵完全二叉树」→ 完全二叉树 CONTAINS 完美二叉树
- 「X 是 Y 的操作」（句式如「Y 的 X 操作」「Y 支持 X 操作」）→ **Y CONTAINS X**
  仅当 X 是直接对 Y 执行的基本操作（插入、删除、查找、遍历等，句式以 Y 为操作对象）。
  例：「二叉搜索树支持插入节点、查找节点、删除节点操作」→ 二叉搜索树 CONTAINS 插入节点、二叉搜索树 CONTAINS 查找节点、二叉搜索树 CONTAINS 删除节点
  反例：「AVL 树通过旋转保持平衡」——旋转是维护平衡的手段、不是对 AVL 树执行的增删查操作，不得输出 AVL 树 CONTAINS 旋转。

### 5.1 附：历史上反复出错的输出（逐条核对，严禁出现）
- 严禁输出「AVL 树 CONTAINS 二叉搜索树」——正确为 二叉搜索树 CONTAINS AVL 树
- 严禁输出「AVL 树 CONTAINS 平衡二叉树」——正确为 平衡二叉树 CONTAINS AVL 树
- 严禁输出「完美二叉树 CONTAINS 完全二叉树」——正确为 完全二叉树 CONTAINS 完美二叉树

### 5.2 输出前方向自检（每条 CONTAINS 必做）
把关系读成「target 是 source 的一种/子类/典型操作」，若语义不通，而读成「source 是 target 的一种」才通，
说明方向写反了，必须翻转 source 与 target。翻转后仍不确定就删除该关系。

### 5.3 不是 CONTAINS 的情况（严禁）
- 整体-部分结构（「二叉树由根节点、叶节点组成」「链表由节点构成」）：部分只是结构的组成单元、而非"X 是 Y 的一种"类型关系时，不得输出 CONTAINS。只有当"X 是 Y 的一种/子类"（如「完全二叉树是二叉树的一种」）才成立。
  点名禁止（这些是"组成/属性"而非"类型包含"，一律不建立任何关系）：
  - 二叉树 与 节点/根节点/叶节点/左子节点/右子节点/边/层/度/高度/深度 之间
  - 节点 与 左子节点/右子节点 之间
  - 操作关系中的主体必须是正文明确的对应结构（如「二叉搜索树的插入操作」→ 二叉搜索树 CONTAINS 插入节点），不得把操作挂到泛化主体上（「二叉树 CONTAINS 插入节点」不成立）
- 「X 具有属性/特征/指标 Y」（如「二叉树具有高度」「AVL 树用平衡因子衡量平衡」）：Y 是 X 的属性而非 X 的一种，不得输出 X CONTAINS Y。
- 「X 通过 Y 机制维持性质」（如「AVL 树通过旋转保持平衡」）：Y 是维护机制而非 X 的类型，不得输出 X CONTAINS Y（但「右旋、左旋是旋转的两种基本操作」→ 旋转 CONTAINS 右旋 成立）。
- 「X 使用公式/函数 Y 进行表示或计算」（如「数组表示使用映射公式」）：Y 是 X 的计算工具，不得输出 X CONTAINS Y。
- 「要学习 X，必须先掌握 Y」→ Y PRECEDES X，不是 CONTAINS
  例：「要学习多态，必须先掌握继承」→ 继承 PRECEDES 多态

## 六、APPLIES_TO 的判定（含「实现机制」的正确映射）
只有当 source 是方法/算法/技术类知识点、且文本明确说明其被用于实现、解决、完成 target 代表的问题/任务时，才能使用 APPLIES_TO（方向 source→target）。

「X 基于 Y 实现」「X 通过 Y 实现」「X 借助 Y 实现」「X 用 Y 实现」句式：
- Y 是方法/算法/技术 → **Y APPLIES_TO X**
  例：「深度优先遍历通常基于递归实现」→ 递归 APPLIES_TO 深度优先遍历（严禁输出反向）
  例：「前序遍历基于递归实现」→ 递归 APPLIES_TO 前序遍历
- Y 是数据结构等非方法类概念 → 降级为 RELATED_TO（见第七节）；证据不足则不输出
  例：「广度优先遍历借助队列实现」→ 队列 RELATED_TO 广度优先遍历，**严禁 APPLIES_TO**

「X 可用于实现 Y」（X 是技术/结构，Y 是应用对象）→ X APPLIES_TO Y
  例：「二叉搜索树可用于实现多级索引」→ 二叉搜索树 APPLIES_TO 多级索引

方法论思想贯穿某对象的设计（如「二叉树体现分治思想」「分治思想应用于二叉树」）→ 方法 APPLIES_TO 对象
  例：「二叉树体现一分为二的分治逻辑」→ 分治 APPLIES_TO 二叉树

严禁的输出：
- 「X 用于表示 Y」「X 是 Y 的存储方式/表示法」（如「数组表示用于存储完全二叉树」）：表示法与被表示对象的关系不是 APPLIES_TO，若证据不足则不输出。

严禁的输出（违反方向）：
- 深度优先遍历 APPLIES_TO 递归、广度优先遍历 APPLIES_TO 队列、中序遍历 APPLIES_TO 深度优先遍历（这些方向全部颠倒；「X 是 Y 的一种」走 CONTAINS，不是 APPLIES_TO）

不要为了覆盖所有语义而强行映射到现有四类关系；证据不足时宁可不输出。

## 七、RELATED_TO 的方向约定（从严输出）
仅用于「明确密切相关、但既非上下位、也非学习前置、也非应用」的情况，且文本有明确关联表述。
方向约定：
- 工具/支撑方为 source，主体/被支撑方为 target：
  例：「广度优先遍历借助队列实现」→ 队列 RELATED_TO 广度优先遍历
  例：「二叉树可用链表表示」→ 链表 RELATED_TO 二叉树
- 并列类似关系（「与…类似」「工作原理一致」「互为镜像」「互为对称」）时，source 取正文中先出现的一方：
  例：「红黑树与 AVL 树类似」→ AVL 树 RELATED_TO 红黑树
  例：「右旋与左旋互为镜像对称」→ 右旋 RELATED_TO 左旋
- 主体与其思想来源（「X 的查找思想源于二分查找」）→ X RELATED_TO 思想来源
  例：「二叉搜索树的查找思路与二分查找一致」→ 二叉搜索树 RELATED_TO 二分查找
- 方向无法确定时宁可不输出。

严禁的输出：
- 仅因两个概念出现在同一段就输出 RELATED_TO。
- 「X 与 X 序列」这类名称派生关系（如 中序遍历 与 中序遍历序列）不构成 RELATED_TO 证据。
- 「X 的时间复杂度」「X 的性能」等属性关联不得输出。
- 两个知识点仅通过第三方间接联系（如完美二叉树与广度优先遍历仅都关联层序遍历）→ 不输出直接关系。
- 「X 与其维护机制/属性/表示工具」（如 AVL 树与旋转、完美二叉树与高度、数组表示与映射公式）不建 RELATED_TO。
- 仅共享词根不构成关联证据（如「二分查找」与「查找节点」都含"查找"二字，不代表二者存在 RELATED_TO 关系）。

## 八、每条关系必须携带证据与置信度
- evidence：支持该关系的原文短句（必须来自输入文本，不得编造）
- confidence：0~1 的置信度，如实反映证据强弱，不确定就降低

## 九、输出约束
- source 与 target 必须都出现在 entities 中，且 source ≠ target
- 不重复输出相同 (source, type, target)；文本中因分块出现的重复段落，同一知识点/关系只输出一次
- type 只能是 PRECEDES / CONTAINS / RELATED_TO / APPLIES_TO
- 关系密度控制：参考密度为每 1000 字符正文 2~4 条关系。若本次输出明显超出该密度，说明混入了证据不足的关系，请删减到最明确、最有价值的子集。
- 输出前对每条关系自检：
  ① CONTAINS：target 是 source 的一种/子类/典型操作？（读反则翻转 source 与 target）
  ② PRECEDES：文本有明确的「学习 target 前必须掌握 source」表述？
  ③ APPLIES_TO：source 是方法/技术，target 是它实现/解决的问题或任务？
  ④ RELATED_TO：source 是工具/支撑方或正文先出现方？
- 严格只输出 JSON，不要 Markdown 代码块，不要解释文字

## 十、输出格式
{
  "entities": [
    {"name": "实体名", "category": "概念", "description": "一句话描述"}
  ],
  "relations": [
    {"source": "源实体名", "target": "目标实体名", "type": "PRECEDES", "evidence": "原文证据", "confidence": 0.95}
  ]
}

## 课程文本
{text}

请只输出 JSON，不要包含任何其他内容。
```

## 附录 C. 评测口径细则、实验参数快照与版本索引

> 本附录收纳评测机制中的细节部分。正文 6.2 节只保留最有解释力的标准指标；需要核对机制实现时查阅此处。

### C.1 三种关系指标口径

Gold 中每条关系可携带 `core` 布尔标记。**Core 集**为文本明确、按决策树必然成立、无争议的关系；**Full 集**为 Core ∪ 合理但边界模糊、需人工裁量的关系。评测器据此**同时输出三套口径**（实现见 `eval_accuracy.py`）：

| 报告字段 | Precision 分母 | Recall 分母 | 性质 |
|---|:---:|:---:|---|
| `relation_full` | Full | Full | **标准 F1**——P、R 取自同一 Gold 集，可与任何外部结果直接比较 |
| `relation_core` | Core | Core | **保守下界**——只在无争议关系上评分 |
| `relation_primary` | Full | Core | 本项目自建口径，P、R 分母有意不对称 |

**本项目申报采用 `relation_primary`，但必须同时披露另两套。** 采用它的理由是两类错误的实际代价不同：把一条「模型确实抽对、只是标注边界模糊」的边判为错误，会低估 Precision；把一条「无争议、该抽却没抽」的边放过，会高估 Recall。

**在本次申报的开发集上，三套口径数值完全相同。** 开发集第 7 章·树的 Gold 中 33 条关系的 `core` 全为 `true`，**Core = Full = 33**，因此 `relation_primary` = `relation_core` = `relation_full` = **0.8312（P=0.7841, R=0.8889）**。也就是说，**本次申报的 0.8312 就是标准意义上的 F1**，非对称口径未产生任何偏离。三套数值可在 `eval_report_第7章_树_v15.json` 中逐一核对。

双层 Gold 机制真正生效的实例是第 1 章·语句（Core 40 / Full 45，Core 占 89%），它验证了机制可用，但该章**不属于本次申报范围**。

### C.3 评分前的六类丢弃与对账恒等式

关系从模型输出到进入评分须过 6 道过滤，每道丢弃的原因单独计数：

| 代号 | 含义 |
|---|---|
| `invalid_relation_type` | 关系类型不在四类白名单内 |
| `invalid_endpoint` | source 或 target 为空 |
| `synonym_split` | 归一化后 source == target（模型把同一实体拆成两种写法） |
| `dangling_endpoint` | 端点不在 `entities` 列表中（悬空边） |
| `duplicate` | 重复三元组（多因分块重叠） |
| `low_confidence` | 模型自评置信度低于该类阈值 |

**为什么必须逐类记账**：其中 `low_confidence` 最容易造成误诊——这类关系**模型其实抽到了**，是本系统的阈值把它砍掉的。若不单独披露，它会被「完全漏抽」一并吃掉，于是「**阈值设太严**」被系统性误诊为「**模型召回能力不足**」，后续优化方向会完全跑偏。

报告要求每轮满足对账恒等式 `pred_raw_total == pred_total + dropped_total`，并标明 `raw_source` 字段来自抽取器直接上报（`extractor`，精确值）还是评测器反推（`derived`，仅用于补齐）。一旦对不上，即说明抽取侧与评测侧的计数口径已经漂移，该轮结果不可采信（v1.2 基线第 3 轮即为一例，见 6.4 节）。

### C.4 可复现指纹

报告头部固定记录三项指纹，保证「某个分数由哪份数据、哪套归一化规则算出」可追溯：

| 项 | 第 7 章 v1.5 取值 |
|---|---|
| 归一化版本 | `NORMALIZATION_VERSION = "n1"` |
| 别名表 SHA256 | `960bb3117d7fe9ef…` |
| Gold SHA256 | `50f316ce7bea6690…` |

三者任一变化，历史分数即不可直接比较。因此**修改别名表必须递增 `NORMALIZATION_VERSION` 并全量重算**。同一知识点在 Gold 与模型输出中的写法差异（大小写、括号、术语后缀、同义词）若不在归一化层统一，会**同时**制造假性漏抽与假性臆造——**先统一口径，再谈模型优化**。

### C.5 `confidence` 的定位

`confidence` 是提示词要求模型输出的**自评置信度**（附录 A 第八节）。它在本项目中只承担三件事：① 工程侧过滤（低于阈值的关系在入库/评分前丢弃，单列为 `low_confidence`）；② 人工复核排序（教师审核时低置信度条目优先呈现）；③ 结果分析（观察模型「自认为不确定」的部分是否与错误高发区重合）。

**明确不作为**：模型准确率、概率校准度、或评测分数的任何替代指标。该字段未经任何概率校准，与真实正确率之间没有可用的对应关系。
