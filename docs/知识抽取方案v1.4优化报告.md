# 知识抽取方案 v1.4 优化报告

> 目标：在不改变单阶段架构、不重写 Prompt 主体、不改变任何现有抽取口径与参数的前提下，为现行抽取器增加**可观测性与诊断能力**。
>
> 结论：v1.4 的诊断字段已完整接入「抽取 → 校验 → 合并 → 入库前日志」链路。四章 Gold 回归的关系 F1 与原方案基本持平（均值 0.9090 vs 0.9066），实体 F1 略降 0.0038，均在单轮采样波动内；token 用量增加 9.2%。**没有证据表明准确率提高，本报告也不作此结论。**

---

## 一、修改前的系统结构

### 1.1 调用链

```
文档（PDF/TXT/DOCX/MD）
  → DocumentParser 解析为纯文本
  → KnowledgeExtractor.extract(text)
    → chunk_text_for_llm(text, max_tokens=6000, overlap_tokens=400)
    → 分块并发（_MAX_CONCURRENCY=4）调用 _extract_single(chunk)
      → extraction_cache 读取（键 = Prompt 指纹 + 模型 + 温度 + 文本）
      → _request_completion（DeepSeek，JSON mode，失败回退普通模式）
      → _parse_json
      → _validate_extraction_payload
      → extraction_cache.store（只缓存成功结果）
    → 可恢复失败分块串行重试（_EXTRACTION_RETRY=1）
    → _merge_results(results)
      → 实体：_normalize_entity_name 后按规范名去重
      → 关系：白名单 / 空端点 / 自环 / 悬空端点 / 重复三元组 / confidence 阈值
  → task_state.save_extraction(doc_id, sha, entities, relations)
  → KnowledgeGraphManager.build_graph(course_id, doc_id, entities, relations)
  → SQLite 回填 entity_count / relation_count / 状态
```

### 1.2 修改前各字段的去向

| 字段 | 校验层 | 合并层 | task_state | Neo4j | eval_accuracy |
|---|---|---|---|---|---|
| entity.name/category/description | 保留 | 保留并去重 | 保留 | 保留 | 参与实体 F1 |
| entity.evidence | 原 Prompt 未要求 | **丢弃** | — | — | — |
| relation.source/target/type | 保留 | 保留 | 保留 | 保留 | 参与关系 F1 |
| relation.evidence | 保留 | 保留 | 保留 | 保留（边属性） | 不参与 F1 |
| relation.direction_basis | 原 Prompt 未要求 | **丢弃** | — | — | — |
| unmatched_mentions | **顶层字段被整体丢弃** | 不存在 | — | — | — |
| dropped_counts / dropped_relations | 合并时生成 | 保留 | 不存 | — | 用于错误归因 |
| error / error_types | 分块失败时生成 | 透传 | 不存 | — | 不参与 F1 |

### 1.3 修改前的三个可观测性缺口

1. **实体没有证据**：无法判断模型给出的知识点是否有原文依据。
2. **关系没有方向依据**：无法区分「模型没解释」与「解释了但方向错」。
3. **漏抽不可见**：模型没有输出的知识点，系统完全不知道；`_merge_results` 只记录「抽到了但被丢弃」，不记录「压根没抽到」。

此外，`_merge_results` 重建实体 dict 时只保留 `name/category/description/descriptions`，即使模型给了实体 evidence 也会丢；`_validate_extraction_payload` 只返回 `entities/relations`，顶层 `unmatched_mentions` 会被丢。

## 二、修改后的系统结构

### 2.1 调用链（只增加诊断旁路）

```
文档 → 解析 → extract()
  → 分块并发 _extract_single(chunk)
    → 缓存/请求/解析/校验（不变）
    → 新增：_with_chunk_diagnostics(clean, chunk)
         └─ extraction_diagnostics.build_diagnostics
  → 失败分块重试（不变）
  → _merge_results(results, source_text=text, source_chunks=chunks)
    → 原有实体去重 / 关系过滤（完全不变）
    → 新增：实体 evidence 累积（evidence / alt_evidences）
    → 新增：关系 direction_basis 保留
    → 新增：三元组重复次数 / 不同证据 / 涉及分块
    → 新增：unmatched_mentions 跨分块去重合并
    → 新增：分块 summary / chunk_details / name_records
    → 新增：最终 diagnostics 汇总
  → task_state.save_extraction(entities, relations)（字段附加，不改变产物结构）
  → kg_manager.build_graph（只读原有字段，诊断字段被忽略）
  → document_service 写一条诊断摘要 INFO 日志
```

### 2.2 架构不变性

- 仍是**一次 LLM 请求同时抽取 entities + relations**，没有拆成实体/关系两个阶段。
- 没有候选实体池，没有新增候选过滤，没有新增 evidence 硬门。
- 分块、并发、重试、缓存、异常分类、confidence 阈值、关系去重顺序全部原样。
- 诊断字段只旁路记录，不参与任何「是否保留」的判断。

## 五、Prompt 改动内容

### 5.1 只增加三个可选字段

**实体（第一节要求）**

```
- evidence（可选）：支持该实体的原文短句，尽量逐字摘录；找不到逐字依据时省略，不要编造
```

**关系（第八节证据与置信度）**

```
- direction_basis（可选）：一句话说明关系类型与方向依据。CONTAINS 写清上位/下位，
  PRECEDES 写清先修方向，APPLIES_TO 写清方法/应用对象，RELATED_TO 写清方向约定。
  不确定时省略，不要为了填字段而编造依据（缺失不影响该关系的保留）。
```

**顶层输出（新增第十一节）**

```
## 十一、可选诊断字段（只记录，不改变上面的抽取判定）
以下字段都可以省略、为空或输出 []，缺失不会导致实体/关系被删除：
- 实体 evidence：支持该实体的原文短句。
- 关系 direction_basis：关系类型与 source→target 方向的简要依据。
- unmatched_mentions：原文中像课程知识点、但你没有纳入 entities 的术语，最多 10 条。
  只作漏抽诊断线索：它们不会自动成为实体，也不会用于建立关系。
  不要放普通名词、变量、代码符号、动作短语、章节标题；没有就输出 []。
```

输出格式示例同步增加 `evidence`、`direction_basis`、`unmatched_mentions` 三个键。

### 5.2 原规则全部保留

实体类别定义、实体粒度、上位类别实体、四类关系决策树、PRECEDES 学习依赖限制、CONTAINS 方向与边界（含化学/物理/复杂度专项规则与历史错误禁止清单）、APPLIES_TO 方向、RELATED_TO 方向约定、关系密度控制、输出格式主体均逐字保留。

Prompt 长度：10,890 → 11,522 字符（+632，+5.8%）。

### 5.3 缓存失效

`_prompt_fingerprint()` 对整段 `EXTRACTION_PROMPT` 做 SHA-256，Prompt 改动后旧缓存键自然不再命中，不会把 v1.3 与 v1.4 结果混用。缓存内容只存模型原始结果，不存 `diagnostics`。

## 六、新增诊断字段说明

### 6.1 模型输出侧

| 字段 | 层级 | 类型 | 说明 |
|---|---|---|---|
| `evidence` | entity | string，可选 | 支持该实体的原文短句 |
| `direction_basis` | relation | string，可选 | 关系类型与方向依据 |
| `unmatched_mentions` | 顶层 | array，可选 | `{name, evidence, reason}`，Prompt 要求每块 ≤10 条 |

### 6.2 Python 诊断侧（`extraction_diagnostics.py`）

**证据四分类**

| 分类 | 判定 |
|---|---|
| `exact_match` | 原始 evidence 是原文连续子串 |
| `normalized_match` | NFKC（含全半角）+ 空白折叠后是原文子串 |
| `paraphrase` | 有 evidence，但字符串匹配无法确认 |
| `missing` | 缺失、空串、纯空白、非字符串 |

`paraphrase` 不是错误标签；任何分类都不删除实体/关系。

**direction_basis 三态**

- `present`：字段存在（含空值）；
- `empty`：字段存在但清洗后为空；
- `missing`：字段完全缺失。

**名称记录**

每个实体记录：`name`（模型原名）、`normalized_name`（现有规则规范化）、`name_changed`、`name_in_source`、`evidence`、`evidence_match`。

**分块与重复**

- `chunks`：每块的 `summary`（成功/失败、错误类型、四分类计数）；
- `chunk_details`：每块的实体/关系诊断明细（含被丢弃前的关系与证据）；
- `name_records`：跨块去重后的原始名→规范名记录；
- `relation_duplicates`：三元组出现次数、不同证据数、涉及分块数/序号、最终是否入图。

**限量**

- `unmatched_mentions`：Prompt 建议每块 ≤10，Python 上限 50；
- 诊断明细：每个列表最多 500 条，计数始终精确；
- 文本字段（evidence/direction_basis/reason）：最多 300 字符。

### 6.3 最终 `result` 新增键

```json
{
  "unmatched_mentions": [],
  "relation_duplicates": [],
  "diagnostics": {
    "summary": {...},
    "entities": [...],
    "relations": [...],
    "unmatched_mentions": [...],
    "name_records": [...],
    "chunks": [...],
    "chunk_details": [...],
    "relation_duplicates": [...]
  }
}
```

原有 `entities`、`relations`、`raw_relation_count`、`dropped_relations`、`dropped_counts`、`dropped_entity_count`、`chunk_count`、`failed_chunk_count`、`succeeded_chunk_count`、`entity_duplicates`、`duplicate_names`、`error`、`error_types` 全部保留。

## 七、新增代码的调用链

1. **单块抽取** `KnowledgeExtractor._extract_single()`：
   - 缓存命中 → `_with_chunk_diagnostics(cached, text)`；
   - 真实请求 → `_validate_extraction_payload()` → 缓存原始结果 → `_with_chunk_diagnostics(clean, text)`。
2. **校验** `_validate_extraction_payload()`：
   - 实体/关系额外字段经 `{**item}` 保留；
   - `evidence` 非字符串降级为 `""`；
   - `direction_basis` 仅在模型给出时保留并清洗；
   - 顶层 `unmatched_mentions` 清洗后返回；
   - 原有实体/关系必需字段校验与逐条丢弃逻辑不变。
3. **分块诊断** `_with_chunk_diagnostics()`：
   - 调 `build_diagnostics(payload, chunk_text, normalize_name=_normalize_entity_name)`；
   - 不修改 payload，不写缓存。
4. **合并** `_merge_results(results, source_text="", source_chunks=None)`：
   - 实体循环累积 `evidence`/`evidences`，最终转 `alt_evidences`；
   - 关系循环记录 `relation_occurrences`，保留 `direction_basis`；
   - 关系过滤与去重顺序不变；
   - 汇总 `unmatched_mentions`、`relation_duplicates`、`chunks`、`chunk_details`、`name_records`；
   - 用合并后的实体/关系 + 全文再算一次 `diagnostics.summary`。
5. **上层** `document_service._process_document`：
   - 新抽取直接用 `result["diagnostics"]`；
   - 断点续跑复用旧产物时现场 `build_diagnostics`；
   - 只写一条 INFO 日志，不落核心表。
6. **入库** `kg_manager.build_graph`：
   - 只读 `name/category/description/alt_descriptions/category_variants` 与关系 `source/target/type/confidence/evidence`；
   - 诊断字段天然被忽略，不进入 Neo4j。

## 十一、尚未解决的问题

1. **单轮结论**：每章只跑 1 轮。`temperature=0` 不保证供应商确定性——树章 v1.4 同配置两次运行分别得到 56/33 与 60/34，说明实体 F1 ±0.02 内的差异不能归因于代码改动。
2. **token 成本 +9.2%**：诊断字段是模型多写出来的，不是免费观测。若生产环境对成本敏感，需要在 Prompt 中进一步压缩字段长度或按文档类型选择性启用。
3. **截断风险**：化学章观察过一次分块截断。诊断字段增加单块输出长度，在知识点极密集的块上更容易触顶 8192；当前未改 `max_tokens`（遵守参数冻结）。
4. **`paraphrase` 不等于错误**：它只表示字符串匹配无法确认，语义正确性仍需人工/Gold 判断。
5. **`direction_basis` 存在不等于方向正确**：Python 不验证方向语义，只检查字段存在/为空。
6. **`unmatched_mentions` 只是线索**：模型可能漏报，也可能塞入非知识点；Python 只做格式清洗与限量，不代表召回已完整。
7. **未做新领域泛化验证**：四章 Gold 是既有领域，v1.4 在未见领域上的诊断表现未验证。
8. **诊断只进日志/抽取产物，未持久化到核心表**：这是刻意的兼容选择；若后续要做诊断看板，需要另设独立的诊断产物或表，不能直接改图谱核心 schema。

## 十二、是否建议合并到主分支

**建议合并，但按「可观测性改动」而非「准确率提升」定位。**

理由：

1. 单阶段架构、Prompt 领域规则、四类关系定义、过滤口径、名称归一化、confidence 阈值、缓存/重试参数均未改变。
2. 四章 Gold 回归未出现明显退化：关系 F1 均值 +0.0024，实体 F1 均值 −0.0038，均在单轮波动内；没有证据支持「准确率提高」，也没有证据支持「明显退化」。
3. 诊断字段不进入 Neo4j/SQLite/API/前端，`kg_manager` 只读原有字段，合并后不会破坏现有业务。
4. 新增测试 17 + 12 项全部通过，既有 9/16/16/56 项回归全部通过，`ruff` 与 `import app.main` 通过。
5. 诊断价值明确：复杂度章 29/43 条关系证据是改写句，运动学/化学重复三元组分别 47/55 条，这些都是原方案看不见的质量信号。

合并前建议：

- 由项目负责人确认 token +9.2% 的成本可接受；
- 观察化学等密集章节的截断率，必要时另立实验评估输出上限；
- 不要把 `unmatched_mentions` 直接升级为正式实体；若要自动修复漏抽，必须另立实验并重新跑 Gold；
- 保留 `document_service` 的诊断日志，后续可接独立诊断看板，但不要改图谱核心 schema。
