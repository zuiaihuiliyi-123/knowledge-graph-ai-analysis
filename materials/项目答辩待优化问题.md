## 0. 先看这一节

**最重要的发现：知识抽取在封存集上没有达到 0.70。**

v1 PPT 和第 9 章只引用了开发集（第 7 章「树」）的关系 F1 0.8312。但 `backend/eval_data/` 里还有三章从未参与调优的封存集，用定稿 v1.5 各跑了 3 轮：

出处：`backend/eval_data/评测报告_{数据结构,化学,物理}_第2章_*_v15_人工版.md` 第 28–36 行；`backend/eval_data/封存集标注说明.md`。

这意味着三件事：

1. 评委只要问一句「换一章还是 0.83 吗」，如实回答就是「不是」。这件事不能在现场才第一次暴露。
2. 「赛题 7 项指标全部达成」这句话目前不严谨。第一项只能说「开发集达成」。
3. 宽松口径也只有 0.42–0.66，说明主要问题是**关系对本身没找全**，而不只是类型判错或方向反了。

**v2 PPT 的处理方式：主动披露。** 第 9 页明确标为「开发集」，新增第 10 页「封存集泛化测试」，第 18 页指标表第一行改为「开发集达成」并用琥珀色标出。理由是：评测纪律（SHA256 冻结、封存集）本身就是项目最大的亮点，主动展示封存集结果反而证明评测是真的；被评委追问出来，则会让前面所有数字的可信度一起受损。如果团队决定不披露，至少要准备好第 6 节 Q1 的回答。

**第二个重要发现：PRECEDES 前置关系从未被评测过。** 四份金标准（树、数据结构、化学、物理）里 PRECEDES 的数量都是 0（`docs/知识抽取准确率测试报告.md:23`），而学习路径推荐完全依赖这类边。

**决赛前最值得投入的三件事**（详见第 4、7 节）：

1. 改进关系抽取，并在**新的**封存集上重测（第 5.1 节）。
2. 问答基线对比：纯 LLM、关键词检索、向量 RAG 三组同题对比（第 4 节 T2）。
3. 小规模真实用户验证（第 4 节 T4–T6）。

## 4. 待补实验的具体做法

**T2 问答基线对比**

1. 把 `docs/问答测试集.md` 从 21 题扩到 50 题以上，其中课外题和诱导性问题（例如「课程里说的 XX 定理」，而实际上课程里没有）不少于 10 题。
2. 三组用同一题集：
   - A 组：不检索，直接把问题发给 DeepSeek。
   - B 组：只用现有的关键词检索兜底路径，强制走 Cypher `CONTAINS`。
   - C 组：现有的向量 RAG。
3. 判分：两人独立盲评（不知道答案来自哪组），分歧题第三人仲裁，同时报告两人一致率。也可以加一组 LLM 裁判作为参考，但不能只用 LLM 裁判。
4. 输出：一张三组对比柱状图，替换第 11 页表格里的「待测」。
5. 预期：A 组在课外题上大概率会「编」，这正好能证明 RAG 加边界约束的价值。

**T4 教师建图耗时**

- 请 2–3 位老师，每人选 1 章自己熟悉的内容。
- 组 1：纯手工列知识点和关系，记录耗时。
- 组 2：用系统上传，然后在界面上校验到满意为止，记录耗时。
- 两组最好由不同老师做同一章，或者同一老师间隔一周做不同章，避免记忆效应。

**T5 学生可用性（SUS）**

- 10–20 名学生，每人完成 4 个任务：找到某个知识点的前置知识、用 AI 助教问一个课程问题、做一组练习、查看错题本。
- 记录任务完成率和耗时，结束后填标准 SUS 10 题问卷。SUS 68 分以上通常被认为可用性中上。

**T6 教师修改量**

- 在 T4 组 2 的过程中，统计教师对抽取结果的新增、修改、删除条数，分别除以抽取总数。
- 如果系统里没有现成的操作日志，可以对比校验前后两份图谱的差异：Neo4j 节点上有 `is_manual` 标记，关系上也有。

## 5. 软件项目可以优化的地方

按「对答辩评分的影响」排序。

### 5.1 关系抽取的泛化能力（最高优先）

**现状**：开发集 0.83，封存集 0.30–0.56；宽松口径也只有 0.42–0.66，主要是漏抽关系对。

**可能原因**（需要做错误归因确认，不要直接当结论讲）：

- 封存集文本长 2.5–6 倍，分块后跨块的关系对更容易丢失。
- 提示词的决策树和负例都来自「树」这一章，化学、物理的关系表达方式不同。
- 实体抽取在不同分块中的命名不一致，关系两端对不上。

**建议做法**：

1. 先对封存集做和 v1.2 → v1.3 一样的**错误归因**，按「漏抽关系对 / 类型错 / 方向错 / 臆造 / 实体名不一致」分类统计。
2. 根据归因结果选择改法：
   - 跨块丢失多：改成两阶段抽取，先在全文抽实体并统一命名，再按实体对的共现窗口判关系。
   - 学科表达差异大：为理科（物理、化学）单独补少样本示例。
   - 实体名不一致：加强文档级融合与消歧（`docs/文档级知识融合与实体消歧实施报告.md`）。
3. **评测纪律上的关键一步**：一旦用这三章的错误来改提示词，它们就变成了开发集，不能再称为封存集。改进前要**另准备 1–2 章新的封存集**（建议再选一个学科），金标准先冻结，改完只跑一次。否则评委问「你是不是又在测试集上调参」时无法回答。

### 5.2 补齐 PRECEDES 的评测

- 现有四份金标准里 PRECEDES 都是 0，但学习路径完全依赖它。
- 至少在一章上补标 PRECEDES，单独报告前置关系的 P / R / F1。
- 同时检查抽取结果里的 PRECEDES 有没有环。`path_recommender.py` 用了限长变长路径（`*1..5`、`*1..10`）加 LIMIT，有环时不会死循环，但没有检测或报告环的逻辑（`path_recommender.py:120`、`:298-305`）。建议在入图后做一次环检测，有环时提示教师校验。

### 5.3 推荐引擎的效果评估

- Recall@K 只证明召回安全，不证明推荐有效。
- 离线可做的是**回放评估**：用学生的历史作答，按时间切分，看推荐的题目与学生下一次真正做错的知识点是否重合（命中率、NDCG）。对照组用随机抽题。
- 七信号权重目前是手写常量（`docs/题库与推荐系统设计.md:266-270`），只做过第 7 信号的开关 A/B。至少补一组消融实验：依次去掉每个信号，看命中率变化。
- 最有说服力的是课堂试点：同一班级分两组，一组随机练习、一组推荐练习，比较前后测成绩。这在决赛前未必来得及，可以写进展望。

### 5.4 问答链路

- 测试集扩充与基线对比见 T2。
- 向量服务不可用时会静默退回关键词检索。建议在回答里或前端显示「当前为关键词检索模式」，避免演示时「回答变差却不报错」。
- top-3 召回 95% 低于回答正确率 100%。可以试问题改写或查询扩展，并把「top-3 命中」作为回归基准。

### 5.5 代码健壮性

| 问题 | 位置 | 建议 |
|---|---|---|
| 15 处 `except ...:` 后直接 `pass` | `backend/app/services/` | 至少改为 `logger.warning(...)`，否则功能静默失效时无从排查 |
| 同步阻塞 IO 跑在 `async def` 端点里 | 除问答链路外的大部分端点 | 抽取、批量导入等耗时端点优先改用 `asyncio.to_thread` |
| 上传先把整个文件读进内存再判断大小 | `api/documents.py:38`（`await file.read()`） | 用流式读取，超过上限立即中断 |
| 跨库删除没有补偿机制 | `document_service.py:282` 起 | 现状是按固定顺序、每步幂等、失败即返回错误可重试，已经比较稳。可再加「删除中」状态与后台重试 |
| 验证脚本直连线上 `app.db` 与 Neo4j | `backend/test_*.py` | 增加测试库配置，至少让脚本支持指向临时库 |
| 没有 CI、lint | 全仓库 | 加一个最简单的 GitHub Actions：`ruff` 加前端 `npm run build` |

### 5.6 重新抽取后的数据一致性（需团队确认）

`kp_id` 按 uuid 生成，重新抽取会整体更换。调研时**没有找到**把旧 `kp_id` 迁移到新 `kp_id` 的逻辑，向量索引会自动重建，但学习记录、收藏、题目关联的 `kp_id` 可能悬空。请团队实测确认：重新抽取一份已有学习记录的文档后，学生端的掌握进度和收藏是否还在。如果会丢，建议按 `(course_id, document_id, name)` 做新旧 `kp_id` 映射迁移。

### 5.7 遗留模块与文档

- Git 分析模块（`git_analyzer.py`、`git_kg_manager.py`，约 1000 行）没有挂任何路由。建议移到单独目录或分支，避免评委看代码时疑惑。
- `README.md` 仍按 Streamlit 描述前端，与现状不符，建议重写。

### 5.8 演示稳定性

- Neo4j 数据不在版本库里，换一台机器 `kp_id` 会大面积悬空（`docs/协作与图谱共享.md`）。决赛现场必须使用固定的演示机，提前一天完整跑一遍演示流程。
- 准备完整的演示录屏作为断网或故障时的备份。
- 演示前确认 `EMBEDDING_API_KEY` 有效、余额充足，并看一眼 `qa_service` 有没有降级 warning。

### 5.9 成本与私有化

- 抽取 token 目前没有精确统计：`question_extractor.py:144` 是按 `len(chunk) // 3` 粗估的。建议在 LLM 调用处读取 `response.usage`，按文档累计，写入文档记录。
- 私有化：至少用一个本地模型（例如通过 Ollama 或 vLLM 提供 OpenAI 兼容接口）跑通一次抽取和问答，并报告效果差异。这能同时回答「成本」和「数据合规」两类问题。
- 数据合规：课程资料会发给外部 API。PPT 和答辩里不要说「数据不出校」，除非已经完成私有模型实测。

### 6.1 知识抽取

**Q1. 0.8312 是在哪份数据上测的？换一章还能到 0.83 吗？**

- 回答要点：0.8312 是开发集「树」章的 3 轮均值。我们另外准备了数据结构、化学、物理三章封存集，金标准在看预测前冻结。在封存集上实体 F1 稳定在 0.81–0.86，关系 F1 是 0.30–0.56，没有达到 0.70。宽松口径也只有 0.42–0.66，说明主要问题是漏抽关系对。封存集文本是开发集的 2.5–6 倍，我们正在做错误归因并改进。
- 翻页：v2 第 9、10 页，附录 A3。
- 注意：不要说「封存集只是参考」或「其他章节没测」。这些报告就在仓库里。

**Q2. 三轮迭代都在同一份金标准上调，这算不算对测试集过拟合？**

- 回答要点：对开发集来说是的，所以我们才单独准备了封存集来测泛化，结果就是 Q1 的数字。这也是我们把 0.8312 明确标为开发集结果的原因。下一轮改进会再准备一份新的封存集，避免重复使用。
- 翻页：第 10 页。

**Q3. 关系 F1 怎么算？方向错了算对还是算错？**

- 回答要点：按（源、类型、目标）三元组严格匹配，方向错了算错，另外单独报告方向错误率。匹配前做全角半角、空白、大小写归一化，加 20 条别名表，别名表在看预测前冻结，版本和 SHA256 写进报告。Precision 以 Full 集为分母，Recall 以 Core 集为分母，同时披露保守下界和宽松口径。
- 出处：`backend/eval_accuracy.py:20-39`、`:92-94`、`:165-175`。
- 翻页：附录 A3。

**Q4. 金标准是谁标的？几个人标？一致性多少？**

- 回答要点：团队成员依据原文人工标注，标注时不看模型预测，完成后用 SHA256 冻结。目前是单人标注，没有做标注一致性检验，这是我们的不足，计划补一章双人独立标注并报告 Cohen's κ。
- 注意：如果 T9 已经做完，直接报 κ 值。不要编造标注人数。

**Q5. 为什么用单阶段抽取，不用「先抽实体再抽关系」的两阶段？**

- 回答要点：单阶段调用次数少、延迟低，在开发集上效果足够。但我们没有做两阶段的对比实验。封存集的结果显示长文档跨块漏抽是主要问题，两阶段正是下一步要试的方向。
- 出处：`docs/第4章_知识抽取模块设计.md:7`（只有设计论证，没有对比实验）。

**Q6. v1.2 在小样本上 F1 有 0.93，放大后只有 0.16，这说明什么？**

- 回答要点：说明在玩具规模上的评测不可信，这也是我们坚持用真实章节规模评测的原因。当时归因出三类系统性问题：CONTAINS 方向颠倒、把属性臆造成子概念、APPLIES_TO 与金标准决策树冲突，三轮迭代分别对应修复。

### 6.2 问答与检索

**Q7. 问答 20/20 是怎么判对的？如果不检索、直接问 DeepSeek，能答对多少？**

- 回答要点：每题标注了预期知识点，用来判检索是否命中；回答是否正确由人工判断。我们还没有做纯 LLM 的基线对比。（如果 T2 已完成，直接报三组对比结果。）
- 出处：`backend/test_qa_testset.py:28`、`:74-83`。
- 注意：判分人数和规则如实说。

**Q8. 课外拒答 1/1，样本是不是太少？**

- 回答要点：是的，只有 1 题，统计意义有限。我们计划扩到 10 题以上，包括诱导性问题。从机制上说，系统提示词约束模型在上下文不足时明确拒答，而不是用通用知识冒充课程内容。

**Q9. 为什么不用 LangChain 或向量数据库？**

- 回答要点：当前单文档最多几十到上百条向量，numpy 检索 0.2 毫秒，5000 条时也只要 0.42 毫秒，用不上近似索引。我们还在论文复现实验里测过 HNSW：9000 条时比树索引快 20–30 倍，但在当前规模下没有必要。自研链路让我们能精确控制新鲜度检查和来源回溯。
- 翻页：附录 A1。出处：`docs/论文算法复现实验.md`。

**Q10. 教师改了图谱，问答会不会还用旧数据？**

- 回答要点：不会。每次问答都会比对 Neo4j 当前的 `kp_id` 集合和已存向量，不一致就重建该文档的向量。代价是失效粒度是整份文档，改一个知识点会让整份文档重新向量化。

### 6.3 学习路径与推荐

**Q11. 学习路径依赖前置关系，前置关系抽得准吗？**

- 翻页：第 21 页。

**Q12. 如果前置关系有环，路径会怎样？**

- 回答要点：路径查询用了限长变长匹配和 LIMIT，有环时不会死循环。但我们目前没有主动检测环，计划在入图后加环检测并提示教师。
- 出处：`path_recommender.py:120`、`:298-305`。

**Q13. 七个信号的权重是怎么定的？**

- 回答要点：目前依据教育学理论（最近发展区、遗忘曲线、ALEKS 的外缘概念）人工设定，权重和恒为 1，由代码断言保证。只对第 7 信号（语义相关度）做过开关对比。完整的消融和调参是下一步工作。

**Q14. 你们怎么证明系统能提升学习效果？**

### 6.4 工程与数据

**Q15. 重新抽取一份文档后，学生原来的学习记录怎么办？**

- 回答要点：先按第 5.6 节实测确认。如果会丢，诚实说明并给出映射迁移方案；如果不会丢，说明机制。

**Q16. SQLite 和 Neo4j 两个库之间没有事务，删除时一边失败怎么办？**

- 回答要点：删除按固定顺序执行：图谱 → 向量 → 学习记录 → 收藏 → 题库 → 文件 → 文档记录。每一步都是幂等的，任一步失败会返回明确错误、不会假装成功，重试会从失败处继续。所有删除都按 `(course_id, document_id)` 限定，不会误删同课程其他文档。
- 出处：`backend/app/services/document_service.py:282-326`。翻页：附录 A2。

**Q17. 系统能支持多少学生同时使用？**

- 回答要点：我们没有做过多用户压测，不能给出具体数字。已经做的是：SQLite 改为 WAL 模式解决并发写锁（13/13 测试通过）；图数据库故障时 2 秒超时加熔断。面向一个班级的规模我们有信心；更大规模需要压测，也可能需要把 SQLite 换成服务端数据库。
- 注意：不要说「支持百级并发」，没有数据支撑。

**Q18. 一门 300 页的教材，抽取要多久、花多少钱？**

- 回答要点：目前实测过的是 1.2 万 tokens 一章 41 秒。（T3、T7 完成后报告「规模 - 耗时 - 费用」曲线。）抽取采用 6000 tokens 分块、4 路并发，耗时随分块数大致线性增长。
- 注意：在 T3 完成前不要报具体费用。

**Q19. 课程资料发给外部大模型，有没有数据安全问题？**

- 回答要点：当前版本调用 DeepSeek 和 SiliconFlow 的公网接口，会把课程文本发出去。系统通过 OpenAI 兼容接口接入模型，可以替换为学校私有部署的模型。（T8 完成后补充实测结果。）

**Q20. 你们的系统和现有教学平台自带的知识图谱功能有什么区别？**

- 回答要点：围绕三点讲，不要贬低别人。第一，自动构建加教师校验，而不是纯手工建图；第二，图谱直接驱动问答、路径和练习，形成闭环；第三，每个能力都有可复现的评测数据，包括不好看的封存集数据。
- 注意：不要对未核实的竞品功能下结论。

### 6.5 赛题与团队

**Q21. 赛题叫「基于 AIGC」，生成式能力体现在哪？**

- 回答要点：四处。第一，大模型从文档抽取知识点和关系；第二，RAG 生成有来源的回答；第三，从试题文档中抽取题目导入题库，且明确约束模型不能自己解题（`question_extractor.py:24`）；第四，给题目自动推荐知识点（`kp_labeler.py`，字面、向量、图谱三层证据，只给候选，由教师确认）。
- 翻页：第 13 页。

**Q22. 团队分工是怎样的？你本人做了哪部分？**

- 回答要点：提前准备，每位成员能讲清自己负责模块的一个技术细节和一个踩过的坑。这类问题在答辩中经常出现，回答含糊会被认为参与度不足。
